### 2-2. Set-Cookie 처리
- `Domain=` 속성만 뺀다(`rewriteSetCookie`, `:81`). 그러면 쿠키는 프록시 호스트(127.0.0.1)에 붙는다. 여러 줄 Set-Cookie는 배열 그대로 둔다.
- `Secure`·`HttpOnly`·`SameSite`·`Path`·`Max-Age`는 바꾸지 않는다.
- d0111d8 쿠키 근거(`git show d0111d8:…`):
  - `apps/api/src/originproof_api/accounts.py:110-117`: `set_cookie(…, httponly=True, samesite="lax", secure=settings.session_cookie_secure or request.url.scheme == "https")`. Domain을 지정하지 않는다.
  - `settings.py:18`: `session_cookie_secure: bool = False`.
  - 프록시→API는 http이고 X-Forwarded-Proto를 넘기지 않는다. 그래서 기본 설정에서는 Secure가 붙지 않고, http://127.0.0.1:8790에서 쿠키가 저장된다.
  - `API_SESSION_COOKIE_SECURE=true`로 켜면 Secure가 붙는다. Chrome은 127.0.0.1을 안전한 출처로 봐서 받아들이지만, 다른 브라우저는 확인하지 않았다(질문 Q3).
- 쿠키는 포트를 가리지 않는다. 같은 브라우저에서 127.0.0.1:8768 등이 만든 쿠키도 함께 넘어간다. API는 자기 세션 쿠키 이름만 읽는다.

### 2-3. d0111d8 Origin 검사를 통과하는 방식 (근거: 감사 복제본에서 `git show d0111d8:<경로>`로 읽기만 함)
- `apps/api/src/originproof_api/main.py:120`: `app.add_middleware(RequestSecurity, settings=app_settings)`. CORS 미들웨어는 없다.
- `apps/api/src/originproof_api/security.py`
  - `:36`: `/v1/`·`/v2/`·`/v3/`로 시작하지 않는 경로(`/health/…`)는 검사 없이 통과한다.
  - `:55-57`: 요청 빈도를 넘으면 429에 `Retry-After`를 붙인다. 프록시는 이 헤더를 그대로 돌려준다.
  - `:58-63`: GET·HEAD·OPTIONS가 아니면 두 경우에 403 `ORIGIN_FORBIDDEN`을 준다. `origin`이 있는데 `browser_origins`에 없을 때, 또는 `origin`이 없고 `sec-fetch-site == "cross-site"`일 때다.
- `settings.py:23-28` / `.env.example:31`: `API_BROWSER_ORIGINS` 기본값은 `:3000`·`:8000`(localhost·127.0.0.1)뿐이다.
- **프록시 방식**
  1. 프록시가 쓰기(POST·DELETE)에 `security.py:58-63`과 같은 규칙을 먼저 적용한다. 허용 목록은 프록시 자기 출처 `http://127.0.0.1:<포트>`·`http://localhost:<포트>` 둘뿐이다. 다른 출처와 cross-site 쓰기는 프록시가 403으로 막는다(`op5-proxy.mjs:120-124`). 시험 "Origin 검사"가 이를 확인한다.
  2. 통과한 요청은 Origin·Sec-Fetch-Site를 빼고 넘긴다. API에서는 `origin is None`이고 `sec-fetch-site`도 없으므로 `:60-62` 두 조건이 모두 거짓이 되어 통과한다.
  3. 그래서 `.env`의 `API_BROWSER_ORIGINS`를 바꿀 필요가 없다. 업스트림 포트를 8000이 아닌 값으로 바꿔도 그대로 동작한다.
- CSRF는 그대로 지켜진다. 쓰기는 API의 `require_csrf`(예: `accounts.py` logout)가 세션의 `csrf_token`과 `X-CSRF-Token`을 비교한다. 프록시는 이 헤더를 손대지 않고 넘긴다.
- 빈도 제한 키: `security.py:53-55`는 연결한 쪽 IP(`scope["client"]`)를 쓴다. 프록시를 거치면 모두 127.0.0.1 하나로 세어진다. 브라우저가 직접 붙어도 127.0.0.1이라 차이는 없다.

## 3. T5 첫 화면 픽셀 비교

### 3-1. 스크립트
`node 개발/png-diff.mjs <기준.png> <비교.png>`
- 출력: 두 파일 크기, `다른 픽셀: N / 전체 (비율%)`, 판정
- 종료 코드: 0 = 같음 · 1 = 다른 픽셀 있음 · **2 = 크기 다름(실패, 비교 안 함)** · 3 = 읽기/형식 오류
- RGBA 네 값 중 하나라도 다르면 다른 픽셀로 센다(허용 오차 없음). 8비트 전 형식, 팔레트 1·2·4비트, 16비트(상위 바이트)를 읽는다. 인터레이스는 오류로 처리한다.
- 자기시험 `node --test 시험/png_diff.test.mjs` → **5건 통과**. 필터 0~4 디코드 일치, 1픽셀 차이=1, 같은 파일=0(종료 0), 다른 파일>0(종료 1), 크기 다름(종료 2), PNG 아님(종료 3)을 본다.

## 5. 남은 문제
1. 기본 `httpForward`(실제 node:http 호출)는 소켓 금지 때문에 시험하지 못했다. 처리기는 가짜 업스트림으로만 확인했다. 본부가 프록시와 finals-up을 함께 켠 뒤 실서버 칸으로 확인해야 한다.
2. 업스트림이 꺼져 있으면 이제 fetch 실패가 아니라 502 `UPSTREAM_UNREACHABLE`이 온다. 화면은 이것을 "서버가 지금 처리하지 못했어요."(`op5_client.js:96`, 5xx 일반 문구)로 보여 준다. 검사안내 4-4의 8번 기대 문구 "서버에 닿지 못했어요…"와 달라진다. 화면 코드(문구)는 바꾸지 않았다(질문 Q1).
3. 파일로 열었을 때 나오는 안내(`op5_client.js:89`)는 아직 "개발/협업 테스트 시작.command 로 연 화면에서 해 주세요."라고 이전 서버를 가리킨다(질문 Q2).
4. 실서버 모드는 `?mode=api` 쿼리나 기관 상태의 모드 단추로 켠다. 이 값은 localStorage에 남는다.
5. 픽셀 비교 2건은 미실측이다(3-4).

## 6. 질문 (추측해서 만들지 않음)
- Q1. 프록시가 업스트림에 닿지 못하면 502 `UPSTREAM_UNREACHABLE`을 주고 화면은 5xx 일반 문구를 보여 준다. 화면 문구를 "서버에 닿지 못했어요…"로 맞출지(op5_client.js 문구 표에 한 줄 추가) 정해 주세요. 아니면 검사안내의 기대 문구를 바꿀지(배너) 정해 주세요.
- Q2. `op5_client.js:89` 파일 모드 안내의 실행 파일 이름을 새 `.command`로 바꿀지 정해 주세요(화면 문구 변경).
- Q3. `API_SESSION_COOKIE_SECURE=true`로 검사할 계획이 있는지 알려 주세요. 있다면 Safari·Firefox에서 http://127.0.0.1의 Secure 쿠키를 받는지 본부 실측이 필요합니다(Chrome은 받는다).
- Q4. 기준 캡처가 1440×820이라 새 예약도 1440×820으로 했다. 이전 예약(`5안-연결후-첫화면-*`, 1440×900)은 기준과 크기가 달라 비교할 수 없다. 900 높이 기준을 새로 찍을지, 820으로 계속 갈지 정해 주세요.
