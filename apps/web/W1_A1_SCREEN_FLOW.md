# W1-A1 화면 흐름·권한 정의

상태: W1 API/웹 코드가 phase/W1에 병합됐으며 실제 연결은 [D 최종 QA](../../docs/qa/w1-final-verification.md)에서 확인했습니다. 소유자 본인 확인과 단계 최종 리뷰는 별도입니다. 아래 후속 Proof 기능 정의는 W1 구현 완료를 뜻하지 않습니다.

## 화면 흐름

### 공개 Proof 조회와 제한 내용 비교

1. 사용자가 Proof ID를 입력하거나 Proof ID만 포함한 링크를 엽니다.
2. 로그인 없이 발행자 이름/ID, 유형, 발행·만료 시각, 검증 상태, lifecycle, checks, 검사 범위와 확인 시각을 조회합니다.
3. 이 화면은 `PROOF_ONLY` 결과로 표시하고 입력 자료의 내용까지 일치한다고 말하지 않습니다.
4. 받은 자료를 대조하려면 비교를 별도 요청합니다. 발행기관 담당자 또는 지정 수신자로 로그인하지 않았다면 로그인 화면으로 안내합니다.
5. API가 허용한 주체임을 확인한 뒤에만 유형별 비교 필드를 제출하고, 실제 API 결과의 범위·불일치·미실행 검사를 표시합니다.

공개 링크에는 Proof ID만 둡니다. 원문 payload, 수신자 정보, binding, 자격 증명은 링크나 공개 화면에 넣지 않습니다. 조회는 읽기 전용이며 consume을 호출하지 않습니다.

### 발행기관 신청과 운영자 검토

1. 준비된 발행기관 테스트 계정으로 로그인해 자기 기관의 신청을 작성하고 제출합니다.
2. 제출 뒤 신청 상태를 조회합니다. 제출 중, 검토 대기, 승인, 반려와 실패를 구분합니다.
3. 운영자는 별도 운영자 테스트 계정으로 신청 대기 목록을 열어 신청 정보와 검토 사유를 확인합니다.
4. 운영자는 승인 또는 반려와 사유를 제출합니다. 중복 제출 중에는 재전송을 막고 완료 전까지 대기 상태를 보여줍니다.
5. 발행기관 담당자는 자기 신청의 결정 상태와 사유를 다시 조회합니다.
6. DB 검토 승인과 Registry 체인 활성화는 별도 상태입니다. W1 화면은 체인 상태가 미확인/미연결이면 이를 명시하고 등록 완료로 표현하지 않습니다.

신청의 실제 필드명·상태 enum·검증 규칙은 C의 W1-C1/C4 계약을 따릅니다. 위의 대기/승인/반려는 사용자에게 보여줄 의미 범주이며 wire enum을 정하지 않습니다. UX 초안에서 다룰 정보는 합성 기관 식별·신청 계정·신청 상태·운영자 검토 사유로 한정하며 실제 개인 연락처나 기관 비밀정보를 요구하지 않습니다.

현재 W1 로그인·신청 계약은 C의 병합된 [PR #23](https://github.com/OriginProof-3web/OriginProof/pull/23)입니다. 화면은 `username/password`, 서버 `account_id/username/role/issuer_id/csrf_token`, 신청 `issuer_name`, 결정 `decision/reason`을 소비합니다. `PENDING_REVIEW`, `APPROVED_PENDING_CHAIN`, `REJECTED`를 각각 검토 대기, 승인·체인 활성화 대기, 반려로 표시합니다. API의 실제 경로·필드와 브라우저 연결은 D의 최종 QA에서 재현했습니다. 승인된 W1은 실제 체인 활성화 완료와 다릅니다.

## 역할과 허용 동작

| 화면/동작 | 비로그인 사용자 | 수신자 | 발행기관 담당자 | 운영자 |
| --- | --- | --- | --- | --- |
| 공개 Proof ID 조회 | 허용 | 허용 | 허용 | 허용 |
| 제한 필드 비교 | 로그인 안내 | 지정된 자기 Proof만 요청 | 자기 기관 Proof만 요청 | 운영 권한만으로는 불가 |
| 신청 생성·자기 신청 조회 | 불가 | 불가 | 허용 | 관리 목적으로 신청 목록 조회 |
| 신청 승인·반려·운영 중지 | 불가 | 불가 | 불가 | 허용, 사유 기록 |
| 자기 기관 관리·발행 동작 | 불가 | 불가 | 승인된 자기 기관만 | 운영자 권한만으로는 불가 |
| 타 기관의 신청·Proof 변경 | 불가 | 불가 | 불가 | 승인·중지 등 명시된 관리 동작 외 불가 |

로그인 후 역할과 기관 소속은 서버가 반환한 계정 정보로 표시합니다. UI의 역할 선택이나 요청 body의 역할/기관 ID는 권한 근거가 아닙니다. 실제 허용 여부는 서버 응답으로 판정하고, 다른 기관의 자원은 API 정책에 따라 접근 거부 또는 존재를 숨기는 응답으로 처리합니다.

## 입력 필드 목록

| 화면 | 입력 | 제약·표시 |
| --- | --- | --- |
| 로그인 | 준비된 테스트 계정 식별자, 비밀번호 | 회원가입·외부 로그인 없음. 실제 계정 비밀값을 브라우저 저장소에 보관하지 않음 |
| 공개 조회 | Proof ID | 공개 링크도 Proof ID만 포함 |
| 제한 비교 | Proof 유형에 따라 받은 자료의 필드 | `PAYMENT_REQUEST`: 금액, 통화, 합성 대상 참조. `OFFICIAL_DOCUMENT`: 기관 코드, 문서 유형·번호, 문서 버전. 원본 기대값은 오류에 노출하지 않음 |
| 기관 신청 | 계약상 합성 기관 식별 정보와 신청 정보 | 정확한 필수 필드·길이·오류는 C의 W1-C1/C4 OpenAPI 계약에서 연결 |
| 운영자 검토 | 승인/반려 결정, 검토 사유 | 결정 주체·사유·현재 상태를 확인하고, 체인 반영은 별도로 표시 |

수신자나 역할/기관 식별값을 클라이언트가 임의 지정해 권한을 얻는 입력은 만들지 않습니다. 서버가 공급하거나 검증해야 하는 ID는 읽기 전용 표시이거나 요청에서 제외합니다.

## 대기·빈 상태·오류

| 상황 | 화면 처리 |
| --- | --- |
| 최초 진입·빈 신청 목록 | 무엇을 조회할 수 있는지 설명하고 다음 동작을 제공합니다. 성공 데이터가 있는 것처럼 채우지 않습니다. |
| API 요청 중 | 진행 중 상태를 텍스트로 알리고 같은 변경 요청의 중복 제출을 막습니다. |
| 세션 만료·미인증 (`401`) | 제한 동작을 완료하지 않고 로그인으로 안내합니다. 공개 ID 조회는 계속 사용할 수 있습니다. |
| 역할·소유권 거부 (`403`, 또는 자원 존재를 숨기는 `404`) | 접근이 거부됐음을 설명하고 보호된 필드나 자원 존재 여부를 추가 노출하지 않습니다. |
| 입력 검증 실패 (`422`) | 서버 필드 오류를 해당 입력에 연결하고 입력을 보존해 수정할 수 있게 합니다. |
| 신청 검토 대기·체인 미확인 | DB 신청 결정과 체인 활성 상태를 분리해 표시합니다. 미확인을 성공이나 활성으로 바꾸지 않습니다. |
| 네트워크 오류·서버 오류 (`5xx`) | 성공 상태를 지우지 않은 채 새 성공으로 대체하지 않고, 안전한 재조회/재시도 동작을 제공합니다. 변경 결과가 불명확하면 무조건 재제출하지 않고 먼저 상태를 조회합니다. |
| Proof 미등록·검사 불충분 | API의 `NOT_REGISTERED`/`INCONCLUSIVE`, lifecycle, reason code와 미실행 검사를 그대로 구분합니다. 위조나 사용 가능으로 단정하지 않습니다. |

오류는 색만으로 구분하지 않습니다. 입력 오류는 label과 연결하고, 요청 완료·실패와 상태 변경은 보조기술이 읽을 수 있도록 알립니다.

## W1-A1 확인 기준

- 공개 ID 조회와 인증된 내용 비교가 서로 다른 동작과 결과 범위로 정의되어 있습니다.
- 사용자·발행기관·운영자 허용/금지 동작이 구분되어 있으며 역할 선택으로 권한을 부여하지 않습니다.
- 입력·대기·빈 결과·세션 만료·권한 거부·검증 오류·API 오류가 정의되어 있습니다.
- DB 신청 승인과 실제 체인 활성 상태를 별도로 표현합니다.
- 세션, payload, binding, 개인키 또는 비밀값을 URL·브라우저 저장소·공개 응답에 노출하지 않습니다.
- API route·wire field·오류 코드 중 미합의 항목은 C의 계약에서 확정하며 이 문서는 별도 API 계약을 만들지 않습니다.
