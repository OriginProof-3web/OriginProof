# OriginProof 통합 개발 계획서

> 의심 자료의 피싱 정황을 설명하고, 참여 기관의 납부 요청·증빙에 대한 발행 출처·보호 내용·현재 상태를 검증하는 서비스
>

문서 목적: 4인 팀이 설계, 개발, 테스트, 데모에 공동으로 사용하는 실행 기준서

작업 버전: 4.0 · 개정일: 2026-10-09

개정 목적: 예선 MVP를 기반으로 **W1~W7의 7개 개발 단계로 완성하고 발표할 실제 동작 웹 서비스**의 범위와 완료 기준을 확정합니다.

이 문서는 저장소 안의 개발 계획 기준본입니다. 저장소 밖의 `originproof_integrated_development_plan.md` v1.0을 복사해 개정했으며, 앞으로 계획 변경은 이 파일에서 관리합니다. 원본은 이전 계획 기록으로 보존합니다.

개발 전 담당자는 3장(권한), 7~9장(발행·AI·저장), 15.10절(v4.0 보완 작업), 16장(검증), 17장(범위)을 확인합니다. 2026-10-08 ‘블록체인 저장 범위 구체화’ 대화의 합의와 사용자님의 v4.0 반영 요청을 기준으로 합니다. [멘토링 합의 원문](mentoring_round1_blockchain_decisions.md), [ADR 0002](adr/0002-v4-hybrid-verification.md)에 변경 근거와 전환 기준을 남깁니다.

**계획의 우선순위:** 이 문서 v4.0과 ADR 0002가 변경한 범위는 기존 v3.0 설명보다 우선합니다. 변경하지 않은 서명·권한·상태·consume 정책은 [ADR 0001](adr/0001-finals-contracts.md)을 유지합니다. 현재 runtime 계약은 코드·생성 Schema·ABI·[서명 명세](signing_spec.md)로 확인하며, 계획 개정만으로 구현·리뷰·연결을 완료 처리하지 않습니다.

**이번에 반영한 결정:** 납부 요청 중심의 발행 증거 검증, 가상 기관 명부·이메일·내부 승인·운영자 승인, 보호 항목의 서명·해시, 텍스트·녹음·문서/이미지 AI 분석, DB·체인 저장 분담, 통합 보고서와 보관 원칙, 공개 체인·서버 밖 검증 목표입니다. 두 합성 기관·두 Proof 유형과 기존 회귀는 유지합니다.

**개발 착수 기준:** [ADR 0003](adr/0003-v4-development-baseline.md)에 입력 형식·상한, 보관/삭제 기간·분석 소유권, 코드 만료/시도 제한, AI 평가 방법·초기 합격선을 선정했습니다. 새 납부 3.0.0 필드·정규화와 API/보고서는 소유자 검토용 계약 초안입니다. 선정한 기본값과 계약 검토·구현·측정 완료를 구분합니다.

**개발 중 확정할 것:** 실제 AI/STT/OCR 모델·실행 예산, 공개 네트워크·배포 범위/확정 기준, 공유 계약의 최종 생성물·필요 ABI 변경, 행사 규격입니다. UI/UX의 화면·배치·동선·시각 기준은 [설계 v1.0](ui_ux_design.md)에 권장안을 작성했으며 구현·계약 검토·사용성 검증이 남았습니다. 공개 체인 목표를 로컬 시연 성공으로 대체하지 않습니다. 기존 독립 구현은 계속 진행하며 실제 소비자 연결 전에 계약 리뷰를 마칩니다.

[최종 산출물 구체화 검토안](final_deliverables_draft.md) 0.4는 이 계획의 산출물별 상세 부록입니다. D01~D08의 포함 내용·제공 단위·완료 기준, F01~F23 연결표, 착수 기준·계약 검토·후속 결정과 인계 목록을 구분했습니다. UI/UX 설계 작성과 팀 검토·사용성 검증을 구분합니다. 문서 작성은 구현 완료를 뜻하지 않습니다.

### 개정 이력

v4.0 UI/UX 설계 보완(2026-10-09): [설계 v1.0](ui_ux_design.md)에 15개 화면 템플릿, 역할별 동선·입력/결과·저장·관리 배치, 공통 상태/문구, 시각 토큰·모바일·접근성 기준과 UX01~UX10 검사안을 작성했습니다. A가 구현하고 C/B/D가 계약·체인·분석 상태를 검토합니다. 제품 코드·공유 계약 생성물·사용성 검증 완료를 뜻하지 않습니다.

v4.0 착수 기준 보완(2026-10-08): ADR 0003에 입력·보관·인증 제한의 기본값, 새 모델/API 초안과 전환·검토 순서, AI 평가 선행 기준을 작성했습니다. 기존 범위를 유지하며 UI/UX·모델/공개 네트워크 선택·행사 조건은 후속 작업으로 구분합니다.

아래 v3.0 이하 설명은 당시 결정의 기록입니다. 현재 범위는 위 v4.0 및 17장을 따릅니다.

v3.0 개정: 본선 기준으로 루트·하위 에이전트 지침을 정리하고, 두 유형·키 교체·검증 상태·수신자 binding·공개 조회·체인 consume·Operation 복구 정책을 확정합니다. 자기 영역 독립 구현·검사와 실제 연결·단계 완료의 차이를 명시합니다. 이미 승인된 정책은 재승인하지 않으며 일반 구현 선택은 담당자가 진행합니다. 이번 개정은 기능 구현 완료를 뜻하지 않습니다.

v2.10 개정: 다른 담당자가 기다리는 선행 계약·구현의 원격 공유 시점과 인계 항목을 15.1절에 명시합니다.

v2.9 개정: OpenAI 후보 추출 기본 모델을 GPT-6 Luna(`gpt-6-luna`)로 변경하고, `OPENAI_MODEL` 재정의와 기본 Mock provider 동작을 명시합니다.

v2.8 개정: 개인 기여·기술적 판단·문제 해결·AI 활용·검증 증거를 PR에 기록하고, 개인별 단계 요약과 단계 완료 PR에서 연결하도록 합니다. 공통 PR 템플릿과 포트폴리오 기록 안내를 추가하며, 에이전트의 종료 절차와 단계 완료 조건에 기록 확인을 포함합니다.

v2.7 개정: 단계 완료 시 `phase/W1`~`phase/W7`을 포트폴리오용 결과 브랜치로 고정·보존하고, 다음 단계 브랜치는 직전 단계가 반영된 `integration`에서 시작하도록 명시합니다. 단계별 기준 SHA·작업 ID·검사 결과도 남깁니다.

v2.6 개정: 여러 개발 단계를 한 팀원 작업 묶음으로 이어서 진행할 때의 작업 ID 순서, 단계별 PR 분할, 묶음 완료 기준을 15.1절에 추가합니다. 기존의 상세 작업 ID·선행 조건·단계 집계 브랜치 규칙은 그대로 기준으로 사용합니다.

v2.5 개정: W1~W7을 달력상 주차가 아닌 개발 단계로 사용하고, 모든 단계의 팀원별 작업을 이슈 단위로 상세화합니다. 테스트 계정 로그인·로컬 웹 시연·로컬 EVM을 기본 범위로 확정하고 테스트넷은 핵심 개발 완료 후 논의할 선택 확장으로 옮깁니다. 단계별 집계 브랜치·PR·integration 반영 절차와 의존 브랜치 동기화 규칙을 14장·15.1절에 추가합니다. 에이전트 작업 지시·협업 경계·검증 기준은 15.1~15.9절, 확정된 선택과 남은 결정은 21.1절에서 관리합니다.

주요 개정: 운영자 화면과 발행자 콘솔을 P0로 올리고, 웹에서 기관 승인·공개키 등록·Proof 발행·검증·폐기를 수행하도록 합니다. W0는 W1 시작 준비로 포함하고, W1~W7 이후 발표 이틀에는 새 기능 개발을 배정하지 않습니다.

핵심 원칙: Don’t detect the fake. Verify the real.

## 0. 프로젝트 요약

OriginProof는 사용자가 제출한 문자·녹음·문서/이미지의 피싱 정황과 이유를 AI로 설명하고, 연결 가능한 기관의 발행 기록으로 출처·보호 내용의 일치·현재 유효성을 검증합니다. 대표 사례는 기관·기업의 납부 요청입니다. AI 위험 분석과 서명·해시·체인에 근거한 발행 검증은 독립된 결과로 한 보고서에 표시합니다. 납부 의무의 정당성과 금액의 업무상 정확성은 발행기관의 책임입니다.

### 최종 제품과 제출물

최종 산출물은 **운영자, 발행기관 담당자, 일반 사용자가 웹에서 각자의 작업을 수행하는 서비스 시제품**입니다. W7 완료 시 실행 가능한 RC를 준비하고, 이후 발표 일정에 맞춰 시연합니다. W1~W7은 보기 편하게 나눈 단계이며 각각 1주일을 뜻하지 않습니다. 서비스 기동 이후 핵심 시연은 브라우저에서 진행합니다.

| 산출물 | 최종 제공 내용 | 완료 증거 |
| --- | --- | --- |
| 사용자 웹·통합 보고서 | 텍스트·녹음·문서/이미지 제출, AI 의심 근거·위치·확인 행동, ID·QR/링크 기반 발행 검증 | 세 입력 경로, 정상·변조·기록 없음·판단 보류를 실제 결과로 표시 |
| 발행자 콘솔 | 가상 기관 인증·내부 승인, 공개키 관리, 납부 요청·문서 발행·조회·철회, 허가된 사용 처리 | 인증·승인 누락은 거부하고 화면 조작으로 DB·체인 상태가 변경됨 |
| 운영자 화면 | 기관정보·이메일·내부 승인 결과 검토, 최종 승인·반려·중지, 변경 이력 | 앞선 확인 없이 활성화하지 않고 자기/타 기관의 무권한 승인을 거부 |
| 공통 API·검증 코어 | 서로 다른 분야의 두 Proof 유형과 공통 Signed Proof 구조 | Schema·OpenAPI·Golden Fixture·통합 테스트 |
| 공유 Registry·별도 검증 자료 | 기관·키·불변 발행 증거·상태 이력, 권한 있는 수신자의 원본·서명·검증 규칙 | 로컬 개발 검증과 선택할 공개 네트워크 검증을 구분하고 서버 밖 대조를 재현 |
| 재현·발표 패키지 | 소스·lockfile·실행 안내·테스트 결과·영상·발표 자료 | 다른 노트북 재현과 전체 시연 리허설 |

텍스트·녹음·문서/이미지 분석은 v4.0 합의 범위입니다. 실제 국세청 API·실제 이메일 전송 대신 가상 사업자 명부와 데모 메일함을 사용합니다. 합성 기관 2곳으로 권한 확인과 발행·검증을 시연하며 실제 기관 신원 확인이나 실제 결제 완료로 표현하지 않습니다. 공개 네트워크·입력 제한·평가 기준 등 미확정 값은 21.1절에서 추적합니다.

### 현재 출발점과 남은 차이

점검 기준은 로컬 `feat/mvp-demo-page@18c0ae8`입니다. 원격 PR 병합 상태나 현재 실행 성공을 보장하는 기록은 아닙니다. 이 표는 MVP에서 본선으로 넘어갈 때의 출발점 기록이며 현재 branch별 기능 상태는 작업 PR·검사 SHA로 확인합니다.

| 영역 | 확인된 출발점 | 본선까지 남은 일 |
| --- | --- | --- |
| MVP 검증 | 카드 알림 1종, 서명·해시·필드·Issuer/Key 조회 | 요청형과 문서형으로 공통 코어 확장 |
| Registry | 로컬 Issuer/Key 계약·배포·Reader | 웹 쓰기 권한, Proof 폐기·consume, 로컬 배포 재현 |
| 발행 | seed로 합성 Proof 생성 | 인증된 기관이 화면에서 새 Proof 발행 |
| 웹 | 후보 필드를 입력하는 검증 데모 | 사용자 입력 개선, 발행자 콘솔, 운영자 화면 |
| AI | 후보 추출기와 OpenAI 어댑터, Mock 이미지 replay | 실제 이미지 성능은 별도 평가 후 표시 |
| 통합 | 기존 문서에 정상·변조 HTTP E2E 및 두 개발환경 재현 기록 | 확대된 전체 웹 흐름을 새 RC에서 검증 |

위 표는 v3.0 작성 당시의 출발점입니다. v4.0에서 추가한 AI 분석·기관 인증·보호 필드·저장 및 별도 검증은 15.10절의 후속 구현이며 현재 완료 여부를 추정하지 않습니다.

기존 완료 기록은 [MVP 통합 기록](runbooks/mvp_integration_sequence.md)과 [데모 안내](runbooks/mvp_demo.md)를 참고합니다. 아래 단계별 완료 기준은 앞으로 달성할 목표입니다.

## 1. 문제 정의

사용자는 기관명, 로고, 전화번호, URL, 화면 디자인, 문서 양식과 같은 보이는 정보를 보고 진위를 판단합니다. 그러나 이러한 정보는 복제, 생성, 편집될 수 있습니다. 기존 피싱 탐지는 위험 가능성을 알려주지만 실제 발행 주체가 해당 요청이나 문서를 만들었다는 사실을 직접 증명하지는 못합니다.

OriginProof는 세 가지 신뢰 단절을 해결합니다.

1. 발행자 신뢰: 요청이나 증빙을 실제 상대방 또는 공식 기관이 발행했는가?
2. 내용 무결성: 대상, 금액, 행동, 사건번호, 문서번호 등 핵심 내용이 바뀌지 않았는가?
3. 현재 유효성: 만료, 취소, 폐기, 키 탈취, 재사용 상태가 아닌가?

| 방식 | 주요 질문 | 역할과 한계 |
| --- | --- | --- |
| 피싱 문자 탐지 | 이 문구가 수상한가? | 확률적 판단이며 실제 발행 여부는 증명하지 못함 |
| 악성 URL 탐지 | 이 주소가 위험한가? | URL 밖의 요청과 문서에는 적용이 제한됨 |
| 기관 자체 앱 | 기관 내부 기록에 존재하는가? | 기관별로 분리되어 공통 검증 계층이 없음 |
| 이미지 포렌식 | 화면이나 문서가 편집되었는가? | 편집 흔적이 없다고 정상 발행을 의미하지 않음 |
| OriginProof | 어떤 정황이 의심되며, 기관이 실제로 발행한 보호 내용과 일치하는가? | AI 분석은 기록 없이도 제공하고, 발행 검증은 연결 가능한 Proof와 신뢰 근거가 필요함 |

## 2. 범위와 원칙

| 유형 | 예시 | 공통 검증 내용 |
| --- | --- | --- |
| 요청형 | 송금, 결제, 승인, 청구 요청 | 요청자, 행동, 대상, 금액, 수신자, 유효기간, 재사용 |
| 거래 증빙형 | 송금 완료 증빙, 결제 영수증, 청구서 | 발행자, 거래 ID, 금액, 상태, 발급 시각 |
| 공식 문서형 | 증명서, 확인서, 통지서, 허가서 | 기관, 문서번호, 대상자, 버전, 발급과 폐기 상태 |
| 법률 절차 증빙형 | 접수증, 송달 자료, 전자서명된 제출본 | 기관, 사건이나 접수번호, 제출 시각, 현재 상태 |
| 확장형 | 계약 확인, Web3 서명, AI Agent 요청 | 발행 주체, 권한, 대상, 정책, 서명, 상태 |

### 비목표

1. 모든 문자와 이메일을 자동 수집해 피싱 여부를 분류하지 않습니다.
2. 화면 캡처만으로 실제 거래가 존재한다고 보증하지 않습니다.
3. 문서 내용의 법률적 타당성이나 사실관계를 판단하지 않습니다.
4. 실제 기관을 사칭한 데모를 만들지 않습니다.
5. 개인정보와 원문을 퍼블릭 블록체인에 저장하지 않습니다.
6. AI 결과만으로 VERIFIED 또는 TAMPERED를 결정하지 않습니다.

| 사용 가능한 표현 | 사용하면 안 되는 표현 |
| --- | --- |
| 등록된 발행 기록과 일치합니다 | 법적으로 진짜입니다 |
| 발행 기록을 확인할 수 없습니다 | 가짜임이 증명되었습니다 |
| 핵심 내용이 등록 원본과 다릅니다 | AI가 사기를 확정했습니다 |
| 현재 폐기되었거나 유효하지 않습니다 | 화면만으로 실제 거래가 보장됩니다 |
| 확인 자료가 부족합니다 | 등록되지 않았으므로 무조건 위조입니다 |

## 3. 사용자, 화면과 권한

세 역할은 하나의 Next.js 앱에서 화면과 서버 권한을 구분합니다. 기관 역할 안에는 발행 신청 담당자와 사전에 지정된 내부 승인 담당자를 별도 계정·권한으로 둡니다. 내부 승인자는 자기 신청이나 다른 기관 신청을 승인할 수 없습니다. 화면을 숨기는 것만으로 권한을 보호하지 않습니다. 로그인·기관 소속·객체 소유권을 모든 변경 API에서 검증하고, 체인 쓰기는 허가된 계약 호출자로 제한합니다.

| 역할 | 필수 화면·행동 | 허용하지 않는 행동 |
| --- | --- | --- |
| 일반 사용자 | 세 종류 자료 제출·AI 보고서 확인, Proof ID·QR/링크 조회, 보호 필드 비교·현재 상태 확인, 보고서/원본 저장 선택 | 기관 승인, 키 관리, 임의 Proof 발행·폐기 |
| 발행기관 담당자 | 기관정보·이메일 확인·권한 신청, 지정 승인자의 내부 검토, 자기 기관 키·Proof 관리 | 자기 신청 승인, 운영자 최종 승인 대행, 타 기관 키·Proof 변경 |
| 플랫폼 운영자 | 기관 신청 검토·승인·반려·중지, 변경 이력 확인 | 운영자 권한만으로 타 기관의 서명을 생성 |

관리·수신자 인증은 사전 준비한 테스트 계정으로 구현합니다. 공개 회원가입·외부 로그인은 핵심 개발 완료 후 팀과 합의한 경우에만 추가합니다. 테스트 계정도 서버에서 인증·기관 소속·권한을 검증하며 운영자/두 기관의 신청자·내부 승인자/수신자 계정을 구분합니다. AI 분석용 제출 자료와 보고서는 제출 주체의 접근 범위를 적용하며, 이를 제출했다는 사실만으로 기관의 제한 원본 열람 권한을 얻지 않습니다.

일반 검증 조회는 발행자 관리 로그인 없이 가능하도록 합니다. 금액·대상·문서번호 등 제한 payload의 조회·비교와 대상자 행동은 발행기관 담당자 또는 지정 수신자의 인증을 요구합니다. 익명 비교로 제한 필드를 추측할 수 없도록 권한 검사 전 비교 결과를 반환하지 않습니다. 기관별 계정을 분리하며, 화면의 역할 선택만으로 권한을 얻을 수 없어야 합니다. 일반 검증 요청과 1회성 사용 처리는 분리하고, consume은 발행자 또는 지정된 수신자만 수행합니다.

분석 제출·보고서/원본 보관은 ADR 0003의 착수 정책에 따라 준비된 테스트 계정 로그인 후 이용하며, 소유자는 서버 세션에서 정합니다. 공개 ID/QR 조회는 익명을 유지합니다. 보고서 소유권과 제한 Proof 원본 접근 권한은 별도입니다.

### 브라우저에서 이어지는 필수 흐름

1. 발행기관 담당자가 가상 명부의 사업자번호·기관명·대표자명·개업일자와 일치하는 정보로 신청하고 데모 메일함에서 업무용 이메일 코드를 확인합니다.
2. 사전 지정된 기관 내부 승인자와 운영자가 순서대로 승인합니다. 온체인 활성화를 확인해야 발행할 수 있고 반려·중지·권한 회수 후에는 발행을 거부합니다.
3. 승인된 기관 담당자가 발급키를 생성·등록합니다. 웹에는 공개 signer, key ID, 유효 기간과 상태만 표시합니다.
4. 기관 담당자가 허용된 유형의 내용을 입력하고 발행합니다. 서버가 정규화·서명·저장하고 Proof ID·QR/검증 링크를 반환합니다.
5. 사용자가 해당 Proof를 조회합니다. ID만 입력하면 발행 기록의 유효성만 설명하고, 자료의 내용 일치 여부는 사용자가 제공한 필드를 실제 비교한 경우에만 표시합니다.
6. 사용자가 문자·녹음·문서/이미지를 제출하면 텍스트를 추출하고 AI가 피싱 정황·근거 위치를 설명합니다. 요청 ID가 있으면 접근 권한 확인 후 원본·서명·체인과 보호 필드를 대조합니다. ID가 없으면 AI 분석과 발행 확인 불가를 표시합니다. 인식이 불완전하면 사용자 확인 또는 판단 보류로 처리합니다.
7. 담당자가 키 또는 Proof를 폐기하면 사용자 재검증에 변경된 상태가 반영됩니다.
8. 요청형 Proof는 권한 있는 계정이 사용 처리하며, 중복·동시 사용 시 하나만 성공합니다.

기존 합성 fixture의 `Origin Mock Bank`·`PAYMENT_REQUEST`와 `Origin Mock Office`·`OFFICIAL_DOCUMENT` 두 유형은 유지합니다. v4.0의 대표 설명·시연은 기관·기업의 납부 요청이며, 기존 가상 은행 이름은 실제 은행의 참여나 도입을 뜻하지 않습니다. 기존 필드·기간·수신자 binding은 ADR 0001을 유지하고, 새 납부 보호 필드는 4장·ADR 0002의 버전 전환으로 반영합니다. 기존 `CARD_PAYMENT_NOTICE`는 회귀 검증 사례로 보존합니다. 실제 결제나 실제 기관 업무는 수행하지 않습니다.

## 4. 통합 Proof 모델

모든 분야는 동일한 Signed Proof Envelope를 사용하고 세부 필드는 `proof_type`별 payload schema로 분리합니다.

아래 표는 ADR 0001의 v3.0 기준 모델이며, v4.0 보호 항목을 추가할 새 payload 계약은 이 절의 전환 규칙을 따릅니다. 기준 구현의 `CARD_PAYMENT_NOTICE` v1을 보존하고 W1-C3에서 요청형·문서형 `schema_version=2.0.0`, `app_domain=originproof.finals` 모델을 추가합니다. 정확한 필수 필드·비교 범위는 ADR 0001의 1·4·5절을 따릅니다. 기존 모델의 key ID·chain ID·app domain·signature scheme도 보존하고 [서명 명세](signing_spec.md)와 Golden Fixture를 기준으로 호환성을 검증합니다. 변경 가능한 생명주기 상태는 서명된 원문과 분리해 조회합니다.

| 필드 | 설명 | 필수 여부 |
| --- | --- | --- |
| proof_id | 전역 고유 식별자 | 필수 |
| issuer_id | 발행 주체 식별자 | 필수 |
| proof_type | 요청, 증빙, 문서 등 유형 | 필수 |
| schema_version | 정규화와 검증 규칙 버전 | 필수 |
| payload_hash | canonical payload 해시 | 필수 |
| subject_binding_hash | Proof별 salt와 서버 수신자 token의 canonical hash | 본선 두 유형 필수 |
| issued_at | 발행 시각 | 필수 |
| expires_at | 만료 시각, 유효 구간은 `[issued_at, expires_at)` | 본선 두 유형 필수 |
| nonce | 서버가 생성하는 최소 128비트 무작위 값 | 본선 두 유형 필수 |
| single_use | 요청형 true, 문서형 false | 본선 두 유형 필수 |
| lifecycle_status (별도 조회) | ACTIVE, CONSUMED, EXPIRED, PROOF_REVOKED 등 현재 상태 | 검증 결과에 반영 |
| metadata_hash | 추가 메타데이터 무결성 | 선택 |
| signature | 발행자 전자서명 | 필수 |

P0는 아래 두 유형이며 그 밖의 행은 향후 확장 예시입니다. binding 필드는 서버가 계산하고 사용자가 직접 지정하지 않습니다. 금액은 `amount_minor`로 통일합니다.

| Proof 유형 | 주요 필드 |
| --- | --- |
| ACTION_REQUEST | action, target, recipient_binding, policy_id |
| PAYMENT_REQUEST (P0) | amount_minor, currency, payer_binding, beneficiary_binding, target_hash — 모두 필수 |
| TRANSACTION_RECEIPT | transaction_id, amount, currency, sender_token, recipient_token, status |
| OFFICIAL_DOCUMENT (P0) | institution_code, document_type, document_number, subject_token, version — 모두 필수 |
| LEGAL_PROCESS_PROOF | authority_code, case_or_receipt_number, filing_type, filed_at, status |
| GENERAL_CREDENTIAL | credential_type, holder_binding, claim_hash, valid_from, valid_until |

### v4.0 납부 요청 보호 범위와 버전 전환

발행기관·요청 식별자, 금액·통화, 수취 은행·계좌·예금주, 납부 목적·기한, 발행 시각·유효기간, 특정 수신자 연결 정보를 서명·해시에 포함합니다. 디자인·단순 안내 문구처럼 제외한 부분까지 일치한다고 표현하지 않습니다. 보호 항목을 바꾸려면 기존 요청을 철회하고 새 ID로 발행합니다.

기존 `beneficiary_binding`은 기관 ID의 연결값이고 `target_hash`는 합성 참조의 해시입니다. **이 필드만으로 실제 수취 계좌·예금주·목적 전체를 보호했다고 간주하지 않습니다.** C/B가 새 필드의 정규화·서명/해시 포함 범위·선택적 비공개 연결값을 정의하고 새 schema version·예시·Golden Fixture·OpenAPI·체인 digest 대조를 함께 준비합니다. ADR 0003의 5절에 새 납부 3.0.0과 필드/정규화 초안을 작성했으며, 소유자 리뷰·생성물/Golden 검사 뒤 구현 계약으로 확정합니다.

기존 카드 v1과 본선 2.0.0 자료는 원래 규칙으로 검증하며 보호 범위를 표시합니다. 기존 서명을 조용히 변경·소급 재서명하지 않습니다. 새 정보가 필요한 자료는 재발행 경로를 제공하고, 모델·DB·UI·생성물·필요한 ABI 변경과 데이터 전환을 같은 작업으로 추적합니다. 공개 해시도 추측 공격 가능성을 검토하며 원문·개인정보는 체인 밖에서 보호합니다.

### Canonicalization

1. UTF-8 NFC 정규화를 적용합니다.
2. 키 순서를 고정한 JSON으로 직렬화합니다.
3. 금액은 최소 화폐 단위 정수와 통화 코드로 분리합니다.
4. 날짜는 시간대를 포함해 UTC RFC 3339로 직렬화합니다. 새 v2는 초 단위로 검증하여 체인과 만료 경계를 일치시키고 기존 v1 직렬화는 보존합니다.
5. 수신자 연결은 기존 token/salt 방식을 유지합니다. 납부 보호 필드의 원본은 제한된 체인 밖 저장소에 두고 서명·해시에 결합합니다. 체인에 둘 검증용 연결값의 정규화·추측 방지는 새 계약에서 검토합니다.
6. 기존 payload 해시와 schema version을 포함한 서명 구조는 signing_spec.md를 따릅니다. 변경은 버전·Golden Fixture·마이그레이션 검토 후 적용합니다.
7. 언어별 구현 결과가 Golden Fixture에서 동일해야 합니다.

## 5. 검증 결과 모델

검증 결과, 생명주기 상태, 실패 사유를 분리합니다. 아래는 v3.0 확정 정책이며 실제 enum은 C가 공통 Python 모델에 반영·생성합니다. v2는 실제 검사한 발행 근거·내용과 현재 lifecycle을 분리하고, 기존 v1의 만료 조합은 보존합니다. 검사 순서·대표 상태 우선순위·사유 코드는 ADR 0001의 4절을 따릅니다.

| Verification Status | 의미 | 사용자 안내 |
| --- | --- | --- |
| VERIFIED | 발행 근거·서명·hash 및 요청한 범위 검사 성공 | ID 조회는 발행 기록 확인, 전체 비교 성공은 내용 일치; 현재 사용 가능 여부는 lifecycle과 별도 |
| NOT_REGISTERED | Proof 또는 발행자를 찾을 수 없음 | 검증 가능한 발행 기록이 없습니다 |
| TAMPERED | 서명 또는 핵심 내용이 불일치 | 등록된 원본과 내용이 다릅니다 |
| INCONCLUSIVE | 화질, 형식, 입력 부족 | 추가 확인 자료가 필요합니다 |
| ERROR | 시스템 또는 네트워크 오류 | 잠시 후 다시 시도해 주세요 |

| Lifecycle Status | 의미 |
| --- | --- |
| ACTIVE | 현재 유효함 |
| EXPIRED | 유효기간이 지남 |
| CONSUMED | 1회성 Proof가 이미 사용됨 |
| PROOF_REVOKED | 발행자가 해당 Proof를 폐기함 |
| ISSUER_SUSPENDED | 발행자의 신뢰 상태가 중지됨 |
| ISSUER_KEY_REVOKED | 발행키가 폐기됨 |

기존·확장 Reason Code의 예시는 `INVALID_SIGNATURE`, `PAYLOAD_HASH_MISMATCH`, `TARGET_MISMATCH`, `AMOUNT_MISMATCH`, `RECIPIENT_MISMATCH`, `SUBJECT_BINDING_MISMATCH`, `POLICY_MISMATCH`, `PROOF_NOT_FOUND`, `SCHEMA_UNSUPPORTED`, `LOW_OCR_CONFIDENCE`, `REPLAY_DETECTED`입니다.

AI 위험 수준(위험 높음 / 주의 필요 / 뚜렷한 의심 정황 없음 / 판단 보류)은 위 verification/lifecycle enum과 별도입니다. AI가 낮은 위험을 반환해도 발행 검증을 생략하지 않으며, 발행 근거가 일치해도 AI 경고를 삭제하지 않습니다.

판정은 Proof 식별, domain/network, 신뢰 근거, 서명과 해시, 생명주기, binding, 유형별 필드를 포함합니다. ADR의 확정 순서·조기 종료·NOT_RUN 표시를 구현하며 서명을 검사하지 않고 VERIFIED로 표시하지 않습니다. ID 조회는 PROOF_ONLY, 전체 비교는 FULL_COMPARISON, 입력 부족은 PARTIAL_COMPARISON으로 구분합니다. 최종 RC 기준 검사를 통과한 만료/폐기/소비 Proof는 v2에서 VERIFIED와 해당 lifecycle을 함께 반환하되 현재 사용 불가로 표시합니다. 의존성 장애는 INCONCLUSIVE로 보류합니다.

## 6. 시스템 아키텍처

| 계층 | 구성요소 | 책임 |
| --- | --- | --- |
| Web | 사용자 화면, 발행자 콘솔, 운영자 화면 | 역할별 입력·승인·발행·검증·폐기 및 처리 결과 |
| API | 인증·기관 소속·객체 권한·요청 제한 | 모든 변경의 권한 검증과 요청 추적 |
| Core | Resolver, Canonicalizer, Verification Engine | 서명·해시·유형별 내용·현재 상태 판정 |
| Signing | 기관별 합성 서명기 | 허가된 발행 요청에 서명, 개인키 보호 |
| Blockchain | Issuer·Key·Proof Status Registry | 승인된 기관·키·Proof의 공동 신뢰 상태 |
| Off-chain | PostgreSQL·보호된 파일 저장소 | 기관/계정·원본/서명·분석/보고서·작업/감사·보관/삭제 |
| Worker | 체인 이벤트 수집·작업 상태 동기화 | 확인된 결과 반영, 재시작·중복 처리 |
| Input / AI | Analyzer·파일 처리 | 텍스트·녹음·문서/이미지의 텍스트·위치 추출과 피싱 정황 분석 |

발행 흐름: `로그인 → 기관·계정·키 권한 확인 → 보호 내용 확정 → 정규화·서명 및 검사 → DB 저장 → 체인 등록·확정·재조회 → 등록 완료·Proof ID/QR 전달`

관리 흐름: `권한 확인 → 변경 요청 → 체인 제출 → 확인 → 상태 재조회 → 화면·감사 이력 반영`

사용자 흐름: `자료 입력 → 텍스트/위치 추출·AI 분석 → 요청 ID 식별 → 권한 있는 원본/서명·체인 대조 → AI 근거와 발행 검증을 함께 표시`. ID/QR만 조회하거나 직접 필드를 비교하는 경로도 유지하며 상세 검사 순서는 5장을 따릅니다.

### 장애와 재시도

1. 제출 대기·성공·실패를 구분하고, 트랜잭션 제출만으로 등록 성공을 표시하지 않습니다.
2. 요청 ID로 중복 발행·중복 변경을 방지합니다. timeout 후에는 기존 작업 결과부터 조회합니다.
3. 현재 체인 상태를 확인할 수 없으면 안전한 보류 결과를 표시합니다. 오래된 캐시만으로 현재 유효하다고 판정하지 않습니다.
4. 로컬 체인 장애 시 검증된 복구 절차로 재기동·재배포하고 manifest와 상태를 다시 확인합니다. 선택할 공개 네트워크로 전환할 때는 별도 서명한 데이터를 사용하며 chain ID가 다른 Proof를 그대로 재사용하지 않습니다.
5. AI/STT/OCR 실패 시 분석은 실패·보류로 표시하고 Proof ID·QR와 직접 필드 입력을 통한 발행 검증은 독립적으로 제공합니다.

## 7. 블록체인, 기관 승인과 키 관리

검증하는 사실은 “이 기관이 이 보호 내용의 납부 요청을 발행했다”입니다. 기관 심사·키 보관·등록 경로의 신뢰는 별도로 필요하며 블록체인 자체가 업무상 사실의 정확성을 보증하지 않습니다. 기관은 자사 명의 사칭·납부 정보 변조를 수신자가 구별하도록 공식 확인 수단을 제공하기 위해 참여합니다.

발행 증거·상태 변경 이력을 중앙 DB 밖의 **공개 체인에도 보존하고 서버 밖에서 검증할 수 있게 하는 것**이 목표입니다. 권한 있는 수신자에게 서명된 원본·전자서명·검증 규칙과 네트워크/계약 식별 정보를 제공합니다. 해시만으로 원문을 복원할 수 없으며, 현재 상태 확인에는 해당 체인 조회가 필요합니다. 정확한 공개 네트워크·배포 범위·확정 기준은 미정입니다. 로컬 EVM은 개발·복구용이고 공개 체인 검증의 완료 증거가 아닙니다.

온체인에는 기관·키 식별자와 공개 검증키/signer, 요청 식별자, 보호 내용의 hash/digest를 포함한 불변 commitment, 발행 시각·기간, 필요한 수신자 검증용 연결값, 철회·기관 중지·키 폐기·사용 상태와 이력을 저장합니다. 금액·계좌·원문·인증코드·개인키·AI 판단은 직접 저장하지 않습니다. 납부 완료는 실제 결제 확인과 연결하기 전까지 기록하지 않으며 consume을 결제 완료로 표현하지 않습니다.

| 구성 | 범위 | 계획 기능 |
| --- | --- | --- |
| IssuerRegistry | P0, 기존 구현 확장 | 승인된 기관 등록, 상태 조회·중지 |
| IssuerKeyRegistry | P0, 기존 구현 확장 | 공개키 등록·조회·교체·폐기 |
| ProofStatusRegistry | P0, 기존 계획 확장 | 불변 발행 commitment, 철회·상태 조회, 권한 있는 consume·중복 사용 거부 |
| PolicyRegistry | P1 | 별도 정책 해시·도메인 관리가 필요한 경우 |
| EvidenceAnchor | P1 | 필수 Proof commitment와 별개의 추가 anchor 또는 batch 최적화 |

표의 기능명은 요구사항이며 현재 ABI를 뜻하지 않습니다. B가 기존 계약을 우선 재사용하고 W1에 확정 정책에 맞는 변경 ABI·쓰기 권한 명세를 작성해 C와 검토합니다. Registry 운영자 권한과 발행용 서명키는 분리합니다.

### 기관 온보딩

국세청 API를 호출하지 않고 사전 구성한 가상 기관 명부로 외부 조회를 모의합니다. 명부에는 기관명·테스트 사업자번호·대표자명·개업일자·기관 상태·공식 이메일 도메인·사전 지정 승인 계정을 둡니다. 신청자는 명부와 승인자를 임의로 바꿀 수 없습니다.

1. 사업자번호·기관명·대표자명·개업일자가 명부와 일치하고 정상 상태인지 확인합니다.
2. 등록된 도메인의 업무용 이메일을 데모 메일함 인증코드로 확인합니다. 실제 메일 발송은 하지 않으며 만료·재사용 금지·시도 제한은 실제로 검사합니다.
3. 담당자가 자기 기관의 납부 요청 발행 권한을 신청합니다.
4. 명부에 미리 지정된 내부 승인자가 별도 계정으로 승인합니다. 자기 신청·타 기관 승인·신청자가 만든 승인 계정은 거부합니다.
5. 운영자가 앞선 확인과 내부 승인 근거를 검토해 최종 승인·반려합니다.
6. 온체인 기관 활성화까지 확인한 뒤 담당자 권한·발행키를 연결합니다. DB 승인만으로 발행을 허용하지 않습니다.

이메일 인증만으로 자동 승인하지 않습니다. 발행 요청마다 소속·담당자 권한·기관/계정/키 상태·필수 항목·기간을 재검사하고, 내용 확정 → 서명 → 서명/해시/기관·키 연결 검증 → 체인 등록 → 확정 및 상태 재조회 순서로 처리합니다. 권한 회수·기관 중지·키 폐기 후의 신규 발행은 거부합니다.

### 키 등록과 서명

- 웹에서 등록하는 대상은 **공개 검증키/signer와 key ID·유효 기간**입니다. 공개 주소를 안다는 이유만으로 등록 권한을 부여하지 않습니다.
- 본선 기본안은 기관별로 분리된 서버 측 합성 서명기입니다. 담당자의 웹 요청으로 발급키를 생성하고 공개 signer를 Registry에 등록합니다. 등록 전 challenge 서명 검증으로 서명기와 공개키의 대응을 확인합니다.
- 개인키는 서버의 보호된 secret 또는 제한된 파일에서만 사용합니다. 브라우저 코드·입력 폼·API 응답·로그·Git·온체인에 개인키를 노출하지 않습니다. 공개키만 등록해 놓고 대응하는 서명기 없이 발행 성공을 표시해서는 안 됩니다.
- 이 구조는 합성 기관 시제품의 키 보관 방식입니다. 실제 기관 자체 지갑·KMS 연동은 확장 범위이며 도입 완료로 표현하지 않습니다.
- 키 교체는 새 키 등록·서명 검증·발행 전환 후 이전 키의 상태를 처리합니다. 정상 교체는 새 키 등록 확정 후 신규 발행 키만 전환하고 이전 키를 자동 폐기하지 않습니다. 과거 Proof는 발행 당시 키 기간·서명을 검사하므로 정상 교체/키 기간 종료만으로 무효화하지 않습니다. 유출 폐기는 해당 키의 과거 Proof도 현재 사용 불가로 처리합니다. ADR 0001의 3절을 따릅니다.
- 폐기한 키는 재활성화하지 않습니다. 만료·폐기 키로 신규 발행을 거부하며 기존 Proof는 현재 키 상태를 결과에 표시합니다.

### Proof 상태와 1회 사용

Proof 폐기는 발행자 권한으로 처리합니다. consume은 발행자 또는 지정된 수신자에게만 허용하고, 같은 Proof의 동시 요청은 원자적으로 하나만 성공하게 합니다. 누구나 호출 가능한 검증 조회가 Proof를 소비해서는 안 됩니다. 온체인 상태 변경 권한과 API의 기관·수신자 권한을 함께 검증합니다. P0는 테스트 계정을 인증하는 trusted gateway 서버가 주체를 대행 전달하고 체인은 허가된 caller·불변 Proof commitment·기관/binding·기간·상태를 검사합니다. 웹 로그인 자체를 체인이 검증하는 구조로 설명하지 않습니다. 정확한 등록·권한·원자성·W3→W4 연결은 ADR 0001의 6절을 따릅니다.

## 8. AI 분석과 텍스트·녹음·문서 입력

세 입력 경로를 이번 시연 범위에 포함합니다. 발행 기록이 없어도 피싱 정황 분석을 제공합니다. 입력은 공통 텍스트와 원문 위치로 변환하되 읽거나 듣지 못한 값을 추측해 채우지 않습니다.

| 입력 | 처리 | 근거 위치 |
| --- | --- | --- |
| 문자·메신저·대화 내역 | 붙여 넣은 텍스트 분석 | 원문 문장 |
| 녹음 파일 | 음성을 텍스트로 변환(STT)한 뒤 분석 | 음성 시간대 |
| 문서·캡처 이미지 | 텍스트 추출/OCR 후 분석 | 페이지·이미지 내 위치 |

탐지 항목은 기관·인물 사칭 정황, 긴급성·불안 조성, 송금·계좌 변경 유도, 비밀번호·인증번호 요구, 링크·앱 설치 유도, 확인 방해·비밀 유지 요구입니다. 단어 하나보다 요구 행동과 앞뒤 맥락을 분석하고, 비교할 기존 안내가 없으면 계좌가 변경됐다고 단정하지 않습니다.

| AI 결과 | 의미 |
| --- | --- |
| 위험 높음 | 송금·정보 탈취 등으로 이어지는 강한 의심 정황 |
| 주의 필요 | 추가 확인이 필요한 의심 요소 |
| 뚜렷한 의심 정황 없음 | 제공된 범위에서 주요 의심 패턴을 찾지 못함; 안전 보증 아님 |
| 판단 보류 | 내용 부족·인식 불완전·분석 실패로 판단 불가 |

임의의 피싱 확률 백분율을 표시하지 않습니다. 보고서는 한 줄 결과 → 의심 원문·위치 → 이유 → 의심 유형 → 확인할 행동 순서로 제공하고, 발행 기록 검증 결과를 별도 항목으로 함께 표시합니다. AI 판단은 기관 승인·온체인 등록이나 VERIFIED/TAMPERED의 근거가 아닙니다.

기존 `LLMProvider`·OpenAI/Mock 어댑터와 명시적 오류 처리를 재사용합니다. 기존 기본 provider `mock`과 `OPENAI_MODEL` 설정은 유지하되 새 분석·STT·OCR 모델은 실제 비교 후 결정하며, 평가 방법·초기 합격선은 ADR 0003의 8절을 따릅니다. 유료 live 평가는 별도 승인된 범위에서 실행하고 Mock replay를 실제 인식·분석 성능으로 보고하지 않습니다.

추출값과 사용자 확인값, 모델·프롬프트·평가 데이터 버전을 구분합니다. refusal·incomplete·timeout·rate limit·Schema 오류는 분석 보류/실패로 표시합니다. AI가 실패해도 ID·QR·직접 필드 비교는 동작해야 합니다. 지원 형식·상한·180초 작업 제한은 ADR 0003의 2절, 평가 기준은 8절을 적용하며 합성/사용 허용 자료만 사용합니다. 실제 지원·성능은 구현 후 검사합니다.

현재 MVP API는 `POST /v1/mvp/card-notices/verify`이며 [현재 API 문서](api/mvp_verification.md)를 따릅니다. 아래 표는 본선에서 제공할 **예정 기능 계약**입니다. 정책은 ADR 0001과 v4.0 ADR 0002를 따르며 URL·요청·응답은 C가 OpenAPI로 구현·공유하여 소비자가 검토합니다. 표 자체를 현재 사용 가능한 endpoint로 간주하지 않습니다.

| 작업·감사 이력 | 요청자, 기관, 대상 ID, 변경 전후, 결과 | 기관 담당자는 자기 기관, 운영자는 관리 범위 |

| Entity | 주요 정보 | 보존 기준 |
| --- | --- | --- |
| Account / Membership | 인증 주체, 역할, 기관 소속 | 계정 운영 기간, 비밀값 응답 금지 |
| IssuerApplication | 신청 기관·담당자·검토 사유·상태 | 합성 데모 기록 |
| Issuer / IssuerKey | 기관 ID, 공개 signer, key ID, 유효 기간, 상태 | 검증에 필요한 장기 기록 |
| Proof / ProofPayload | 유형, 발행자, 서명 원본, payload, 상태 참조 | 재검증용 별도 보관; Proof 만료 후 30일까지, ADR 0003 전환 절차 적용 |
| Operation / AuditEvent | 요청 ID, 주체, 대상, 트랜잭션, 처리 결과·시각 | 데모 30일 기준, 비밀정보 제외 |
| VerificationSession | 검사 범위, 상태·근거, 확인 시각 | 기본 24시간 |
| Artifact / Analysis / Report (계획 개념) | 제출 파일·추출 텍스트·AI 근거·검증 결과·저장 선택 | 처리 종료 후 삭제가 기본; 보고서는 선택 보관, 원본 저장은 별도 선택 |

공개 조회는 최소 발행 정보·상태·검사 근거만 제공하고 제한 payload·비교는 인증 후 제공합니다. 요청 ID는 `(account_id, action, request_id)` 범위에서 유일하며 내용 충돌은 거부합니다. Operation은 전송 전 저장하고 제출/확정/실패/결과 미확인을 구분하며 timeout 후에는 재조회·복구합니다. 로컬 성공 receipt 1 confirmation과 상태 재조회가 로컬 완료 조건입니다. 공개 네트워크의 확정 기준은 별도 결정하며 로컬 값을 그대로 적용하지 않습니다. 상세는 ADR 0001의 5·7절을 따릅니다.

### DB·파일 저장소와 체인의 연결·보관

| 위치 | 저장할 정보 | 사용 목적 |
| --- | --- | --- |
| 일반 DB | 가상 기관 명부·계정·소속·권한·신청·승인 이력 | 기관/담당자 확인과 접근 통제 |
| 보호된 DB·파일 저장소 | 기관 발행 원본·전자서명·비공개 수신자 연결 정보 | 받은 보호 항목과 대조, 권한 있는 대상의 별도 검증 |
| 체인 밖 임시 저장소·DB | 사용자 제출 자료·추출 텍스트·AI 결과·보고서 | 분석·결과 제공·선택 보관 |
| 일반 DB | Operation·감사·체인 등록/실패 이력·상태 사본 | 진행 상태 추적·복구; 현재 체인 상태를 대신하지 않음 |
| 블록체인 | 기관·키, 요청 ID와 보호 내용 hash/digest, 기간·불변 commitment·변경 이력 | 발행 근거와 현재 상태 검증 |
| 별도 보호된 키 저장소 | 기관 발행 개인키 | 서명; API 응답·브라우저·공개 로그에 노출 금지 |

기관 발행: 권한 확인·내용 확정·서명/등록 전 검사 → DB 원본·서명 저장 → 같은 요청 식별자로 체인 등록 → 확정·재조회. 결과 미확인 거래는 먼저 조회하고 무조건 새 거래를 만들지 않습니다. 최종 v4.0에서 DB 저장만 된 자료는 등록 대기이며, W3 중간 동작의 제한은 단계별로 표시합니다.

사용자 확인: 자료 제출 → 텍스트 추출·AI 분석 → ID/QR/링크 식별 → 권한 확인 → DB 원본·서명·체인 대조 → 통합 보고서. 기록이 없으면 발행 확인 불가이며, 금액·ID가 불완전하면 사용자 확인 또는 보류합니다. 사용자 입력·AI 판단을 발행 사실로 자동 등록하지 않습니다.

DB 원본의 보호 항목으로 hash/digest를 다시 계산해 체인 값과 비교합니다. 원본 변조는 탐지할 수 있지만 삭제된 원본을 해시로 복원할 수는 없습니다. 현재 유효성은 체인 조회를 기준으로 하며 RPC 실패 시 오래된 DB 상태로 성공을 만들지 않습니다.

사용자 제출 파일·분석 입력은 처리 종료 후 삭제하는 것이 기본입니다. 보고서는 저장을 선택한 경우 필요한 근거와 함께 보관하고, 원본 파일 보관은 별도로 선택하게 합니다. 기관의 발행 원본·서명은 재검증 목적으로 따로 보관합니다. ADR 0003의 3절에 종료 직후 원본/분석 입력 삭제, 미선택 결과 전달본 최대 10분, 선택 보고서·원본 7일, 기관 원본의 Proof 만료 후 30일, 실패 잔여물 정리와 권한을 정의합니다. 전달본의 필요한 인용도 임시 보관임을 안내합니다. v3.0의 Artifact 최대 24시간 기준을 새 입력 전체에 적용하지 않습니다. Operation은 기록 후 30일(미해결은 해결 후 30일), VerificationSession은 생성 후 24시간을 적용하며 기존 데이터에는 전환 점검 없이 삭제를 실행하지 않습니다.

공유 Python 모델 `packages/python/originproof_core`가 계약 원본입니다. JSON Schema와 TypeScript 타입은 생성하고, OpenAPI와의 일관성을 검증합니다. 스키마·enum·서명 또는 ABI 변경은 ADR, 호환성·마이그레이션 계획, 소유자 리뷰를 포함합니다.

## 11. 기술 스택

이미 MVP에서 선택한 기술을 유지합니다. 아래 확장 기능은 구현 목표이며 새 의존성 설치를 의미하지 않습니다.

| 영역 | 기준 | 본선 작업 |
| --- | --- | --- |
| Frontend | Next.js·TypeScript, 기존 웹 앱 | 사용자·기관·운영자 화면 및 접근성 |
| Backend | Python·uv·FastAPI·Pydantic | 인증·기관 권한·발행·관리·검증 API |
| Blockchain | Solidity·Foundry·OpenZeppelin | Registry·불변 발행 증거·상태, 로컬 개발·복구와 공개 체인/별도 검증 목표 |
| Database | PostgreSQL·SQLAlchemy 2·Alembic | 계정·신청·발행·작업·감사 기록 |
| Queue / Indexer | Redis·Celery 및 기존 projection 모듈 | 필요한 비동기 처리와 상태 동기화 |
| AI·입력 처리 | 기존 LLMProvider·OpenAI/Mock 어댑터 우선 | 피싱 정황·근거 분석, STT/OCR·필드 추출·실패 처리·평가; 세부 모델 미정 |
| Infra | Docker Compose·Makefile·GitHub Actions | 재현 기동, CI, 웹 접근 가능한 시연 환경 |

서명·정규화는 [기존 명세](signing_spec.md)를 재사용합니다. 인증 대상은 사전 준비한 테스트 계정, 웹 접속은 로컬 시연으로 확정합니다. 세션은 서버 저장·8시간 고정 만료·로그아웃 폐기·HttpOnly/SameSite=Lax cookie·CSRF 방식으로 확정하고 C가 W1-C1/C2에서 구현·검사합니다. HTTPS에서는 Secure를 적용합니다. 회원가입·외부 로그인·인터넷 호스팅은 기본 범위에 포함하지 않습니다. v4.0은 공개 체인과 서버 밖 검증을 목표로 하며 구체적인 네트워크·배포 범위는 후속 결정입니다. 로컬 웹 실행과 공개 체인 사용은 별개이고 인터넷 웹 호스팅은 계속 선택 범위입니다. Solidity/Foundry 등 기존 스택은 유지합니다. 외부 서비스나 프레임워크를 추가하기 전에 기존 구현으로 요구사항을 충족할 수 있는지 확인합니다.

## 12. 4인 역할과 협업

아래 A~D는 본선의 확정된 **업무 배정**입니다. M1~M4는 MVP 당시 역할 표기이며 본선 역할과의 담당자 연결은 아래와 같습니다. M3와 M4는 같은 담당자가 맡지만 Contract Core와 배포·ABI·Chain Adapter의 책임 및 파일 소유 경계는 분리합니다. MVP의 `mvp/integration` 병합 담당과 본선 역할은 별개이며, 형준님은 본선에서 A Product·Frontend를 담당합니다. 프론트엔드 작업을 마지막 단계에 몰아서 진행하지 않습니다.

| 역할 | 담당자 (MVP 역할) | 책임 | 주요 산출물 |
| --- | --- | --- | --- |
| A. Product·Frontend | 김형준님 (MVP 통합·병합 담당) | 세 역할의 화면, UX, 접근성, 발표 | 웹 UI, 화면 E2E, 리허설·영상 |
| B. Blockchain·Security | 여하민님 (M3·M4) | Registry·Proof 상태, 배포, 권한·키 정책 | 계약·ABI·배포 정보, 보안 검증 |

### 본선 브랜치와 요청 기반 main 반영

기본 흐름은 **이슈별 작업 브랜치 → 현재 단계 집계 브랜치 → 단계 완료 PR → `integration` → 사용자님 요청 → 통합 검증 → `main` PR**입니다. `phase/W1`~`phase/W7`은 각 개발 단계에서 팀원 결과를 모으는 브랜치이며 `integration`은 완료된 단계를 함께 검증하는 누적 브랜치, `main`은 검증된 시연 기준입니다. W 번호는 달력 일정이 아닙니다.

1. PR #19는 병합되었고 본선용 `integration`이 생성되어 있습니다. 현재 기준 SHA를 확인해 재사용합니다. 기존 `mvp/*`는 MVP 이력이며 본선 통합 브랜치와 구분합니다.
2. 단계 결과의 확정·승격은 W1부터 순서대로 진행합니다. 독립 작업의 선행 개발은 15.1절을 따릅니다. 단계 작업을 시작할 때 한 명의 단계 통합 담당자가 최신 `integration` SHA에서 해당 단계 집계 브랜치(`phase/W1`~`phase/W7`)를 만들고 원격에 올려 시작 기준 SHA를 기록합니다. 다음 단계 브랜치는 직전 단계가 `integration`에 반영된 뒤의 최신 SHA에서 만듭니다. 같은 단계 이슈는 해당 `phase/Wx`의 최신 SHA에서 `feat/<issue>-<summary>`, `fix/<issue>-<summary>`, `docs/<issue>-<summary>` 작업 브랜치를 만듭니다. 개인별 영구 브랜치는 두지 않습니다.
3. 담당자는 자기 작업 브랜치만 원격에 push하고 PR 대상은 해당 `phase/Wx`로 지정합니다. 공유 집계 브랜치에 직접 push하지 않습니다. 관련 경로 리뷰와 CI를 통과한 PR은 단계 담당자가 `phase/Wx`에 병합합니다. 병합된 선행 PR은 단계가 전부 끝날 때까지 기다리지 않고 같은 단계 안의 의존 작업에서 사용할 수 있습니다.
4. 의존 작업자는 착수 시, 선행 PR 병합 알림 후, 자기 PR 제출 전에 `git fetch origin`으로 `origin/phase/Wx` 최신 SHA를 확인합니다. 승인된 코드가 집계 브랜치에 들어온 뒤에만 실제 구현을 연결하고 영향을 받는 검사를 다시 실행합니다. 브랜치 병합이나 새 커밋을 백그라운드에서 자동 감시하지 않습니다.
5. 단계 통합 담당자는 해당 단계 작업이 모두 수용 기준을 만족하고, 관련 작업 PR이 `phase/Wx`에 병합되고, D의 독립 확인과 단계 검사가 통과했을 때 최종 SHA를 기록합니다. 계획 ID에 속한 작업이 차단/미완료이거나 PR이 미병합이면 단계를 완료 처리하지 않습니다. 완료가 확인되면 시작 기준 SHA·최종 SHA·포함 작업 ID·검사 결과를 담아 `phase/Wx` → `integration` PR을 만들고 필수 리뷰·CI를 마친 뒤 병합합니다. 병합된 `phase/Wx`는 그 단계의 포트폴리오 결과 브랜치로 보존하며 이후 커밋을 추가하거나 다른 단계에 재사용하지 않습니다. 다음 단계는 갱신된 `integration`에서 별도 브랜치로 시작하므로 이전 단계를 포함한 누적 상태가 됩니다. 단계에서 새로 추가된 변경은 시작 기준 SHA와 해당 단계 PR로 구분합니다. 별도 프로세스가 자동 감지해 push하는 기능은 현재 저장소에 구성되어 있지 않습니다.
6. `main` 반영을 위한 통합 검증(기존 주간 검증)은 사용자님 `@Jordi2801K`가 명시적으로 요청한 때만 진행합니다. 매주 또는 7일마다 자동으로 실행하지 않습니다. C(사용자님)가 단일 진행 담당자가 되어 검증 대상 `integration` SHA를 정하고, D와 영역별 담당자는 요청에 따라 검증·리뷰를 지원합니다. A의 본선 주 역할은 Product·Frontend입니다.
7. 통합 검증을 통과한 뒤에만 C 또는 사용자님이 해당 작업을 맡긴 에이전트가 `integration` → `main` PR을 올립니다. 같은 반영 작업은 한 명 또는 한 에이전트가 순차적으로 진행하고, 열린 동일 대상 PR이 있으면 새 PR을 중복 생성하지 않고 갱신합니다. 팀원이나 다른 에이전트가 독자적으로 검증·main PR 작업을 시작하지 않습니다. 작업 PR의 검사와 일반 CI는 기존대로 수행합니다.
8. main 반영 PR에는 요청 기록, 포함 이슈, 변경 화면·API, 검증한 SHA와 실제 결과, 미완료 항목을 기록합니다. 검증 실패 시 PR 생성과 main 반영을 보류하고 결과를 보고합니다. PR 생성 후 리뷰·필수 CI를 통과하면 C가 병합합니다. 검증 후 추가 커밋이 들어오면 최신 SHA를 다시 검증합니다.
9. 장기 브랜치 간 이력이 이어지도록 main 반영 PR은 merge commit으로 병합합니다. `main`의 병합 결과와 예외 수정은 `integration`에 반영하고 다음 작업을 시작합니다.
10. 병합된 이슈 작업 브랜치는 후속 작업·열린 PR에서 사용하지 않는지 확인한 뒤 삭제합니다. `phase/W1`~`phase/W7`은 각 단계의 최종 SHA를 가리키는 포트폴리오 기록으로 계속 보존하고 수정·재사용·삭제하지 않습니다. 이후 발견한 수정은 현재 진행 중인 단계의 작업 브랜치에 반영하고 이슈에서 원래 단계와 연결합니다. `main`과 `integration`도 개발 중 기준 브랜치로 유지하며 강제 푸시하거나 삭제하지 않습니다.

### `main` 운영 규칙과 직접 푸시 예외

- 일반 변경은 PR, 작성자 외 리뷰어 1명 이상 승인, 해당 경로 CODEOWNER 승인과 필수 CI 통과를 거칩니다. 현재 비공개 저장소 요금제에서는 이 규칙을 GitHub가 강제하지 못하며 직접 푸시·강제 푸시·브랜치 삭제도 기술적으로 차단되지 않습니다.
- 사용자님 `@Jordi2801K`이 `main` 직접 푸시를 명시적으로 요청한 경우에만 직접 푸시합니다. 이는 팀이 준수할 운영 규칙이며 GitHub 권한으로 기술 제한되지 않습니다.
- 직접 푸시 요청을 수행할 때에도 변경 내용·필요한 검사 결과·요청 사유·반영 SHA를 이슈에 남기고, 반영 직후 `main` 변경을 `integration`에 동기화합니다. 직접 푸시 요청은 강제 푸시나 브랜치 삭제 허가를 뜻하지 않습니다.
- 명시 요청 여부와 PR·리뷰 절차는 팀과 에이전트가 지키며, GitHub가 이를 강제하지 않습니다.

위 내용은 채택한 운영 정책입니다. 현재 저장소는 비공개이며 사용 중인 요금제에서 브랜치 보호와 Rulesets API가 요금제 제한(HTTP 403)으로 제공되지 않는 것을 확인했습니다. 따라서 `main`은 보호된 상태가 아니며 적용 여부를 다시 확인할 때까지 PR·리뷰·직접 푸시 제한은 팀 규칙으로 관리합니다. 요금제가 바뀌면 C가 적용 가능한 보호 설정을 확인합니다. 아래 CI 표는 목표이며 미구현 검사는 구현 후 필수 검사로 등록합니다.

Definition of Done은 수용 기준 충족, 변경에 필요한 테스트와 품질 검사 통과, 보안 영향 확인, 문서 갱신, 리뷰 승인을 포함합니다. P0 웹 기능은 해당 역할의 브라우저 조작부터 실제 상태 변경·재조회까지 성공해야 합니다.

### 15.1. 에이전트와 함께 개발하는 작업 단위

아래 작업은 **개발 예정 항목**입니다. 작업 ID는 계획 안의 참조이며 GitHub Issue 번호가 아닙니다. 문서를 개정했다고 이슈가 생성되거나 해당 기능이 구현된 것은 아닙니다. W1~W7 모두 바로 이슈로 옮길 수 있도록 팀원별 세부 작업으로 나눕니다. 모든 작업에 담당자·선행 조건·산출물·완료 기준·작업 PR 대상 집계 브랜치를 둡니다. 작업표의 선행 조건은 계약 승인 후 착수할 수 있는 부분과 실제 구현 연결 후 완료할 부분을 구분해 읽습니다.

- A = 김형준님(`@kimhyounjun`), B = 여하민님(`@hamin1228`), C = 사용자님(`@Jordi2801K`), D = 여인준님(`@yijun0330`)입니다.
- 단계 목표는 네 명의 합산 결과입니다. 에이전트에게 담당자의 준비된 작업 ID를 지정합니다. 여러 작업 ID를 한 번에 맡길 때는 아래 작업 묶음과 순서를 명시하되 각 ID의 선행 조건·수용 기준은 따로 지킵니다. 한 작업도 PR이 커지면 계약·구현·연결 순으로 나누되 최종 완료는 실제 연결 결과로 판단합니다.
- 각 담당자는 이슈에 기준 `integration` SHA와 현재 `phase/Wx` SHA를 기록하고 그 단계 집계 브랜치에서 이슈별 브랜치를 만듭니다. 자기 작업 브랜치에만 push하고 완료 PR의 대상은 `phase/Wx`입니다. 착수 시 이미 구현된 항목은 코드·검사 증거를 확인해 재사용하며 같은 기능을 다시 만들지 않습니다.
- 다른 담당자가 기다리는 선행 계약·구현은 독립 범위의 검사를 마치면 자기 작업 브랜치에 push하고 브랜치 URL·SHA·사용 가능한 범위·미승인 결정·검사 결과를 의존 작업 ID에 인계합니다. `phase/Wx`가 아직 없으면 준비용 브랜치를 먼저 공유하고, 단계 브랜치 생성 뒤 그 단계로 PR을 올립니다. 원격 공유만으로 작업을 완료 처리하거나 미승인 계약을 확정하지 않습니다.
- 확정된 v4.0 범위와 유지되는 기존 계약으로 자기 영역 구현·mock/합성 데이터 검사까지 진행합니다. 새 공유 인터페이스는 소유자가 초안·예시·테스트를 작성하고 관련 담당자 리뷰 후 소비자가 공통 기준으로 사용합니다. 일반 구현 선택은 자율 진행하며 이미 승인된 정책을 재승인받지 않습니다. 실제 API·체인 연결에 의존하는 완료 판정만 연결 후에 합니다. 각 에이전트가 같은 경계를 별도로 정의하지 않습니다.
- 담당자가 자기 코드의 테스트를 함께 작성하고 D는 독립적인 실패 사례·E2E·재현을 맡습니다. D에게 모든 테스트 구현을 넘기지 않습니다.
- 단계 담당자는 모든 작업 ID가 완료 조건을 만족하고 해당 PR·독립 확인·단계 검사가 통과한 시점에 `phase/Wx` SHA를 고정하고 `phase/Wx` → `integration` PR로 완성 결과를 승격합니다. 이 단계 완료 PR이 이슈 완료 시 자동으로 실행되도록 해주는 GitHub Action은 현재 없으므로, 단계 완료 작업/에이전트가 실행되어야 합니다. `integration` → `main` 검증·PR은 14장의 사용자님 명시 요청 규칙을 따르며 자동 실행하지 않습니다.
- 번호는 일정이 아니라 의존 관계를 정리하는 용도입니다. 담당자는 선행 조건이 충족된 작업을 골라 진행하고, 막히면 원인·필요한 결정·영향받는 작업 ID를 기록한 뒤 독립 작업을 진행합니다. 속도가 빨라도 완료 검사를 생략하지 않습니다.
- 각 단계는 `phase/W1`~`phase/W7` 집계 브랜치를 사용합니다. 모든 작업 브랜치는 현재 단계 집계 브랜치에서 시작하고, 리뷰된 PR로 결과를 모읍니다. 다른 단계 branch를 임의로 기준에 섞지 않습니다. 해당 단계 통합 담당자는 최신 `integration` SHA에서 집계 브랜치를 처음 생성하고 SHA를 기록합니다.
- Codex·Claude 에이전트는 팀 브랜치를 백그라운드에서 자동 감시하거나 새 커밋을 자동으로 현재 작업에 합치지 않습니다. 작업 환경에 시작 시점의 체크아웃과 로컬 Git 참조가 보이며, 원격의 새 커밋은 `git fetch` 후에야 확인할 수 있습니다.
- 의존 PR/작업 ID와 통과 조건을 이슈에 연결합니다. 선행 코드가 현재 `phase/Wx`에 아직 들어오지 않았으면 의존 연결 부분을 `Blocked`로 표시하고, 확정 정책·공유 계약·mock으로 가능한 자기 영역 구현과 검사를 진행합니다. 다른 PR의 구현을 로컬에서 합친 결과는 통합 완료로 기록하지 않습니다.
- 각 에이전트는 착수 때, 선행 작업 병합 알림 뒤, 자기 PR을 올리기 전에 `git fetch origin`으로 확인한 `origin/phase/Wx` SHA를 기록합니다. 집계 브랜치가 전진했으면 자기 이슈 브랜치에 최신 단계 변경을 반영하고 충돌·관련 검사를 해결한 뒤 PR을 올립니다. 이미 완료된 검사도 영향을 받으면 다시 실행합니다.
- 네트워크나 인증이 없어 fetch할 수 없으면 독립 작업은 마지막 확인 SHA에서 계속할 수 있습니다. 최신 공유 계약에 의존하는 작업의 연결·완료는 보류하고, 차이·필요 권한·후속 작업 ID를 기록합니다. 다른 팀원의 branch를 임의로 checkout·merge·cherry-pick하거나 공유 브랜치를 재작성하지 않습니다.
- 단계 통합 담당자가 의존 PR 병합이나 새 단계 SHA를 이슈/PR로 알려줍니다. 에이전트가 실행 중이라는 이유만으로 새 커밋 알림을 받아 계속 polling하지 않습니다. 업데이트를 받으면 `fetch → phase SHA와 선행 PR 확인 → 작업 branch 갱신 → 영향받은 검사 → 작업 재개` 순서로 이어갑니다.

계획·운영 지침 자체를 준비하는 문서 PR은 `integration`을 대상으로 할 수 있습니다. 이는 미완료 기능을 단계 검증 없이 통합하는 예외가 아닙니다.

#### 여러 단계에 걸친 팀원 작업 묶음

아래 묶음은 같은 팀원이 여러 작업 ID를 이어서 맡길 때의 기본 순서 예시입니다. 실제 착수 순서는 각 작업의 선행 조건과 준비 상태로 정하고, 묶음 이름은 편의를 위한 부모 항목입니다. 작업 ID별 완료 기준·리뷰·검사는 그대로 적용합니다.

| --- | --- | --- |
| A · 형준님 | 화면 기본 흐름 → 상태·UX 마감 → 통합·발표 | `W1-A1~A3 → W2-A1~A2 → W3-A1~A3`; `W4-A1~A3 → W5-A1~A3`; `W6-A1~A3 → W7-A1~A3` |

다음 단계 집계 브랜치가 아직 없어도 승인된 계약만으로 가능한 독립 작업은 먼저 개발할 수 있습니다. 이때 최신 `integration`에서 준비용 작업 브랜치를 만들고 예정 단계와 선행 조건을 기록합니다. 해당 `phase/Wn`이 생성되면 그 최신 변경을 작업 브랜치에 반영하고 충돌·관련 검사를 해결한 뒤 그 단계로 PR을 올립니다. 준비용 브랜치를 이전 단계에 병합하거나 실제 선행 구현 연결 없이 완료로 표시하지 않습니다. 기본은 단계별 브랜치에서 시작하며 이 절차는 선행 개발에만 적용합니다.

묶음 이슈나 에이전트 지시에는 담당자, 포함 작업 ID와 순서, 각 작업의 선행 조건, 단계별 PR 링크를 기록합니다. 다음 작업이 선행 결과를 요구하면 해당 작업 ID를 `Blocked`로 두고, 이미 준비된 독립 작업만 진행합니다. v4.0 입력/AI·기관 인증·보관·공개 체인/별도 검증 변경분은 15.10절 V4-01~08을 같은 담당자의 작업 묶음에 추가합니다. 공개 네트워크 결정 전에도 로컬 구현·검증 자료 준비는 진행하고, 공개 체인 목표의 실제 완료는 F22로 따로 확인합니다.

묶음이 여러 단계에 걸쳐도 한 작업 브랜치나 PR을 여러 `phase/Wx`에 걸치지 않습니다. 현재 단계의 묶음 작업만 해당 `phase/Wx`에서 브랜치로 만들고 그 단계 집계 브랜치로 PR을 보냅니다. 단계 완료 조건을 충족해 `phase/Wx`가 `integration`에 반영되면 그 브랜치와 SHA를 해당 단계의 포트폴리오 결과로 고정합니다. 이후 다음 단계가 시작되면 다음 단계 집계 브랜치(예: W1 다음은 `phase/W2`)에서 새 작업 브랜치를 만들어 이어갑니다. 따라서 앞 단계 PR은 묶음 전체 완료까지 미루지 않으며, 단계 경계를 넘을 때마다 리뷰·검사 가능한 변경으로 나누어 공유합니다. 각 단계 PR 병합 뒤 의존 담당자는 해당 단계 집계 브랜치를 fetch하고 최신 SHA에서 연결·검사를 이어갑니다. 묶음은 모든 포함 작업 ID가 각자 완료되고 해당 단계 PR·통합 검사가 끝났을 때만 완료입니다. 포트폴리오 인계에는 단계 PR, 최종 SHA, 포함 작업 ID, 통과 검사 결과를 함께 기록합니다.

#### 개인 기여와 포트폴리오 기록

작업 상세 근거는 공통 [PR 템플릿](../.github/pull_request_template.md)에, 개인별 단계 요약은 [포트폴리오 기록 안내](portfolio/README.md)의 양식에 남깁니다. 설계·구현·리뷰·테스트·장애 분석·통합·문서 기여를 실제 담당자별로 구분하며 PR 작성자나 병합자를 전체 구현자로 간주하지 않습니다.

1. 에이전트는 착수 시 역할·단계·작업 ID·문제·범위·선행 작업·시작 SHA를 기록합니다. 개발 중 중요한 선택·대안·실패 원인·해결·협업 인계를 이슈/PR에 갱신합니다.
2. PR 제출 전 변경 전후 동작, 본인과 다른 팀원의 기여, AI 활용과 본인의 판단·수정·검증, 명령·환경·코드 SHA·실제 결과·증거 링크·한계를 작성합니다. 템플릿 자동 삽입 여부와 관계없이 에이전트는 저장소의 템플릿을 읽고 본문을 채웁니다. CLI로 제출할 때도 같은 내용을 본문 파일로 전달합니다.
3. 각 담당자는 단계 마무리 때 `docs/portfolio/Wn-A.md`~`Wn-D.md` 중 자기 역할 파일을 작성합니다. 기존 PR·ADR·증거를 연결하고 중복 로그는 복사하지 않습니다. 묶음 개발도 단계마다 나누며, 미래 기록은 만들지 않고 부분 완료·미실행을 구분합니다.
4. 단계 통합 담당자는 완료 PR에서 A~D 개인 기록 4개와 최종 SHA·검사 결과를 연결합니다. 각 담당자와 작성자 외 리뷰어의 사실 확인, 필수 근거, 기록 문서 반영이 끝나야 단계 완료로 처리합니다. 동결 후 기록 보충은 integration 대상 문서 PR로 하고 보존된 단계 브랜치는 변경하지 않습니다.
5. 수치·개인 기여 비율·리뷰 승인은 실제 근거 없이 추정하지 않습니다. 공개 가능 여부와 비밀정보 제거, 증거의 접근·보관 방법도 안내를 따릅니다. 에이전트는 종료 보고에 기록 링크와 누락 근거를 포함하며 별도 수집 자동화가 실행된 것으로 표현하지 않습니다.

#### 이슈와 에이전트에 전달할 공통 형식

작업 착수 시 해당 담당자가 다음 형식으로 이슈를 만들고 다른 담당자의 의존 작업과 연결합니다. 아직 이슈가 없다면 같은 내용을 작업 지시로 작성한 후 구현 전에 기록합니다. 완료 조건 없이 “W1 개발 전체 진행”이라고 지시하지 않습니다.

담당자 / 리뷰어: C / A(연결), D(거부 사례); 필수 경로 소유자 리뷰 별도
기준: 현재 phase branch의 실제 SHA, 개발 계획서 버전, 관련 ADR·승인된 계약

#### 다른 팀 작업이 끝나야 진행되는 경우

| 상태 | 에이전트가 할 일 | 완료로 볼 조건 |
| --- | --- | --- |
| 선행 PR 준비 전 | 선행 작업 ID·담당자·필요 계약을 기록하고 연결 부분만 `Blocked`로 표시합니다. 확정 정책·기존 계약으로 자기 영역 구현·mock/합성 테스트를 진행하며 필요한 공유 계약은 소유자가 초안으로 작성·인계합니다. | 독립 구현·검사와 실제 연결 대기를 구분하고 미병합 코드를 통합된 것으로 가정하지 않습니다. |
| 선행 PR이 열렸지만 미병합 | 지정된 리뷰/병합 담당에게 PR 링크와 필요한 시점을 공유합니다. 해당 PR을 꼭 써야 하는 경우에만 작성자 확인과 이슈에 적힌 branch/commit을 사용한 임시 검증을 합니다. | 임시 검증 결과는 PR의 SHA·환경을 표시하고 `integration` 통합 결과와 분리합니다. |
| 선행 PR이 현재 `phase/Wx`에 병합됨 | 작업 환경에서 `git fetch origin`을 실행하고 병합된 PR·새 `origin/phase/Wx` SHA를 확인합니다. 자기 작업 branch에 최신 단계 집계 변경을 반영하고 충돌·호환성을 해결합니다. | 선행 계약·생성 타입·실제 API/Adapter에 연결하고 변경 영향이 있는 검사를 새 SHA에서 다시 통과합니다. |
| fetch 불가 또는 권한/네트워크 실패 | 마지막으로 확인한 기준 SHA를 보고하고 독립 작업만 진행합니다. 공유 계약이 필요한 연결·완료는 보류합니다. | 병합 유무를 추측하지 않고 접근 차단을 기록합니다. 네트워크가 복구되면 먼저 다시 fetch합니다. |
| 선행 PR 자체가 취소·범위 변경 | blocker 이슈에 새 API/Schema·담당/순서를 갱신하고 사용자/소유자의 승인된 계약을 기다립니다. | 예전 인터페이스에 계속 구현하지 않습니다. |

선행 작업 상태는 `origin/integration`이 아니라 현재 `origin/phase/Wx`에서 확인합니다. 단계 브랜치는 해당 단계 통합 담당자가 만들고, 단계 PR의 병합 결과만 `integration`에 포함됩니다.

체크 시점은 **작업 착수, 선행 PR 병합 통지 후, 자신의 PR 제출 전**입니다. 에이전트가 계속 작업하는 동안 팀 branch를 자동으로 주시하거나 실시간 동기화하지 않습니다. 팀은 PR·이슈 상태, 담당자의 명시적인 작업 지시로 변경을 전달합니다. sync 중 충돌을 해결할 수 없거나 다른 담당자의 코드 소유권이 걸리면 임의 병합하지 말고 재현 SHA·충돌 경로·필요 결정을 handoff 합니다. 병합은 14장의 PR·리뷰 운영 규칙을 따릅니다.

**단계 완료:** 브라우저에서 기관 승인·키 등록·폐기와 감사 이력을 확인하며, 승인 전·타 기관 변경·중복·체인 실패가 안전하게 처리됩니다. 로컬 EVM 배포 정보를 남깁니다. W2의 로컬 체인 연결 완료와 v4.0 공개 체인 목표 완료는 별도로 판단합니다. 키 교체 전체 정책과 Proof 발행/폐기/consume의 동작 완료는 W3·W4에 확인합니다.

`make mvp-test`만으로 코어·indexer·웹 전체 검증을 대신하지 않습니다. `make typecheck`의 Python 부분은 현재 `compileall` 검사이며 정적 타입 검증 완료로 표현하지 않습니다. `make security`는 현재 안내만 출력하므로 보안 검사 통과 증거가 아닙니다. 보안 검사 도구/명령의 실제 도입은 C/B가 W1에 현황을 기록하고 W6 이전에 담당 이슈로 연결합니다.

`make demo-reset`은 현재 DB 볼륨을 삭제하는 reset을 포함합니다. 개인의 폐기 가능한 합성 데모 환경에서만 사용하고 공유·보존 데이터에 실행하지 않습니다. deploy·migration·live 체인 검사는 대상 환경과 부작용을 확인한 뒤 수행합니다.

작업 완료 보고에는 계획 ID와 실제 이슈/PR 링크, 검사한 SHA, 명령/결과, 동작 증거, 다음 담당자가 사용할 계약/생성 파일 버전, 미완료·이월 항목을 남깁니다. 계획표의 완료 기준을 충족하지 못한 작업을 날짜나 PR 병합 여부만으로 Done 처리하지 않습니다.

| F23 | 등록·변경·결제 표현 | DB 저장 후 체인 미확정은 대기, 불변 commitment 덮어쓰기 거부, 변경 시 철회·재발행, consume을 납부 완료로 표시하지 않음 |

상태 조합은 ADR 0001로 확정했습니다. 기존 카드 v1은 `INCONCLUSIVE + EXPIRED`를 보존하고 본선 v2는 실제 검사 성공과 lifecycle을 분리합니다. 서명/내용 검사 실패·누락·RPC 불가에서는 VERIFIED를 만들지 않으며 동시에 존재하는 lifecycle의 대표 우선순위와 모든 원인도 검사합니다. enum·문서가 있다는 이유로 구현 완료로 간주하지 않습니다.

단위 검증은 정규화·서명·경계값, 계약 검증은 권한·기간·상태·동시성, 통합 검증은 API·DB·chain·indexer, 브라우저 E2E는 세 역할의 전체 흐름을 다룹니다. 기본 테스트는 Mock/합성 데이터로 재현하고 유료 API 평가는 별도 opt-in으로 기록합니다.

2. 합성 기관 2곳, 가상 명부 대조 → 데모 업무용 이메일 확인 → 사전 지정 내부 승인 → 운영자 승인 → 온체인 활성화.
3. 공개키 생성·등록·교체·폐기, 기관별 보호된 서명기와 매 발행 권한 재확인.
4. 납부 요청 중심의 보호 항목 서명·해시·발행/철회/재발행, 공식 문서형도 유지. 기존 카드 v1·본선 2.0.0은 원래 계약으로 회귀합니다.
5. ID·QR/링크 조회, 받은 보호 필드 비교, 발행 출처·내용·현재 상태와 검사 범위 표시.
6. 텍스트·녹음·문서/이미지 입력, 위치를 보존한 텍스트 변환, 피싱 정황·맥락 분석과 네 단계 결과·근거·확인 행동.
7. AI 분석과 발행 검증의 통합 보고서. 기록 없음·AI 실패·인식 부족·체인 장애를 안전/위조 확정으로 바꾸지 않습니다.
8. DB·체인 저장 분담, 불변 발행 commitment·상태 이력, 등록 대기/실패/복구, 원문·개인정보의 체인 밖 보관.
9. 제출 자료 기본 삭제, 보고서 선택 보관·원본 별도 선택, 기관 발행 원본·서명의 재검증용 보관.
10. 기존 키/Proof 폐기·만료·기관 중지, 지정 수신자·권한 있는 consume·동시 재사용 방지. 실제 납부 완료와 구분합니다.
11. 공개 체인 발행 근거와 권한 있는 대상의 서버 밖 검증이 최종 목표입니다. 네트워크·배포 범위·확정 기준은 21.1절 후속 결정이며, 로컬 개발·복구 완료만으로 이 목표를 완료 처리하지 않습니다.
12. 보안·접근성·장애/재시작, 다른 환경 재현, 같은 RC 리허설 3회, 실행·복구 문서·테스트 보고·발표 자료·영상.

W1~W7은 단계 구분이며 기존 완료 phase를 다시 쓰지 않습니다. 15.10절의 추가 작업과 미확정 값이 해당 검증에 연결되어야 v4.0 완료를 판정합니다. 계획 반영은 새 기능 구현 완료나 기한 확정이 아닙니다.

### P1 선택

마스킹 보고서 파일 다운로드·검색·통계, 별도 PolicyRegistry·추가/batch anchor, 실제 기관 KMS·외부 지갑, 공개 회원가입·외부 로그인·인터넷 웹 호스팅입니다. 필수 별도 검증 자료 제공은 선택적 보고서 다운로드와 구분합니다.

### P2 확장

추가 Proof 유형, 이미지 조작 포렌식, AI Agent 요청, L2·Consortium 비교입니다. 기본 피싱 맥락 분석과 문서 글자 추출은 이미 v4.0 범위이므로 이 확장 목록에 포함하지 않습니다.

추가 선택 기능은 필수 작업 뒤 검토합니다. 합의한 세 입력·AI·기관 인증·발행 검증 범위를 줄여야 한다면 변경 사유와 시연 영향을 함께 검토하며, 미구현 항목을 조용히 선택 항목으로 바꾸지 않습니다.

## 18. 최종 시연과 제출 계획

아래 흐름을 합성 데이터로 브라우저에서 실제 실행합니다. 행사 발표 시간은 확정되지 않았으므로 W7에 주어진 시간에 맞춰 진행 속도와 설명을 조정합니다.

1. 신규 합성 기관의 명부 일치·데모 이메일 확인·발행 권한 신청을 진행합니다.
2. 지정 내부 승인자와 운영자 세션에서 각각 검토·승인하고 Registry 활성화를 확인합니다.
3. 기관 담당자가 공개키를 생성·등록하고 활성 상태를 확인합니다.
4. 첫 기관이 새 요청형 Proof를 발행하고 QR/검증 링크를 전달합니다.
5. 사용자 세션에서 텍스트·녹음·문서/이미지 세 경로를 시연합니다. AI 의심 근거와 발행 검증을 함께 보고 금액·계좌를 바꾼 자료의 보호 항목 불일치를 확인합니다. 기록 없는 자료와 인식 실패·분석 보류도 보여줍니다.
6. 다른 분야의 기관이 문서형 Proof를 발행하고 같은 코어로 검증합니다.
7. 발행자가 Proof 또는 키를 폐기한 뒤 사용자 세션에서 변경된 결과를 확인합니다.
8. 허가된 계정이 1회성 요청을 사용하고 재사용이 거부됨을 확인합니다. 납부 완료로 표시하지 않습니다.
9. 사용자 제출 자료 삭제와 보고서/원본의 별도 저장 선택을 확인합니다.
10. 공개 네트워크·배포 범위가 정해지고 검증되면 권한 있는 대상의 서명 원본·규칙으로 서비스 API 밖 검증을 시연합니다. 미완료이면 목표와 실제 시연 범위를 명시하며 로컬 성공으로 대체하지 않습니다.

두 기관을 모두 미리 활성화한 데이터만으로 온보딩 완료를 주장하지 않습니다. 적어도 한 기관은 발표 중 신규 승인·키 등록을 수행합니다. 체인 트랜잭션 확정 전에는 대기 상태를 보여주며 승인 성공을 흉내 내지 않습니다.

| 성공 기준 | 목표 |
| --- | --- |
| 웹 완결성 | 기동 후 핵심 흐름을 터미널·DB 직접 수정 없이 수행 |
| 신뢰 경계 | 미승인 기관·타 기관 변경은 거부되고 누가 승인했는지 확인 가능 |
| 설명 가능성 | AI 의심 이유·위치와 발행 검사 결과를 독립 표시; 정상의 발행자/서명/내용 근거와 실패/미실행 원인·현재 상태 구분 |

### 21.1. 합의 방향·착수 기준·후속 결정과 구현

[개발 최종 산출물 후속 결정 목록](final_deliverables_pending_decisions.md)에 기술 선택·공유 계약 최종 검토·행사/시연/제출 조건을 L01~L14로 저장했습니다. 결정 시점과 준비 담당을 따라 추적하며 이미 선정한 ADR 0003 기본값을 다시 미정으로 돌리지 않습니다.

기관 납부 요청의 출처·보호 내용·상태 확인, 가상 기관 인증 단계, 세 입력·AI 네 단계 보고서, 저장 분담·기본 삭제/선택 보관, 공개 체인·서버 밖 검증 목표는 이번 v4.0에 반영했습니다. 다시 방향 승인을 받을 항목으로 취급하지 않습니다.

## 22. 최종 팀 합의 문장

> 우리는 문자·녹음·문서에서 피싱이 의심되는 부분과 이유를 설명하고, 참여 기관이 실제 발행한 납부 요청·증빙의 보호 내용과 현재 상태를 확인하는 서비스를 만듭니다. AI 위험 분석과 발행 기록 검증을 각각 보여주며, 원본은 보호된 DB·파일 저장소에, 발행 증거와 상태 이력은 블록체인에 남깁니다. 공개 체인과 필요한 검증 자료를 통해 권한 있는 대상이 서버 밖에서도 확인할 수 있게 하는 것이 목표입니다.

성공 기준은 17장의 합의 범위와 16장의 실제 검증 증거입니다. 납부 의무·업무상 금액의 진실성·AI의 무오류·완전한 사기 방지를 보증하지 않습니다. 산출물 세부 구성은 별도 검토안이며, 결정되지 않은 값이나 구현되지 않은 기능을 완료로 소개하지 않습니다.
