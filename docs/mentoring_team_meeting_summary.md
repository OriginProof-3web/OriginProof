# OriginProof — 팀 회의용 쉬운 요약

> **당시 멘토링·회의 준비 기록 — 2026-10-13 연결 갱신:** 본문의 합의와 검토 경위는 보존합니다. 현재 개발에는 [최신 개발 계획서](development_plan.md)과 [ADR 0004](adr/0004-v5-governance-wallet-versioning.md)를 적용합니다. 운영자 단독 활성화·서버 기관 서명·새 ID 재발행·모든 입력 필수 가정은 신규 경로에서 대체됐습니다. 입력은 회의 후 확정하고 Decisions API는 후속 검토입니다.

**우리가 만들려는 서비스:** 문자·녹음·문서를 보고 피싱이 의심되는 이유를 알려주고, 참여 기관이 실제로 보낸 납부 요청인지 확인해 주는 서비스입니다.

아래는 다음 멘토링을 위해 정리한 설계 방향입니다. 구현이 완료된 기능 목록은 아닙니다.

## 1. 블록체인: “이 기관이 실제로 보낸 요청인가?”

**기관이 발행한 증거를 남기고, 사용자가 받은 내용과 비교합니다.**

- **확인할 것:** 어느 기관이 발행했는지, 금액·계좌·기한 등이 바뀌었는지, 취소되거나 만료된 요청인지입니다. 그 돈을 실제로 내야 하는지와 금액이 업무상 올바른지는 발행기관이 책임집니다.
- **저장할 것:** 기관과 요청을 구별하는 번호, 내용을 비교할 값, 발행 시각·유효기간, 취소 여부 등입니다. 내용을 비교할 값인 **해시**는 보호할 내용을 계산해 만든 ‘디지털 지문’이라고 이해하시면 됩니다. 원문과 개인정보 전체를 공개하지 않습니다.
- **왜 블록체인인가:** 공개 체인에 증거를 남겨 우리 회사의 DB와 설명에만 의존하지 않고 확인할 수 있게 합니다. 평소에는 우리 서비스를 이용하고, 원하면 받은 원본·전자서명·공개 기록으로 별도 검증할 수 있게 합니다. 공개 체인과 별도 검증은 목표 구조이며, 현재 로컬 체인은 개발용입니다.
- **아무나 등록할 수 있는가:** 기관정보 확인 → 업무용 이메일 인증 → 사전에 지정된 기관 담당자 승인 → 우리 운영자 승인을 거칩니다. 발행할 때도 권한과 전자서명을 확인합니다. 전자서명은 등록된 기관의 발행키로 해당 내용에 서명했는지 확인하는 증거입니다.

**시연에서는** 실제 국세청 조회 대신 준비해 둔 가상 사업자 명부를 대조하고, 이메일도 데모용 메일함으로 확인합니다. 사업자번호만 입력했다고 발행을 허용하지 않습니다.

**예시:** A기업은 5만 원을 요청했는데 사용자가 받은 안내에는 50만 원이라고 적혀 있다면, 발행 기록과 비교해 금액이 달라졌음을 알려줍니다. A기업에는 자사 명의 사칭과 납부 정보 변조를 고객이 구별할 수 있게 한다는 이용 가치가 있습니다.

## 2. AI: “어떤 부분이 수상하고, 왜 조심해야 하는가?”

**사용자가 자료를 넣으면 먼저 내용과 대화 맥락을 분석합니다.** 기관의 발행 기록이 없는 자료도 AI 분석을 받을 수 있습니다.

| 입력 | 분석 방법 |
| --- | --- |
| 문자·메신저·대화 내역 | 붙여 넣은 글을 분석합니다. |
| 녹음 파일 | 음성을 글로 바꾼 뒤 분석합니다. |
| 문서·캡처 이미지 | 글자를 추출한 뒤 분석합니다. |

탐지할 것은 **기관·가족 사칭 정황, 급하게 송금하도록 압박하는 표현, 계좌 변경 유도, 비밀번호·인증번호 요구, 링크·앱 설치 유도, 주변에 확인하지 못하게 하는 요구**입니다. 단어 하나보다 어떤 행동을 요구하는지와 앞뒤 맥락을 살펴봅니다.

결과는 **위험 높음 / 주의 필요 / 뚜렷한 의심 정황 없음 / 판단 보류**로 보여줍니다. ‘피싱 확률 87%’처럼 근거가 불명확한 숫자는 사용하지 않습니다. 잘 읽거나 듣지 못했다면 보류하고, 의심 정황이 없다는 결과도 안전을 보증하지는 않습니다.

보고서는 **한 줄 결과 → 의심 문장과 위치 → 의심 이유 → 피싱 유형 → 확인할 행동** 순서로 제공합니다. 녹음은 시간대, 문서는 페이지 등으로 원래 부분을 찾을 수 있게 합니다.

**예시:** “지금 입금하지 않으면 계좌가 정지됩니다. 다른 사람에게 알리지 마세요.”라는 내용에서 긴급성·불안 조성과 확인 방해 정황을 짚고, 공식 연락처로 확인하도록 안내합니다.

## 3. 일반 DB와 블록체인: “원본과 증거를 어떻게 함께 쓰는가?”

**일반 DB는 자료를 보관하는 곳이고, 블록체인은 발행 증거와 현재 상태를 확인하는 곳입니다.** 둘을 납부 요청 번호로 연결합니다. 이렇게 역할을 나누어 함께 사용하는 것이 ‘하이브리드’입니다.

| 일반 DB·파일 저장소 | 블록체인 |
| --- | --- |
| 기관·계정 정보, 담당자 권한과 승인 기록 | 승인된 기관과 발행키 정보·상태 |
| 납부 요청 원본과 기관의 전자서명 | 요청 번호, 내용의 디지털 지문, 발행 시각·기간 |
| 사용자 제출 자료, AI 분석 결과와 보고서 | 요청 취소 등 상태 변경 이력 |

**기관이 발행할 때:** 권한과 서명을 검사한 뒤 원본은 DB에, 발행 증거는 블록체인에 저장합니다. 블록체인 반영까지 확인해야 등록 완료입니다.

**사용자가 확인할 때:** 자료를 AI로 분석하고, 자료에 있는 요청 번호·QR·검증 링크로 발행 기록을 찾습니다. 원본·전자서명·블록체인 기록을 대조한 결과와 AI 분석을 한 보고서에 함께 보여줍니다. DB의 원본이 바뀌어도 체인에 저장한 디지털 지문과 비교해 차이를 발견할 수 있습니다.

- 기록을 찾지 못하면 AI 분석을 제공하고, 발행 여부는 **‘확인 불가’**로 표시합니다. 기록이 없다는 이유만으로 피싱이라고 확정하지 않습니다.
- 사용자 제출 자료와 AI 판단은 자동으로 블록체인에 등록하지 않습니다.
- 사용자 제출 자료는 처리 후 삭제하는 것이 기본입니다. 보고서는 사용자가 저장을 선택할 때 보관하고, 원본 파일 저장은 별도로 선택하게 합니다. 기관의 발행 원본은 재검증을 위해 따로 보관합니다.
- 체인 조회가 실패하면 이전 DB 기록만 보고 현재 유효하다고 판단하지 않습니다.

**최종 보고서 예시:** AI는 “긴급 송금과 비밀 유지를 요구해 위험 높음”, 발행 기록 검증은 “A기업의 요청은 존재하지만 금액이 다름”이라고 각각 설명합니다. 두 결과를 하나의 피싱 확정 판정으로 섞지 않습니다.

세부 내용은 [멘토링 준비 정리](mentoring_round1_blockchain_decisions.md)에 있습니다. 공개 체인 종류, 지원 파일의 세부 제한, 보존 기간 등은 구현 전에 구체화할 사항입니다.
