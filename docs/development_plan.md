# OriginProof 통합 개발 계획서

> 중요한 디지털 요청과 증빙의 발행 주체, 내용 무결성, 현재 유효성을 검증하는 범용 신뢰 플랫폼
>

문서 목적: 4인 팀이 설계, 개발, 테스트, 데모에 공동으로 사용하는 실행 기준서

작업 버전: 2.1 · 개정일: 2026-09-29

개정 목적: 예선 MVP를 기반으로 **7주 개발 후 마지막 이틀 동안 발표할 실제 동작 웹 서비스**의 범위와 완료 기준을 확정합니다.

이 문서는 저장소 안의 개발 계획 기준본입니다. 저장소 밖의 `originproof_integrated_development_plan.md` v1.0을 복사해 개정했으며, 앞으로 계획 변경은 이 파일에서 관리합니다. 원본은 이전 계획 기록으로 보존합니다.

개발 전 담당자는 이 문서의 3장(권한), 15장(주차), 17장(P0), 16장(검증 기준)과 해당 기능 부분을 확인합니다. 이 문서의 미래 API·Schema·ABI는 개발 목표이며 현재 구현 계약을 자동으로 변경하지 않습니다. 구현 기준은 승인된 Python 모델, 생성 Schema, ABI, [서명 명세](signing_spec.md)입니다. 계약 변경은 담당자 리뷰와 ADR을 거칩니다.

주요 개정: 운영자 화면과 발행자 콘솔을 P0로 올리고, 웹에서 기관 승인·공개키 등록·Proof 발행·검증·폐기를 수행하도록 합니다. W0는 W1 시작 준비로 포함하고, W1~W7 이후 발표 이틀에는 새 기능 개발을 배정하지 않습니다.

핵심 원칙: Don’t detect the fake. Verify the real.

## 0. 프로젝트 요약

OriginProof는 중요한 디지털 요청이나 증빙을 실제 발행 주체가 발행했는지, 보호된 내용이 바뀌지 않았는지, 현재 사용할 수 있는지 검증합니다. AI는 필드 추출을 돕고, 최종 판정은 서명·발행 기록·신뢰 상태를 검증하는 규칙 엔진이 수행합니다.

### 최종 제품과 제출물

최종 산출물은 **운영자, 발행기관 담당자, 일반 사용자가 웹에서 각자의 작업을 수행하는 서비스 시제품**입니다. 7주 말까지 실행 가능한 RC를 준비하고, 이후 이틀은 발표와 시연에 사용합니다. 서비스 기동 이후 핵심 시연은 브라우저에서 진행합니다.

| 산출물 | 최종 제공 내용 | 완료 증거 |
| --- | --- | --- |
| 사용자 웹 | Proof ID·QR/검증 링크 입력, 내용 비교, 근거와 현재 상태 표시 | 새로 발행한 Proof의 정상·변조·미등록·만료 결과 |
| 발행자 콘솔 | 기관 신청, 공개키 등록·교체·폐기, Proof 발행·조회·폐기, 허가된 사용 처리 | 화면 조작으로 API·DB·체인 상태가 실제 변경됨 |
| 운영자 화면 | 신청 검토·승인·반려, 기관 중지, 변경 이력 확인 | 미승인 기관·타 기관의 권한 없는 변경 거부 |
| 공통 API·검증 코어 | 서로 다른 분야의 두 Proof 유형과 공통 Signed Proof 구조 | Schema·OpenAPI·Golden Fixture·통합 테스트 |
| 공유 Registry | 기관·공개키·Proof 상태, 배포 ABI·주소·체인 정보 | 테스트넷과 로컬 배포에서 상태 변경 재조회 |
| 재현·발표 패키지 | 소스·lockfile·실행 안내·테스트 결과·영상·발표 자료 | 다른 노트북 재현과 전체 시연 리허설 |

이미지/PDF OCR와 추가 분석은 P1입니다. 실제 기관 연동 없이 합성 발행자 2곳으로 서비스 흐름을 증명합니다. 실제 기관 신원 확인을 끝낸 서비스라고 표현하지 않습니다.

### 현재 출발점과 남은 차이

점검 기준은 로컬 `feat/mvp-demo-page@18c0ae8`입니다. 원격 PR 병합 상태나 현재 실행 성공을 보장하는 기록은 아닙니다.

| 영역 | 확인된 출발점 | 본선까지 남은 일 |
| --- | --- | --- |
| MVP 검증 | 카드 알림 1종, 서명·해시·필드·Issuer/Key 조회 | 요청형과 문서형으로 공통 코어 확장 |
| Registry | 로컬 Issuer/Key 계약·배포·Reader | 웹 쓰기 권한, 테스트넷, Proof 폐기·consume |
| 발행 | seed로 합성 Proof 생성 | 인증된 기관이 화면에서 새 Proof 발행 |
| 웹 | 후보 필드를 입력하는 검증 데모 | 사용자 입력 개선, 발행자 콘솔, 운영자 화면 |
| AI | 후보 추출기와 OpenAI 어댑터, Mock 이미지 replay | 실제 이미지 성능은 별도 평가 후 표시 |
| 통합 | 기존 문서에 정상·변조 HTTP E2E 및 두 개발환경 재현 기록 | 확대된 전체 웹 흐름을 새 RC에서 검증 |

기존 완료 기록은 [MVP 통합 기록](runbooks/mvp_integration_sequence.md)과 [데모 안내](runbooks/mvp_demo.md)를 참고합니다. 아래 주차별 완료 기준은 앞으로 달성할 목표입니다.

## 1. 문제 정의

사용자는 기관명, 로고, 전화번호, URL, 화면 디자인, 문서 양식과 같은 보이는 정보를 보고 진위를 판단합니다. 그러나 이러한 정보는 복제, 생성, 편집될 수 있습니다. 기존 피싱 탐지는 위험 가능성을 알려주지만 실제 발행 주체가 해당 요청이나 문서를 만들었다는 사실을 직접 증명하지는 못합니다.

OriginProof는 세 가지 신뢰 단절을 해결합니다.

1. 발행자 신뢰: 요청이나 증빙을 실제 상대방 또는 공식 기관이 발행했는가?
2. 내용 무결성: 대상, 금액, 행동, 사건번호, 문서번호 등 핵심 내용이 바뀌지 않았는가?
3. 현재 유효성: 만료, 취소, 폐기, 키 탈취, 재사용 상태가 아닌가?

| 방식 | 주요 질문 | 역할과 한계 |
| --- | --- | --- |
| 피싱 문자 탐지 | 이 문구가 수상한가? | 확률적 판단이며 실제 발행 여부는 증명하지 못함 |
| 악성 URL 탐지 | 이 주소가 위험한가? | URL 밖의 요청과 문서에는 적용이 제한됨 |
| 기관 자체 앱 | 기관 내부 기록에 존재하는가? | 기관별로 분리되어 공통 검증 계층이 없음 |
| 이미지 포렌식 | 화면이나 문서가 편집되었는가? | 편집 흔적이 없다고 정상 발행을 의미하지 않음 |
| OriginProof | 실제 주체가 발행했고 현재 자료와 일치하는가? | 발행자 참여와 검증 가능한 Proof가 필요함 |

## 2. 범위와 원칙

| 유형 | 예시 | 공통 검증 내용 |
| --- | --- | --- |
| 요청형 | 송금, 결제, 승인, 청구 요청 | 요청자, 행동, 대상, 금액, 수신자, 유효기간, 재사용 |
| 거래 증빙형 | 송금 완료 증빙, 결제 영수증, 청구서 | 발행자, 거래 ID, 금액, 상태, 발급 시각 |
| 공식 문서형 | 증명서, 확인서, 통지서, 허가서 | 기관, 문서번호, 대상자, 버전, 발급과 폐기 상태 |
| 법률 절차 증빙형 | 접수증, 송달 자료, 전자서명된 제출본 | 기관, 사건이나 접수번호, 제출 시각, 현재 상태 |
| 확장형 | 계약 확인, Web3 서명, AI Agent 요청 | 발행 주체, 권한, 대상, 정책, 서명, 상태 |

### 비목표

1. 모든 문자와 이메일을 자동 수집해 피싱 여부를 분류하지 않습니다.
2. 화면 캡처만으로 실제 거래가 존재한다고 보증하지 않습니다.
3. 문서 내용의 법률적 타당성이나 사실관계를 판단하지 않습니다.
4. 실제 기관을 사칭한 데모를 만들지 않습니다.
5. 개인정보와 원문을 퍼블릭 블록체인에 저장하지 않습니다.
6. AI 결과만으로 VERIFIED 또는 TAMPERED를 결정하지 않습니다.

| 사용 가능한 표현 | 사용하면 안 되는 표현 |
| --- | --- |
| 등록된 발행 기록과 일치합니다 | 법적으로 진짜입니다 |
| 발행 기록을 확인할 수 없습니다 | 가짜임이 증명되었습니다 |
| 핵심 내용이 등록 원본과 다릅니다 | AI가 사기를 확정했습니다 |
| 현재 폐기되었거나 유효하지 않습니다 | 화면만으로 실제 거래가 보장됩니다 |
| 확인 자료가 부족합니다 | 등록되지 않았으므로 무조건 위조입니다 |

## 3. 사용자, 화면과 권한

세 역할은 하나의 Next.js 앱에서 화면과 서버 권한을 구분합니다. 화면을 숨기는 것만으로 권한을 보호하지 않습니다. 로그인·기관 소속·객체 소유권을 모든 변경 API에서 검증하고, 체인 쓰기는 허가된 계약 호출자로 제한합니다.

| 역할 | 필수 화면·행동 | 허용하지 않는 행동 |
| --- | --- | --- |
| 일반 사용자 | Proof ID·QR/링크로 조회, 받은 자료의 핵심 필드 비교, 근거·상태 확인 | 기관 승인, 키 관리, 임의 Proof 발행·폐기 |
| 발행기관 담당자 | 기관 신청·승인 상태, 자기 기관 공개키 관리, Proof 발행·목록·폐기 | 자기 기관 자체 승인, 타 기관 키·Proof 변경 |
| 플랫폼 운영자 | 기관 신청 검토·승인·반려·중지, 변경 이력 확인 | 운영자 권한만으로 타 기관의 서명을 생성 |

일반 검증 조회는 발행자 관리 로그인 없이 가능하도록 합니다. 대상자에게 제한된 정보·행동은 별도 인증을 요구합니다. 기관별 계정을 분리하며, 화면의 역할 선택만으로 권한을 얻을 수 없어야 합니다. 일반 검증 요청과 1회성 사용 처리는 분리하고, consume은 발행자 또는 지정된 수신자만 수행합니다.

### 브라우저에서 이어지는 필수 흐름

1. 발행기관 담당자가 합성 기관 정보로 등록을 신청합니다.
2. 운영자가 신청과 담당자 정보를 확인하고 승인합니다. 반려·중지된 기관은 신규 발행을 할 수 없습니다.
3. 승인된 기관 담당자가 발급키를 생성·등록합니다. 웹에는 공개 signer, key ID, 유효 기간과 상태만 표시합니다.
4. 기관 담당자가 허용된 유형의 내용을 입력하고 발행합니다. 서버가 정규화·서명·저장하고 Proof ID·QR/검증 링크를 반환합니다.
5. 사용자가 해당 Proof를 조회합니다. ID만 입력하면 발행 기록의 유효성만 설명하고, 자료의 내용 일치 여부는 사용자가 제공한 필드를 실제 비교한 경우에만 표시합니다.
6. 사용자가 받은 자료의 금액·문서번호 등을 비교하고 결과와 근거를 확인합니다.
7. 담당자가 키 또는 Proof를 폐기하면 사용자 재검증에 변경된 상태가 반영됩니다.
8. 요청형 Proof는 권한 있는 계정이 사용 처리하며, 중복·동시 사용 시 하나만 성공합니다.

권장 본선 시나리오는 `Origin Mock Bank`의 `PAYMENT_REQUEST`와 합성 문서 발행기관의 `OFFICIAL_DOCUMENT`입니다. 기관명·필드·수신자 binding은 W1에 확정합니다. 기존 `CARD_PAYMENT_NOTICE`는 회귀 검증 사례로 보존합니다. 실제 결제나 실제 기관 업무는 수행하지 않습니다.

## 4. 통합 Proof 모델

모든 분야는 동일한 Signed Proof Envelope를 사용하고 세부 필드는 `proof_type`별 payload schema로 분리합니다.

아래는 확장 모델입니다. 현재 구현은 `CARD_PAYMENT_NOTICE` 하나이며 W1에 요청형·문서형 계약을 추가합니다. 기존 모델의 key ID·chain ID·app domain·signature scheme도 보존하고 [서명 명세](signing_spec.md)와 Golden Fixture를 기준으로 호환성을 검증합니다. 변경 가능한 생명주기 상태는 서명된 원문과 분리해 조회합니다.

| 필드 | 설명 | 필수 여부 |
| --- | --- | --- |
| proof_id | 전역 고유 식별자 | 필수 |
| issuer_id | 발행 주체 식별자 | 필수 |
| proof_type | 요청, 증빙, 문서 등 유형 | 필수 |
| schema_version | 정규화와 검증 규칙 버전 | 필수 |
| payload_hash | canonical payload 해시 | 필수 |
| subject_binding_hash | 수신자나 대상자의 salted hash | 유형별 |
| issued_at | 발행 시각 | 필수 |
| expires_at | 만료 시각 | 유형별 |
| nonce | 재전송 방지 값 | 요청형 필수 |
| single_use | 1회 사용 여부 | 요청형 선택 |
| lifecycle_status (별도 조회) | ACTIVE, CONSUMED, EXPIRED, PROOF_REVOKED 등 현재 상태 | 검증 결과에 반영 |
| metadata_hash | 추가 메타데이터 무결성 | 선택 |
| signature | 발행자 전자서명 | 필수 |

| Proof 유형 | 주요 필드 |
| --- | --- |
| ACTION_REQUEST | action, target, recipient_binding, policy_id |
| PAYMENT_REQUEST | amount, currency, payer_binding, beneficiary_binding, target_hash |
| TRANSACTION_RECEIPT | transaction_id, amount, currency, sender_token, recipient_token, status |
| OFFICIAL_DOCUMENT | institution_code, document_type, document_number, subject_token, version |
| LEGAL_PROCESS_PROOF | authority_code, case_or_receipt_number, filing_type, filed_at, status |
| GENERAL_CREDENTIAL | credential_type, holder_binding, claim_hash, valid_from, valid_until |

### Canonicalization

1. UTF-8 NFC 정규화를 적용합니다.
2. 키 순서를 고정한 JSON으로 직렬화합니다.
3. 금액은 최소 화폐 단위 정수와 통화 코드로 분리합니다.
4. 날짜는 ISO 8601과 시간대를 포함합니다.
5. 이름, 계좌, 당사자 정보는 토큰이나 salted hash를 사용합니다.
6. 기존 payload 해시와 schema version을 포함한 서명 구조는 signing_spec.md를 따릅니다. 변경은 버전·Golden Fixture·마이그레이션 검토 후 적용합니다.
7. 언어별 구현 결과가 Golden Fixture에서 동일해야 합니다.

## 5. 검증 결과 모델

검증 결과, 생명주기 상태, 실패 사유를 분리합니다. 아래는 목표 모델이며 실제 enum은 공통 Python 모델을 따릅니다. 현재 구현과의 상태 조합 차이는 16장에 명시하고 W1에 확정합니다.

| Verification Status | 의미 | 사용자 안내 |
| --- | --- | --- |
| VERIFIED | 발행자, 서명, 내용이 유효 | 등록된 발행 기록과 일치합니다 |
| NOT_REGISTERED | Proof 또는 발행자를 찾을 수 없음 | 검증 가능한 발행 기록이 없습니다 |
| TAMPERED | 서명 또는 핵심 내용이 불일치 | 등록된 원본과 내용이 다릅니다 |
| INCONCLUSIVE | 화질, 형식, 입력 부족 | 추가 확인 자료가 필요합니다 |
| ERROR | 시스템 또는 네트워크 오류 | 잠시 후 다시 시도해 주세요 |

| Lifecycle Status | 의미 |
| --- | --- |
| ACTIVE | 현재 유효함 |
| EXPIRED | 유효기간이 지남 |
| CONSUMED | 1회성 Proof가 이미 사용됨 |
| PROOF_REVOKED | 발행자가 해당 Proof를 폐기함 |
| ISSUER_SUSPENDED | 발행자의 신뢰 상태가 중지됨 |
| ISSUER_KEY_REVOKED | 발행키가 폐기됨 |

확장 검토 대상 Reason Code는 `INVALID_SIGNATURE`, `PAYLOAD_HASH_MISMATCH`, `TARGET_MISMATCH`, `AMOUNT_MISMATCH`, `RECIPIENT_MISMATCH`, `SUBJECT_BINDING_MISMATCH`, `POLICY_MISMATCH`, `PROOF_NOT_FOUND`, `SCHEMA_UNSUPPORTED`, `LOW_OCR_CONFIDENCE`, `REPLAY_DETECTED`입니다.

목표 판정은 Proof 식별, 신뢰 상태, 서명과 해시, 생명주기, binding, 유형별 필드를 포함합니다. 실제 검사 순서·조기 종료·미실행 검사 표시를 W1에 확정하며, 서명을 검사하지 않고 VERIFIED로 표시하지 않습니다.

### 장애와 재시도

1. 제출 대기·성공·실패를 구분하고, 트랜잭션 제출만으로 등록 성공을 표시하지 않습니다.

4. 테스트넷 장애 시 별도로 준비·서명한 로컬 데모 데이터로 전환하고 네트워크를 화면에 표시합니다. chain ID가 다른 Proof를 그대로 재사용하지 않습니다.
5. P1 AI 실패 시 Proof ID·QR와 직접 필드 입력으로 검증합니다.

## 7. 블록체인, 기관 승인과 키 관리

서로 다른 기관과 검증자가 기관·키·폐기 상태를 공통 Registry에서 확인합니다. DB는 신청·계정·payload와 작업 이력을 저장하며, 온체인에는 opaque ID, 공개 signer, 상태·기간·이벤트만 저장합니다.

| 구성 | 범위 | 계획 기능 |
| --- | --- | --- |
| IssuerRegistry | P0, 기존 구현 확장 | 승인된 기관 등록, 상태 조회·중지 |
| IssuerKeyRegistry | P0, 기존 구현 확장 | 공개키 등록·조회·교체·폐기 |
| ProofStatusRegistry | P0, 신규 목표 | Proof 폐기, 권한 있는 consume, 중복 사용 거부 |
| PolicyRegistry | P1 | 별도 정책 해시·도메인 관리가 필요한 경우 |
| EvidenceAnchor | P1 | 선택적 commitment 또는 batch anchor |

표의 기능명은 요구사항이며 현재 ABI를 뜻하지 않습니다. M3/M4가 기존 계약을 우선 재사용하고 W1에 변경 ABI와 쓰기 권한을 확정합니다. Registry 운영자 권한과 발행용 서명키는 분리합니다.

### 기관 온보딩

1. 기관 담당자의 로그인 계정과 기관 신청을 연결합니다. 신청은 DB에서 대기·승인·반려 상태로 관리합니다.
2. 운영자가 기관 정보와 담당자 권한의 확인 근거를 기록합니다. 본선에서는 합성 기관을 사전에 정한 기준으로 승인합니다.
3. 승인 작업이 성공한 기관만 체인에 활성화합니다. DB 신청 승인과 체인 반영의 중간·실패 상태를 구분합니다.
4. 승인된 기관의 담당자만 자기 기관의 키와 Proof를 관리합니다. 계정이 있다고 해서 신뢰 기관이 되는 것은 아닙니다.
5. 운영자가 기관을 중지하면 신규 발행을 차단하고 기존 Proof의 재검증 결과에 기관 중지를 표시합니다.

### 키 등록과 서명

- 웹에서 등록하는 대상은 **공개 검증키/signer와 key ID·유효 기간**입니다. 공개 주소를 안다는 이유만으로 등록 권한을 부여하지 않습니다.
- 본선 기본안은 기관별로 분리된 서버 측 합성 서명기입니다. 담당자의 웹 요청으로 발급키를 생성하고 공개 signer를 Registry에 등록합니다. 등록 전 challenge 서명 검증으로 서명기와 공개키의 대응을 확인합니다.
- 개인키는 서버의 보호된 secret 또는 제한된 파일에서만 사용합니다. 브라우저 코드·입력 폼·API 응답·로그·Git·온체인에 개인키를 노출하지 않습니다. 공개키만 등록해 놓고 대응하는 서명기 없이 발행 성공을 표시해서는 안 됩니다.
- 이 구조는 합성 기관 시제품의 키 보관 방식입니다. 실제 기관 자체 지갑·KMS 연동은 확장 범위이며 도입 완료로 표현하지 않습니다.
- 키 교체는 새 키 등록·서명 검증·발행 전환 후 이전 키의 상태를 처리합니다. 정상 교체와 유출에 따른 폐기를 구분하고 이전 Proof 처리 정책을 W1 ADR에 명시합니다.
- 폐기한 키는 재활성화하지 않습니다. 만료·폐기 키로 신규 발행을 거부하며 기존 Proof는 현재 키 상태를 결과에 표시합니다.

### Proof 상태와 1회 사용

Proof 폐기는 발행자 권한으로 처리합니다. consume은 발행자 또는 지정된 수신자에게만 허용하고, 같은 Proof의 동시 요청은 원자적으로 하나만 성공하게 합니다. 누구나 호출 가능한 검증 조회가 Proof를 소비해서는 안 됩니다. 온체인 상태 변경 권한과 API의 기관·수신자 권한을 함께 검증합니다.

## 8. AI와 OCR

| 모듈 | 입력 | 출력 | 판정 권한 |
| --- | --- | --- | --- |
| OCR | 이미지와 PDF | 텍스트, 위치, confidence | 없음 |
| Type Classifier | 레이아웃과 텍스트 | proof type 후보 | 없음 |
| Field Extractor | OCR 결과 | ID, 발행자, 금액, 번호 | 없음 |
| Semantic Extractor | 비정형 요청 | action, target, subject 후보 | 없음 |
| Manipulation Signal | 이미지 | 편집 의심 영역 | 없음 |
| Verification Engine | Proof와 Registry | 최종 상태와 사유 코드 | 규칙 기반 |
1. confidence가 낮으면 사용자의 필드 확인을 요구합니다.
2. 추출값과 사용자 확인값을 구분해 기록합니다.
3. 모델, 프롬프트, 임계값 버전을 남깁니다.
4. 합성 자료와 사용 허용 자료로 평가합니다.
5. 실제 개인정보를 학습이나 저장에 사용하지 않습니다.
6. AI 없이도 Proof ID와 QR 기반 검증이 동작해야 합니다.

| Entity | 주요 정보 | 보존 기준 |
| --- | --- | --- |
| Account / Membership | 인증 주체, 역할, 기관 소속 | 계정 운영 기간, 비밀값 응답 금지 |

| Infra | Docker Compose·Makefile·GitHub Actions | 재현 기동, CI, 웹 접근 가능한 시연 환경 |

서명·정규화는 [기존 명세](signing_spec.md)를 재사용합니다. 인증 방식·테스트넷·본선 접속 환경은 W1에 결정합니다. 외부 서비스나 프레임워크를 추가하기 전에 기존 구현으로 요구사항을 충족할 수 있는지 확인합니다.

### 본선 브랜치와 주간 병합

기본 흐름은 **작업 브랜치 → `integration` → 주간 PR → `main`**입니다. `main`은 검증된 시연 기준, `integration`은 팀 작업을 수시로 모아 검증하는 브랜치로 유지합니다.

1. 기존 PR #19(`mvp/integration` → `main`)의 검토·병합을 마친 뒤, 승인된 `main` SHA에서 본선용 `integration`을 생성합니다. 기존 `mvp/*`는 MVP 이력이며 본선 통합 브랜치와 구분합니다.
2. A~D 모두 최신 `integration`에서 이슈별 작업 브랜치를 만듭니다. 이름은 `feat/<issue>-<summary>`, `fix/<issue>-<summary>`, `docs/<issue>-<summary>`를 사용하며 개인별 영구 브랜치는 두지 않습니다.
3. 완료한 작업은 `integration`을 대상으로 PR을 올리고, 담당 영역 리뷰와 필요한 검사를 통과한 뒤 수시로 병합합니다. 작업자는 최신 통합 변경을 반영해 충돌을 해결합니다.
4. W1~W7 매주 말 C가 `integration` → `main` PR을 준비하고, 영역별 담당자가 리뷰하며 D가 통합 검증 결과를 정리합니다. A의 본선 주 역할은 Product·Frontend입니다.
5. 주간 PR에는 포함 이슈, 변경 화면·API, 검증한 SHA와 실제 결과, 미완료 항목을 기록합니다. 리뷰·필수 CI·해당 주 통합 검증이 통과하면 C가 병합합니다. 주말이 되어도 기준을 충족하지 못하면 기존 `main`을 유지하고 이월 사유를 기록합니다. 검증 후 추가 커밋이 들어오면 최신 SHA를 다시 검증합니다.
6. 장기 브랜치 간 이력이 이어지도록 주간 PR은 merge commit으로 병합합니다. `main`의 병합 결과와 예외 수정은 `integration`에 반영하고 다음 작업을 시작합니다.
7. 병합된 작업 브랜치는 후속 작업·열린 PR에서 사용하지 않는지 확인한 뒤 삭제합니다. `main`과 `integration`은 개발 기간 동안 유지하며 강제 푸시하거나 삭제하지 않습니다.

### `main` 보호와 직접 푸시 예외

- 일반 변경은 PR, 작성자 외 리뷰어 1명 이상 승인, 해당 경로 CODEOWNER 승인과 필수 CI 통과를 요구합니다. 일반 직접 푸시·강제 푸시·브랜치 삭제를 차단합니다.
- 사용자님 계정 `@Jordi2801K`에 한정된 보호 규칙 우회 권한을 마련합니다. **사용자님이 해당 변경의 `main` 직접 푸시를 명시적으로 요청한 경우에만** 예외를 사용합니다. 관리자 권한이나 이전 요청만으로 상시 직접 푸시하지 않습니다.
- 예외 적용 시에도 변경 내용·필요한 검사 결과·요청 사유·반영 SHA를 이슈에 남기고, 반영 직후 `main` 변경을 `integration`에 동기화합니다. 직접 푸시 요청은 강제 푸시나 브랜치 삭제 허가를 뜻하지 않습니다.
- 명시 요청 여부는 팀과 에이전트가 지키는 운영 규칙입니다. GitHub 우회 권한 자체가 대화 속 요청 여부를 판별하지는 않습니다.

위 내용은 채택한 운영 정책이며 GitHub 설정 완료 기록이 아닙니다. W1 시작 시 C가 저장소 요금제·권한과 적용 가능한 보호 설정을 확인하고, 실제 실행되는 필수 CI 이름·CODEOWNER·우회 대상과 적용 결과를 기록합니다. 특정 계정으로 우회를 제한할 수 없으면 관리자 전체에 예외를 열지 않고 가능한 설정을 다시 합의합니다. 설정을 확인하기 전에는 보호가 적용됐다고 보고하지 않습니다. 아래 CI 표는 목표이며 미구현 검사는 구현 후 필수 검사로 등록합니다.

Definition of Done은 수용 기준 충족, 변경에 필요한 테스트와 품질 검사 통과, 보안 영향 확인, 문서 갱신, 리뷰 승인을 포함합니다. P0 웹 기능은 해당 역할의 브라우저 조작부터 실제 상태 변경·재조회까지 성공해야 합니다.

| CI 단계 | 자동화 | 실패 시 병합 |
| --- | --- | --- |
| Pre-commit | format, lint, secret scan | 금지 |
| PR CI | unit, contract, schema, typecheck, build | 금지 |
| Integration | Docker Compose, seed, API와 chain test | 금지 |
| Security | dependency audit, Slither, static scan | High 이상 금지 |
| E2E | 발행, 조회, 검증, 폐기, 소비 | 금지 |

make demo-reset 한 번으로 Mock Issuer, fixture, 테스트 계정과 상태를 재생성할 수 있어야 합니다.

## 16. 테스트 전략과 수용 기준

현재 MVP 완료 기록을 확대된 서비스의 테스트 결과로 재사용하지 않습니다. 아래 항목은 본선 RC에서 새로 검증할 수용 기준입니다. 각 테스트는 기대값과 실제값, 실행 커밋·환경을 남깁니다.

| ID | 시나리오 | 기대 결과 |
| --- | --- | --- |
| F01 | 신규 요청형·문서형 Proof 발행 후 검증 | 두 기관·두 유형에서 VERIFIED + ACTIVE, 발행·서명·내용 근거 |
| F02 | 같은 ID의 금액 또는 문서번호 변경 | TAMPERED와 실제 불일치 필드의 사유 |
| F03 | 만료된 Proof | EXPIRED 표시, 현재 사용 가능하다는 안내 금지 |
| F04 | 1회성 Proof의 순차·동시 consume | 허가된 요청 하나만 성공, 나머지 REPLAY_DETECTED; 반복 조회는 상태 불변 |
| F05 | 기관 A가 기관 B의 키·Proof 변경 | 서버·계약 권한에 따라 거부, B의 상태 불변 |
| F06 | 등록되지 않은 Proof·발행자 조회 | NOT_REGISTERED, 위조라고 단정하지 않음 |
| F07 | Proof 폐기 후 새 사용자 세션에서 재검증 | PROOF_REVOKED 반영, 현재 유효로 표시하지 않음 |
| F08 | 키 폐기·키 만료·정상 교체 | 신규 발행 차단/전환과 기존 Proof 처리 결과가 W1 정책과 일치 |
| F09 | 기관 신청 후 승인 전 발행·키 등록 시도 | 거부; 운영자가 승인하고 체인 반영 후에만 허용 |
| F10 | 무권한 사용자의 기관 승인·consume 시도 | 거부; 임의 역할·기관 ID 주입으로 우회할 수 없음 |
| F11 | 기관 중지 후 신규 발행·기존 Proof 검증 | 발행 거부, 기존 Proof에 ISSUER_SUSPENDED 표시 |
| F12 | 등록·발행 요청 timeout 후 재시도 | 기존 작업 조회, 키·Proof·체인 변경 중복 생성 방지 |
| F13 | RPC 장애·미확인 트랜잭션·재시작 | 대기/오류 구분, 현재 유효 판정 보류, 복구 후 상태 일치 |
| F14 | 지정 수신자·서명 도메인·네트워크 불일치 | 해당 보호 필드/권한 검증 실패; 다른 chain ID 서명 재사용 금지 |
| F15 | 비밀정보·접근성·요청 제한 | 개인키/토큰 노출 없음, 키보드 사용·결과 읽기 가능, 과도한 요청 제한 |
| F16 (P1) | 이미지/PDF 저품질·오추출·악성 입력 | 불확실성·실패를 명시, 파일 제한·삭제, 실제 모델 평가와 Mock replay 분리 |

서명 검증 결과와 현재 유효성을 분리합니다. 현재 MVP는 만료 시 `INCONCLUSIVE + EXPIRED`를 사용합니다. 원래 v1 계획의 `VERIFIED + EXPIRED`와 차이가 있으므로 W1에 조합 정책을 ADR·모델·Fixture로 확정합니다. Proof 폐기·consume의 조합도 함께 정하며 enum이 존재한다는 이유로 기능 완료로 간주하지 않습니다.

단위 검증은 정규화·서명·경계값, 계약 검증은 권한·기간·상태·동시성, 통합 검증은 API·DB·chain·indexer, 브라우저 E2E는 세 역할의 전체 흐름을 다룹니다. 기본 테스트는 Mock/합성 데이터로 재현하고 유료 API 평가는 별도 opt-in으로 기록합니다.

## 17. 본선 범위와 우선순위

### P0 필수 — W5 통합 완료, W6 검증, W7 RC

1. 일반 사용자·기관 담당자·운영자의 웹 화면과 실제 서버 권한 검증.
2. 서로 다른 분야의 합성 기관 2곳에 대한 웹 신청·승인·반려·중지.
3. 승인된 기관의 공개키 생성·등록·목록·교체·폐기와 보호된 기관별 서명기.
4. 요청형·문서형 각 1개 adapter와 웹 발행·목록·조회·폐기. 기존 카드 알림 회귀 검증 유지.
5. Proof ID·QR/검증 링크, 받은 자료의 핵심 필드 비교, 근거·현재 상태를 보여주는 사용자 화면.
6. 정상·변조·미등록·만료·Proof 폐기·키 폐기·기관 중지 검증.
7. 지정 수신자 binding과 권한 있는 consume·동시 재사용 방지. 단순 조회는 소비하지 않음.
8. 작업 대기·실패·재시도·감사 이력, 비인가 변경·중복 처리·개인키 노출 방지.
9. 로컬·테스트넷 Registry, 네트워크 표시, 재현·seed·smoke·복구 안내.
10. 다른 환경 재현, RC·발표 자료·영상·두 날짜의 시연 준비.

서비스 기동과 합성 계정 준비는 스크립트를 사용할 수 있지만, 발표에서 보여줄 기관 승인·키 등록·발행·검증·폐기는 브라우저에서 실제 수행해야 합니다. 버튼만 바뀌거나 미리 넣은 성공 결과를 표시하는 것은 완료가 아닙니다.

### P1 선택 — P0 완료를 지연시키지 않는 범위

1. 이미지/PDF OCR와 후보 필드 확인, 실제 추출 성능 평가.
2. 업로드 원문 암호화·만료 삭제. 파일 업로드를 제공하는 경우에는 보안 처리가 함께 필수입니다.
3. 마스킹 리포트 다운로드, 검색·통계 편의 기능.
4. 별도 PolicyRegistry, EvidenceAnchor 또는 batch anchor.
5. 실제 기관의 자체 서명기·외부 지갑·KMS 연결.

### P2 확장

추가 Proof 유형, 이미지 조작 의심 영역, LLM 의미 비교, AI Agent 요청, L2·Consortium 비교는 본선 P0 이후 확장입니다.

일정이 부족하면 P2 → P1 순으로 제외합니다. 세 역할의 웹 흐름, 두 발행자·두 유형, 권한·서명·현재 상태·재사용 방지는 유지합니다. P0가 지연되면 기능을 조용히 선택 항목으로 바꾸지 말고 팀 합의로 계획과 발표 범위를 함께 갱신합니다.

## 18. 최종 시연과 제출 계획

아래 흐름을 합성 데이터로 브라우저에서 실제 실행합니다. 행사 발표 시간은 확정되지 않았으므로 W7에 주어진 시간에 맞춰 진행 속도와 설명을 조정합니다.

1. 기관 담당자 세션에서 신규 합성 기관을 신청합니다.
2. 운영자 세션에서 검토·승인하고 Registry 등록 완료를 확인합니다.
3. 기관 담당자가 공개키를 생성·등록하고 활성 상태를 확인합니다.
4. 첫 기관이 새 요청형 Proof를 발행하고 QR/검증 링크를 전달합니다.
5. 사용자 세션에서 정상 검증 후 금액만 바꿔 불일치 결과와 근거를 확인합니다.
6. 다른 분야의 기관이 문서형 Proof를 발행하고 같은 코어로 검증합니다.
7. 발행자가 Proof 또는 키를 폐기한 뒤 사용자 세션에서 변경된 결과를 확인합니다.
8. 허가된 계정이 1회성 요청을 사용하고, 두 번째 사용이 거부되는 것을 확인합니다.

두 기관을 모두 미리 활성화한 데이터만으로 온보딩 완료를 주장하지 않습니다. 적어도 한 기관은 발표 중 신규 승인·키 등록을 수행합니다. 체인 트랜잭션 확정 전에는 대기 상태를 보여주며 승인 성공을 흉내 내지 않습니다.

| 성공 기준 | 목표 |
| --- | --- |
| 웹 완결성 | 기동 후 핵심 흐름을 터미널·DB 직접 수정 없이 수행 |
| 신뢰 경계 | 미승인 기관·타 기관 변경은 거부되고 누가 승인했는지 확인 가능 |
| 설명 가능성 | 수행한 검사만 근거로 표시, 정상에는 발행자·서명·내용 등 2개 이상 근거; 실패에는 실패 원인·미실행 검사를 구분 |
| 속도 | 이미 발행된 Proof의 일반 검증 5초 이내 목표; 체인 쓰기 확정 시간은 별도 측정 |
| 범용성 | 두 기관의 요청형·문서형이 동일 코어·Registry를 사용 |
| 안정성 | 고정 RC 전체 리허설 3회, 다른 노트북 재현, 로컬 fallback·영상 준비 |
| 제출물 | 소스와 RC SHA, 배포 네트워크·주소, 실행·복구 문서, 테스트 결과, 발표 자료·영상 |

서비스 접속 환경(호스팅 또는 행사장 로컬 접속)은 W1에 결정하고 W6에 검증합니다. 공개된 서비스·문서에는 개인키, 계정 비밀번호, API token을 넣지 않습니다.

## 22. 최종 팀 합의 문장

> 우리는 문자나 화면의 인상을 보고 가짜를 추측하는 시스템을 만들지 않습니다. 다양한 디지털 요청과 증빙에 검증 가능한 발행 기록을 연결하고, 사용자가 실제 발행 주체, 내용 무결성, 현재 상태를 확인한 뒤 안전하게 행동할 수 있는 공동 신뢰 인프라를 만듭니다.
>

OriginProof의 성공은 지원 분야의 개수가 아니라, 서로 다른 분야가 하나의 Proof Core와 Shared Trust Registry를 사용하면서 각 유형의 의미를 정확하게 검증하는 E2E 시스템을 완성하는 데 있습니다.
