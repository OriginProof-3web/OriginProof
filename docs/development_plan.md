# 찐품명품 · OriginProof 통합 개발 계획서 5.1

> 공식 안내의 발행 출처·보호 내용·현재 유효 상태를 검증하고, AI로 전달 메시지의 피싱 위험과 확인할 행동을 설명합니다.

- 작업 버전: **5.1** · 개정일: **2026-10-15, 한국시간**
- 이전 작성: 5.0 **2026-10-11**, 관련 문서 동기화 **2026-10-13**, 공유 계약 준비 **2026-10-14**
- 목적: 5.0 기능·7주 계획을 유지하면서 기존 PR의 병합/종료 결과와 재사용 인계를 저장소에서 추적합니다.
- 개정 이유: GitHub 댓글에만 있던 인계 정보를 에이전트가 관련 개발 중에 찾을 수 있도록 문서화하고, 종료된 PR을 진행 중으로 보던 현황을 갱신합니다. 임시 인계 목록을 AGENTS·START_HERE에 추가하지 않습니다.
- 문서 상태: **개발 계획 5.1 및 재사용 인계 반영본**입니다. 새 기능 구현·소유자/소비 리뷰·5.0 통합 완료를 뜻하지 않습니다.
- 기준본: 이 파일입니다. 수정 직전 4.0은 [원문 보존본](development_plan_v4.0_snapshot.md)에, 직전 5.0은 [Git 고정 원본](https://github.com/OriginProof-3web/OriginProof/blob/1f83369455136236f28f33988ea3b875dba89f11/docs/development_plan.md)에 보존합니다.
- 개정 이력: [0.3절](#03-개정-이유와-이력), 현재 재사용 인계는 [별도 문서](handoffs/v5_reuse_handoff.md)를 확인합니다.
- 중요 미정: **사용자 입력의 최종 지원 종류·우선순위는 팀 회의 후 확정합니다. Decisions API는 현재 개발 범위에서 제외합니다.**

## 0. 읽는 순서와 근거

빠른 확인은 **1장 변경 요약 → 3장 현재 개발 상태 → 4장 유지·전환·제외 → 12장 7주 계획 → 18장 문서 반영 상태와 후속 작업** 순서로 진행하시면 됩니다.

우선순위는 **이번 사용자의 명시적 결정 → 이 문서의 적용 정책 → 변경하지 않은 기존 계약 → 과거 기록·설계 제안**입니다. PDF에 없는 기존 요구를 자동 삭제하지 않고, PDF의 모든 제안 기술로 기존 코드를 일괄 교체하지도 않습니다.

별도 2차 멘토링 회의록 전체는 제공되지 않았습니다. 첨부 기획서의 내용을 2차 멘토링에서 전부 확정한 것으로 추정하지 않았으며, 이번에 선택하신 개발 방향과 Decisions 아이디어를 구분해 반영했습니다.

### 0.2 버전과 완료 상태의 구분

개발 계획 5.1, API 버전, 서명 스키마 버전, 문서 내용의 v1/v2, 컨트랙트 배포 버전은 서로 다릅니다. 계획서 번호만 바꾸어 기존 서명·데이터를 새 규칙으로 해석하지 않습니다.

상태는 다음 네 가지로 기록합니다.

1. **기존 구현·검사 근거 있음:** 코드와 당시 검사 기록이 있습니다.
2. **리뷰·병합·연결 대기:** 개발본이 있으나 대상 단계에 반영되거나 최종 조합으로 검증되지 않았습니다.
3. **5.0 신규·변경 개발:** 새 요구를 구현·검사해야 합니다.
4. **회의 후 결정 / 후속 검토:** 현재 개발 완료 조건에 자동으로 넣지 않습니다.

## 1. 4.0에서 무엇이 달라지는가

아래는 5.0에서 정한 기능 방향입니다. 5.1은 그 범위를 유지하고 PR 현황·인계 접근 경로를 갱신합니다.

| 항목 | 4.0 및 기존 구현 | 5.0 적용 방향 |
| --- | --- | --- |
| 제품 설명 | 납부 요청·증빙 중심 | 공식 안내 검증으로 설명을 통일하고, 납부 안내와 공식 문서를 대표 템플릿으로 사용합니다. 내부 프로젝트명 OriginProof는 유지합니다. |
| 기관 승인 | 명부·데모 이메일·내부 승인 이후 플랫폼 운영자 최종 승인 | 앞의 확인 절차는 유지하고, 온체인 권한 부여는 서로 다른 승인자 **2-of-3 공동승인**으로 전환합니다. |
| 긴급 사고 | 운영자·기관/키 상태 관리 | 승인자 1명 또는 해당 기관 활성 키로 즉시 기관 정지, 재활성화·키 교체는 2-of-3으로 구분합니다. |
| 기관 발행키 | 기관별 서버 합성 서명기 | 신규 공식 안내는 기관 지갑에서 직접 서명합니다. 서버는 기관의 업무 서명을 만들거나 개인키를 보관하지 않습니다. |
| 체인 권한 판단 | 허가된 서버 gateway의 요청·commitment 중심 | 기관의 EIP-712 서명을 컨트랙트가 검증하고, 등록 기관·소유권·nonce·deadline·버전을 확인합니다. |
| 내용 수정 | 철회 후 새 Proof ID 발행 | 신규 안내는 동일 documentId의 다음 버전으로 발행하며 이전 최신 버전을 대체합니다. 과거 Proof 방식은 과거 계약으로 보존합니다. |
| 내용 비교 | 선택 보호 필드 비교 | 보호 필드 비교를 유지하고 **원본 바이트 일치 검사**를 별도 추가합니다. 둘의 검사 범위와 결과를 구분합니다. |
| AI | 추출·피싱 정황·근거 설명 | 규칙 검사와 구조화된 LLM 분석을 연결하고, 근거가 실제 입력에 있는지 검사합니다. 발행 진위 판정과 독립입니다. |
| 입력 | 텍스트·녹음·문서/이미지를 필수로 가정 | **최종 지원 종류·우선순위는 팀 회의 대기**입니다. 기존 추출 자산을 보존하되 신규 STT/OCR 구현을 확정 일정으로 배정하지 않습니다. |
| UI/UX | 15개 화면 템플릿·UX01~10 설계 | 기존 디자인과 템플릿을 재사용하고 공동승인 수·지갑 서명·버전·비교 범위·기관 정지를 보완합니다. |
| 기술 스택 | Next.js + Python API/코어/분석 + PostgreSQL + Solidity | 유지합니다. PDF의 TypeScript 전체 통합 재작성은 채택하지 않습니다. |
| 공개 체인 | 공개 체인·서버 밖 검증 목표 | 목표를 유지하되 네트워크·비용·확정 기준은 미정입니다. 로컬 시연과 공개 네트워크·독립 운영 달성은 별도로 보고합니다. |
| Decisions API | 없음 | 빠른 분류·초기 작업 추천을 위한 **회의 검토 후보**입니다. 이번 7주 필수 개발·성능 약속에 포함하지 않습니다. |

**입력에 관한 최신 결정:** 이전 문서에 세 입력이 P0라고 적혀 있어도 이번에는 자동 적용하지 않습니다. 기존 텍스트·이미지 추출 코드가 있다는 사실과 최종 제품에서 지원할 입력을 확정하는 일은 다릅니다. 입력 결정 전에는 공통 분석 결과·권한·보관·오류 계약과 합성 텍스트 기반 독립 검사를 진행할 수 있습니다.

## 2. 최종 제품과 범위

### 2.1 사용자가 받는 결과

사용자는 받은 안내에 대해 다음 정보를 한 화면에서 확인합니다.

- 어느 등록 기관이 발행했는지와 서명이 유효한지
- 제출한 원본 또는 비교한 보호 항목이 발행 자료와 같은지
- 해당 버전이 철회·대체·만료되었는지, 기관 정지·키 사고 경고가 있는지
- 전달 메시지에서 어떤 행동이 위험하며 어떤 근거로 그렇게 설명하는지
- 검사하지 못한 항목, 확인 시각·네트워크, 다음에 확인할 행동

**공식 기록 확인은 내용의 사실성·납부 의무·거래 완료·행동의 안전을 보증하지 않습니다.** 정상 QR 옆에 추가된 사기 문구는 발행 기록 검사와 별도로 분석합니다. 미등록·AI 보류·원본 불일치·체인 장애를 서로 다른 결과로 표시합니다.

### 2.2 개발 범위

| 구분 | 포함 항목 |
| --- | --- |
| 5.0 필수 기능 | 가상 기관 2곳, 두 안내 템플릿, 기존 인증·권한, 2-of-3 기관 등록·키 교체·재활성화, 단독 긴급 정지, 기관 지갑 서명, 컨트랙트 서명 검사, 문서 소유 고정·버전·철회, ID/QR 조회, 원본/보호 필드 비교 범위 표시, DB 조작 탐지, AI 위험·근거·보류, 통합 결과, 최소 보관·삭제·접근성·복구 |

기존 요청형의 수신자 binding·single_use·consume은 **기존 계약의 보존·회귀 대상**입니다. 공개 안내를 읽거나 QR을 조회하는 행위에 consume을 붙이지 않습니다. 신규 문서 버전에 1회 사용을 확장하는 일은 별도 범위 결정 전까지 추가하지 않습니다.

### 2.3 일정 압박 시 축소 순서

먼저 정상 경로인 기관 확인 → 공동승인 → 기관 서명 → 발행 → 검증 → 철회를 연결합니다. 이후 다음 순서로 추가 부담을 줄입니다.

1. 검색·통계·원문 diff·보고서 파일 출력 등 편의 기능을 미룹니다.
2. 작업자 자동 제출이 불안정하면 **동일 서명·동일 컨트랙트 규칙의 기관 직접 제출**로 시연합니다. Operation 기록·중복 방지·영수증 대조는 유지합니다.
3. 입력 회의에서 정한 우선 경로부터 구현합니다. 미선정 입력은 미구현/후속 후보로 표시합니다.
4. LLM 장애 시 검증된 규칙 결과를 별도로 표시하고 LLM 분석은 보류합니다. 이를 전체 AI 성능 목표 달성으로 표현하지 않습니다.
5. 공개 배포가 준비되지 않으면 로컬 데모임을 표시합니다. 공개 체인·독립 운영 목표는 미달성으로 남깁니다.

공동승인·서명/소유권 검사·현재 상태·민감정보 보호·오류 처리·기본 접근성을 축소 대상으로 삼지 않습니다.

| W5/W6 보안·복원·CI·실제 DB/Anvil 도구 | 유지·재검증 | 신규 서명·nonce·이벤트·DB 전환에도 같은 장애 원칙을 적용합니다. 서버 기관키 백업은 레거시 한정, 신규 기관키 복구 책임은 기관에 있습니다. |
| 카드 알림 v1 endpoint·정상/금액 변조 fixture | 회귀용 유지 | 신버전 작업이 기존 성공/변조 판정을 깨지 않는지 검사합니다. 최종 서비스 대표 화면에서는 중심 시나리오로 사용하지 않습니다. |
| TypeScript 전체 통합·추가 큐/SDK·자체 모델 | 채택하지 않음 | 기존 Python·Next.js·PostgreSQL·Foundry 자산으로 구현합니다. 문서 제안만으로 새 스택이나 병렬 구현을 만들지 않습니다. |

**삭제 조건:** 대체 경로의 기능·보안·회귀·데이터 읽기가 검증되고 호출자/화면/문서 연결이 제거된 뒤에만 후속 작업에서 정리합니다. 지금은 기존 서명키·원본·배포 정보·과거 테스트를 지우지 않습니다.

## 5. 신뢰 범위와 기관 승인

### 5.1 무엇을 신뢰하는가

블록체인에는 기관이 작성한 모든 내용이 진실이라는 사실을 저장하지 않습니다. **등록된 키가 특정 내용을 발행했고, 이후 어떤 상태 변경이 있었는지**를 확인하는 증거를 남깁니다.

전자서명은 서명한 데이터와 키의 관계를 확인합니다. 블록체인은 여러 승인자·발행기관이 권한과 변경 이력을 공유하고 서비스 운영자의 DB 밖에서 확인하는 기준을 제공합니다. 승인자가 한 운영자에게 종속돼 있으면 실제 독립 운영의 장점은 제한됩니다. DB+전자서명·감사 로그라는 대안보다 복잡해지는 이유를 이 공동 권한 관리 요구로 설명합니다.

해커톤의 세 지갑은 **2-of-3 규칙 시연**입니다. 같은 팀·기기에서 관리한다면 실제 다기관 독립 운영을 입증한 것은 아닙니다. 승인자 2명의 공모, 기관이 직접 허위 내용을 발행하는 위험, 악성 웹 화면·키 탈취는 남습니다.

### 5.2 온보딩과 권한

1. 신청자가 가상 사업자번호·기관명·대표자·개업일자를 제출합니다.
2. 사전 준비된 가상 명부와 정상 상태·도메인을 대조합니다.
3. 데모 메일함으로 업무용 이메일 코드를 확인합니다.
4. 명부에 지정된 별도 내부 승인자가 담당자의 발행 권한을 확인합니다. 자기 신청·타 기관 승인은 거부합니다.
5. 기관 지갑이 신청·기관·공개키·nonce·만료에 묶인 일회성 challenge로 키 보유를 증명합니다.
6. 개인정보 없는 기관 공개 메타데이터의 hash와 기관 ID·발행 주소·작업 종류·만료를 묶어 고정 제안을 만듭니다.
7. 서로 다른 승인자 3명 중 2명이 동일 제안을 승인합니다. 중복·만료·변경된 제안은 거부합니다.
8. 두 번째 승인 트랜잭션에서 등록을 실행하고 체인 상태를 재조회한 뒤 활성화를 표시합니다.

내부 승인은 기관 담당자 권한 확인이고, 공동승인은 플랫폼 권한 부여입니다. 두 절차를 같은 것으로 세지 않습니다. 웹 운영자는 신청 접수·검토를 할 수 있지만 혼자 체인 기관을 활성화할 수 없습니다.

| 동작 | 5.0 권한 기준 |
| --- | --- |
| 기관 등록 | 서로 다른 승인자 2-of-3 |
| 키 교체 | 새 키 보유 증명 + 2-of-3 |
| 기관 재활성화 | 2-of-3 |
| 기관 긴급 정지 | 승인자 1명 또는 해당 기관 활성 키 |
| 문서 발행 | 해당 기관의 현재 활성 키 서명 + 기관 ACTIVE |
| 문서 철회 | 해당 문서 소유 기관의 현재 활성 키 서명; 정지 중에도 피해 축소를 위한 철회 허용 |
| 승인자 교체 | 해커톤에서는 배포 시 3명 고정, 운영 교체 UI·정책은 후속 검토 |
| 조회 | 읽기 전용. 제한된 기존 원문은 기존 권한을 유지 |

긴급 정지는 즉시 신규 발행을 차단하고 기존 문서에 경고를 남깁니다. 정지 해제는 단독으로 할 수 없습니다. 실행자·사유 코드는 이벤트로 남기며, 자유 입력 심사자료·개인정보는 온체인에 넣지 않습니다. 단독 정지 남용은 일시 중단을 일으킬 수 있고, 복구에는 두 승인자가 필요합니다.

## 6. 발행·버전·서명·검증

### 6.1 식별자와 버전

- 신규 documentId는 **keccak256(abi.encode(issuerId, docKey))**를 기준으로 합니다. docKey는 기관 안에서 유일하며 개인정보가 없는 내부 문서 키입니다.
- 컨트랙트는 검증된 서명자의 기관을 기준으로 ID를 계산합니다. payload의 issuerId/documentId와 일치하는지 검사하고 최초 소유 기관을 고정합니다.
- 키가 바뀌어도 issuerId와 문서 소유권은 유지됩니다. 서로 다른 기관의 같은 docKey는 서로 다른 문서입니다.
- 버전은 최초 1, 이후 최신 + 1입니다. 새 버전 등록·최신 포인터 변경·ACTIVE인 이전 최신 버전 대체는 하나의 체인 트랜잭션에서 처리합니다. 이미 철회된 이전 최신은 REVOKED를 유지하며 재철회를 거부하고, 새 버전 발행의 성공·최신 포인터는 별도로 유지합니다.
- 철회·대체한 원본/hash는 덮어쓰지 않습니다. 최신 버전을 철회해도 과거 버전이 자동 활성화되지 않습니다.
- QR에는 documentId와 버전을 식별할 수 있는 검증 링크를 사용합니다. 버전 생략 링크가 최신을 조회한다면 화면에 실제 조회 버전을 표시합니다.
- 기존 proof_id와 새 documentId/version은 별도 namespace·계약으로 읽습니다. 기존 자료의 ID·서명을 재계산해 이전 발행 사실을 바꾸지 않습니다.

### 6.2 보호 필드와 원본 바이트

| 검사 | 기준 | 결과의 의미 |
| --- | --- | --- |
| 보호 필드 비교 | 기관·문서 식별/버전, 금액·통화, 은행·계좌·예금주, 목적·기한·공식 링크 등 해당 템플릿의 서명 대상 | **비교한 항목**이 같은지 확인합니다. 생략된 값은 미비교로 남깁니다. |
| 원본 바이트 검사 | 발행자가 확인한 원본 bytes의 SHA-256 | 그 원본 전체가 같은지 확인합니다. 공백·줄바꿈·형식 변환도 다른 원본이 될 수 있습니다. |
| 발행 서명 검사 | EIP-712 typed payload·등록 키·발행 당시 권한 | 해당 기관키가 해당 버전·내용·기간에 서명했는지 확인합니다. |
| 현재 상태 검사 | 신뢰 설정의 체인·계약 직접 조회 | 현재 철회·대체·만료·기관 정지·키 사고 상태를 확인합니다. |

원본 bytes와 보호 필드의 canonical 표현을 혼동하지 않습니다. **원본 hash는 byte 동일성, 보호 필드 hash는 선언한 항목 동일성**을 확인합니다. 두 값의 알고리즘·직렬화·서명 포함 범위를 W1의 새 공유 계약에서 확정합니다. 기존 Keccak 기반 v1/v2 payload hash를 SHA-256으로 일괄 바꾸지 않습니다.

필드와 원본은 발행 전에 같은 확정 데이터로 생성·대조합니다. 서명하는 브라우저가 받은 원본의 hash를 다시 계산하고 보호 필드·기간을 보여준 뒤 서명합니다. 서버가 준 hash만 그대로 서명하지 않습니다. QR을 붙인 렌더링 사본은 hash 대상 원본과 구분합니다.

납부 안내에는 금액·계좌·예금주·기한을 포함하며, 공식 행동 링크를 제공하면 링크도 보호 범위에 넣습니다. 링크를 바꾸는 안내문을 단순 디자인 변경으로 취급하지 않습니다. 기존 3.0.0 납부 필드 제안은 초안으로 재사용하되, 신규 지갑·버전 서명 체계의 최종 지원 버전은 W1 계약 검토로 확정합니다.

신규 공개 체인 시연은 개인정보 없는 합성 공개 안내를 사용합니다. 개인별 청구서·민감자료와 그 단순 hash를 공개하지 않습니다. 기존 제한 Proof와 수신자 binding은 별도 경로에서 기존 권한을 유지합니다.

### 6.3 서명과 제출

1. API가 권한·필드·기관 상태를 검사하고 초안/원본을 준비합니다.
2. 기관 브라우저가 원본 hash와 서명 대상 필드를 확인합니다.
3. 기관 지갑이 EIP-712 업무 payload에 서명합니다.
4. 서버가 서명·payload를 검증하고 원본·서명·Operation을 하나의 DB 트랜잭션으로 저장합니다.
5. 중계자 또는 기관이 같은 publish(payload, signature)를 호출합니다.
6. 컨트랙트가 등록 키·소유권·기관 상태·정확한 다음 버전·nonce·deadline을 검사합니다.
7. receipt·이벤트·해당 문서 상태를 대조한 뒤 확정을 표시합니다.

서명 대상에는 action, issuerId, docKey, documentId, version, 내용 hash/알고리즘, 서명 schema, keyId, issuedAt, expiresAt, nonce, deadline을 포함합니다. EIP-712 도메인은 서비스명·서명 버전·chainId·verifyingContract를 포함합니다. 최종 타입/필드명·인코딩은 C/B 공통 Golden으로 고정합니다.

발행과 철회는 다른 action으로 서명합니다. nonce는 기관별로 원자적으로 소비하고 deadline과 문서 expiresAt을 구분합니다. 중계자의 msg.sender를 기관 발행 권한으로 쓰지 않습니다. 중계자는 가스용 트랜잭션 서명은 할 수 있지만 **기관의 업무 payload에 대신 서명하지 않습니다.**

지갑 거절·주소/네트워크 변경·만료·서명 취소는 성공으로 표시하지 않습니다. 전송 여부가 불명확하면 기존 hash·nonce·이벤트·Operation을 먼저 확인하고, deadline 이후에는 재서명을 요청합니다.

### 6.4 상태와 키 정책

처리 상태, 문서 상태, 검사 결과, 기관/키 경고를 별도 필드로 제공합니다.

| 축 | 기본 상태·표시 |
| --- | --- |
| 업무 처리 | DRAFT, QUEUED, SUBMITTED, MINED, CONFIRMED, FAILED 및 결과 미확인 UNKNOWN |
| 문서 버전 | ACTIVE, REVOKED, SUPERSEDED; EXPIRED는 기간으로 판정 |
| 기관 | 심사/공동승인 대기, ACTIVE, SUSPENDED |
| 키 | 활성, 정상 교체로 신규 사용 종료, 사고/폐기 상태와 적용 블록·이력 |
| 검사 | 성공·불일치·미등록·미실행·확인 불가를 검사 항목별로 제공 |

상태명은 목표 계약이며 현재 enum에 모두 구현됐다는 뜻은 아닙니다. 기존 VERIFIED/TAMPERED 등은 버전별 의미를 유지하고 새 상태를 억지로 기존 값에 끼워 넣지 않습니다.

정상 키 교체 뒤에는 이전 키의 **새 발행을 거부**하되, 교체 이전 정상 발행 서명을 위조로 처리하지 않습니다. 새 v5 경로는 발행 당시 키 권한과 현재 사고 경고를 구분합니다. 유출 시점이 불명확하면 과거 안내에도 추가 확인 경고를 표시하고 사용 가능으로 단정하지 않습니다. 정지 → 새 키 공동승인 → 필요한 문서 철회 → 공동 재활성화 순서를 검증합니다.

기존 v1/v2의 유출 키 폐기·consume·현재 사용 불가 판정은 호환 경로에서 유지합니다. 신규 정책으로 기존 자료를 조용히 재분류하지 않습니다.

| 온체인 | 기관 ID·키 이력·공개 메타데이터 hash·승인자/임계값·제안/승인/정지 이력 | 공동 권한 관리와 감사 근거입니다. |
| 온체인 | documentId·소유 기관·버전·내용 hash·발행 키/블록·기간·최신 포인터·철회/대체·nonce·이벤트 | 발행 증거와 현재 상태의 기준입니다. |
| 기관 지갑 | 신규 기관 발행 개인키 | API·DB·중계자가 보유하지 않습니다. |
| 서버 보호 설정 | 가스용 중계키·세션 등 서비스 비밀 | 기관 업무 서명키와 분리하며 공개 결과·Git·로그에 넣지 않습니다. |

원문·전체 계좌·개인정보·심사자료·사용자 메시지·AI 결과를 온체인에 넣지 않습니다. hash는 암호화/익명화가 아니며 짧은 원문은 추측 가능하므로 데이터 선택 자체를 제한합니다.

### 7.1 동기화와 오류

DB와 체인은 동시에 커밋되는 하나의 트랜잭션이 아닙니다. 기존 Operation을 제출 의도의 내구성 저장소로 재사용하고, 실제 자동 작업자가 필요하면 기존 큐/DB 패턴 안에서 연결합니다. 별도 outbox 테이블이라는 이름만을 위해 같은 상태를 중복 저장하지 않습니다.

| 상황 | 처리·검증 기준 |
| --- | --- |
| DB 저장 실패 | 정상 API 경로에서는 제출하지 않습니다. Writer 예약 해제와 DB commit 결과 미확인 처리를 구분합니다. |
| DB 저장 후 전송 전 중단 | 보존된 요청·서명으로 복구합니다. deadline·기관/키 상태를 다시 확인합니다. |
| 제출 응답 유실 | UNKNOWN으로 남기고 같은 tx/nonce/이벤트를 확인합니다. 새 문서·새 버전을 무조건 만들지 않습니다. |
| receipt 성공·DB 갱신 실패 | 이벤트와 현재 체인 상태로 재조정합니다. 클라이언트가 보낸 txHash만 믿지 않습니다. |
| 직접 제출 txHash 접수 | chainId·계약·성공 receipt·이벤트의 기관/문서/버전/hash가 저장 요청과 같은지 확인합니다. |
| DB 원본 조작 | 재계산 hash 불일치를 표시합니다. 원본 삭제 시에는 비교 불가이며 hash로 복원하지 않습니다. |
| DB 상태 조작 | 실제 체인 철회/대체/정지를 표시하고 DB 불일치를 기록합니다. |
| 기관 표시 조작 | 공개 메타데이터 hash 불일치를 경고하며 검증되지 않은 기관명으로 성공을 꾸미지 않습니다. |
| RPC 장애·reorg | 현재 상태 확인을 보류하고 blockHash·checkpoint·이벤트 중복을 확인합니다. |
| 재시작·재배포 | 같은 배포 복구와 새 계약 배포를 구분합니다. 이전 manifest/주소/상태를 새 체인 결과로 재사용하지 않습니다. |

로컬 확정은 성공 receipt와 상태 재조회로 확인합니다. 공개 네트워크의 MINED/CONFIRMED·재구성 기준은 네트워크 결정 후 확정합니다. 다른 RPC의 동일 응답만으로 암호학적 상태 증명을 완성했다고 표현하지 않습니다.

## 8. AI 분석·입력 후보·Decisions API

### 8.1 AI의 확정된 역할

AI는 기관/인물 사칭 정황, 긴급 송금·계좌 변경 유도, 비밀번호/인증번호 요구, 링크·앱 설치 유도, 공식 확인 방해 등을 **문맥과 요구 행동**으로 설명합니다. 단어 포함만으로 판정하지 않습니다.

| 결과 | 사용자 표현 |
| --- | --- |
| HIGH | 위험 높음 |
| CAUTION | 주의 필요 |
| NO_CLEAR_SIGNAL | 뚜렷한 의심 정황 없음 — 안전을 보장하지 않습니다. |
| ABSTAIN/해당 계약의 보류 값 | 판단 보류 — 부족한 입력·인식·모델 오류를 설명합니다. |

규칙 검사 → 기존 provider의 구조화된 LLM 분석 → 실제 입력 근거 대조 → 보고서 순서로 연결합니다. 생성된 인용이 원문/변환 텍스트에 없으면 근거로 표시하지 않습니다. 부정문·인용된 사기 예시·공식 경고와 실제 요구를 구분하는 사례를 검사합니다.

AI에는 발행·승인·송금·지갑·DB 변경 권한을 주지 않습니다. 입력 속 지시는 분석 대상입니다. AI가 실패해도 ID 조회·원본/필드의 결정론 검증은 동작합니다. 규칙 검사만 제공한 결과는 “규칙 검사 결과”라고 표시합니다.

### 8.2 입력은 회의 후 확정합니다

| 후보 | 재사용·준비 가능한 부분 | 선택 시 추가 작업 |
| --- | --- | --- |
| 텍스트 붙여넣기 | 기존 입력 검증·후보 추출·provider·합성 텍스트 평가 | 피싱 근거·규칙·보고서 연결 |
| 이미지/캡처 | 기존 이미지 검증·Mock/추출 경계 | 실제 OCR/vision·영역 근거·저품질 평가 |
| PDF | 기존 설계·페이지/크기 제한 초안 | 텍스트 추출·렌더/OCR·페이지 근거·악성/손상 처리 |
| 녹음 파일 | 기존 STT·시간대 설계 초안 | 코덱·길이 검사·전사·시간 근거·잡음 평가 |
| 발행 원본 파일 제출 | 원본 hash 검증 정책 | 실제 허용 형식·업로드/비교 UX와 자원 제한 결정 |

최종 선택 전에는 위 모든 항목을 지원한다고 안내하거나 UI에 활성 버튼을 만들지 않습니다. **기관이 원본을 보존하고 hash를 대조하는 코어는 필수**이나 사용자가 어떤 형식으로 원본을 제출할지는 입력 회의에서 결정합니다.

ADR 0003의 후보 제한은 텍스트 10,000 코드 포인트, 이미지 5MiB/12MP/1프레임, PDF 10MiB/10페이지, 녹음 20MiB/300초/2채널입니다. 선택한 형식에만 적용하고 서버가 실제 내용·signature·디코딩 결과를 검사합니다. 외부 URL 자동 방문, 압축 묶음, 브라우저 녹음·카메라 스캔은 별도 선택 없이 추가하지 않습니다.

분석 공통 준비 기준은 작업 전체 180초, 계정별 실행 중 1건·10분당 5건, 동일 요청의 중복 과금/실행 방지입니다. provider timeout·retry는 기존 설정을 재사용하되 전체 제한을 넘기지 않습니다. 늦은 결과가 실패/삭제 상태를 덮어쓰지 않도록 합니다. 실제 지원 상한은 선정된 입력의 검사 결과와 함께 확정합니다.

### 8.3 Decisions API — 현재 범위 밖

2차 멘토링에서 나온 UX 개선 아이디어로 기록합니다. 팀 회의에서 도입 여부를 정하기 전에는 **구현 작업 ID·필수 KPI·완료 조건을 배정하지 않습니다.**

검토 가능한 사용처는 입력/의도의 빠른 분류, “발행 기록 조회 / 내용 비교 / 위험 분석” 중 다음 작업 안내, 첫 사용자에게 필요한 절차 추천입니다. 분류 결과로 허용된 UI 선택지를 추천하는 용도이며 기관 승인·발행 진위·자동 거래를 결정하지 않습니다.

2026-10-11 확인한 [OpenAI Decisions 공식 문서](https://developers.openai.com/api/docs/guides/decisions)는 텍스트·이미지에 대한 확률·선택·점수 형태의 응답을 제공하는 베타 API로 설명합니다. 긴 근거 설명 생성과 같은 역할로 단정하지 않으며, API 자체의 속도 설명을 우리 서비스 전체 지연 개선 보장으로 옮기지 않습니다.

회의에서 확인할 것은 적용 화면 1개와 기대 행동, 기존 규칙/Responses 경로 대비 p50·p95·오추천·비용, 실패 시 기본 버튼 제공, 계정 접근 가능 여부와 전송 데이터입니다. 이번에는 호출·SDK 교체·유료 실험을 수행하지 않습니다.

## 9. 보관·권한·보안 기본값

분석 소유자는 서버 세션에서 정합니다. 보고서 소유권과 기관 제한 원본 접근 권한은 별개입니다. 공개 ID 조회는 로그인 없이 가능하되 기존 제한 payload는 기관/지정 수신자 권한을 유지합니다.

| 데이터 | 개발 기본값 |
| --- | --- |
| 미선택 사용자 원본·전체 변환 텍스트·provider 입력 | 처리 종료 직후 삭제, 실패 잔여물 최대 수명 수락 후 1시간 |
| 미선택 결과 일시 전달본 | 종료 후 최대 10분, 만료 후 접근 거부 |
| 선택 보고서·필요 인용/위치 | 종료 후 7일 |
| 별도 선택 원본 | 수락 후 7일, 악성/형식 검사 실패 자료는 저장하지 않음 |
| 기관 발행 원본·서명 | 버전별 expiresAt 이후 30일까지, 철회·대체로 조기 삭제하지 않음 |
| Operation·감사 | 30일, 미해결 작업은 해결 후 30일 |
| 검증 세션 | 생성 후 24시간 |

이 값은 ADR 0003의 **데모 기본값**을 재사용합니다. 무기한 유효 문서는 이번에 추가하지 않으며 버전별 만료를 둡니다. 실서비스의 영구 보존·법적 보관 정책으로 주장하지 않습니다. PDF의 운영 로그 7일 제안으로 기존 감사/Operation 30일을 자동 변경하지 않습니다.

원본·보고서 보관은 독립 체크박스이며 기본 해제입니다. 만료·삭제 접근 차단은 즉시, 물리 삭제는 정상 가동 중 5분 정리 주기를 사용합니다. 재시작 시 잔여물 정리 후 분석을 수락하고 실행 중 삭제 후 늦은 응답 재저장을 막습니다. 원본이 삭제되면 재생·원본 비교 불가를 표시합니다. 기관 원본은 사용자 분석 삭제와 독립입니다.

가상 이메일 코드는 기존 착수 기준인 6자리·5분 만료·60초 재발급 간격·10분당 3회 발급·코드당 실패 5회·15분 누적 실패 10회 제한을 유지합니다. 새 발급은 이전 코드 무효화, 검증·소비는 원자적으로 처리합니다. 메일함은 데모 전달 수단이며 실제 이메일 소유를 인증했다고 표현하지 않습니다.

보안 필수 사항은 세션/CSRF·기관/객체 권한, 업로드 내용·크기/자원 제한, nonce/deadline·도메인 검증, 개인정보·개인키·token 로그 금지, 자동 외부 URL 접근 금지, 요청 제한, 안전한 오류 응답입니다. 지갑 주소를 안다고 업무 권한을 주지 않습니다. HTTPS 제공 환경에는 Secure cookie를 사용하고 로컬 개발 예외와 구분합니다.

## 10. UI/UX 구체화 반영

### 10.1 기존 설계를 살리는 방식

[UI/UX 1.1](ui_ux_design.md)에 기존 **15개 템플릿**과 공식 웹 디자인을 재사용해 아래 5.0 변경 요구를 반영했습니다. 문서 반영과 실제 UI 구현·제품 검사는 별도입니다. 페이지 수를 늘리는 대신 기존 목록·상세 안에서 필요한 단계를 먼저 표현합니다.

| 기존 ID·화면 | 재사용 | 5.0 보완 |
| --- | --- | --- |
| G01 시작 / G02 로그인 | 자료 분석과 발행 기록 조회 분리, 허용 화면으로 복귀 | 미선정 입력/기능 숨김, 사용자에게 지갑을 불필요하게 요구하지 않음 |
| U01 분석 입력 | 레이블·제한·보관 선택·중복 제출 방지 | 회의에서 선정된 입력만 활성화, 관련 제한만 안내 |
| U02 처리/결과 | AI/발행 결과 두 영역, 근거·확인 행동·보관 안내 | 규칙/LLM 결과 출처, 근거 대조 실패, 검사 범위·문서 버전·체인 경고 |
| U03 발행 기록 | 공개 조회·권한 있는 비교·기술 상세 | 원본 전체/보호 필드/ID 조회를 구분, 구버전·최신 버전 링크, 서버 밖 검증 자료 |
| I01 기관 신청 | 명부·메일·신청 상태 | 지갑 연결·키 보유 증명과 공동승인 0/2·1/2·2/2·체인 반영 표시 |
| I02 내부 승인 | 자기 기관의 타 계정 승인/반려 | 내부 승인과 공동승인 구분, 자기 승인·타 기관 접근 차단 |
| I03 키 관리 | 공개 주소·상태·사고 안내 | 서버 키 생성 버튼을 지갑 등록/새 키 보유 확인으로 전환, 교체 제안·승인 대기 |
| I04 새 발행 | 유형별 필드·읽기 전용 최종 확인 | 원본 hash 재계산 → 서명 대상 확인 → 지갑 서명 → 제출/확정 상태 |
| I05 목록 / I06 상세 | 목록·QR·작업 상태·철회 | documentId/version·최신/대체/철회·이전 버전 이력, 다음 버전 발행 |
| O01 신청 목록 / O02 상세 | 근거 검토·반려·이력 | 고정 제안 내용·서로 다른 승인자·만료·서명/승인 상태, 단독 최종 활성화 제거 |
| O03 기관 목록 / O04 상세 | 기관/키 상태·이력 | 단독 긴급 정지와 2-of-3 재활성화 구분, 실행자·사유·사고 안내 |

웹 역할은 사용자·기관·운영/승인자 세 그룹으로 유지하고 내부 승인자·공동승인자의 세부 권한을 분리합니다. “승인자 A/B/C” 지갑과 개발 담당 A/B/C를 혼동하지 않게 실제 화면에서는 승인자 1/2/3 등으로 표시합니다.

### 10.2 사용자에게 보여줄 정보의 순서

**한 줄 안내 → AI 위험 분석 / 발행 검증 → 실제 근거 → 비교 범위·문서/기관 상태 → 확인할 행동 → 보관·삭제** 순서를 유지합니다. 모바일에서는 같은 순서로 한 열에 배치합니다.

ID만 조회한 경우에는 “발행 기록을 확인했습니다. 받은 내용은 비교하지 않았습니다”라고 안내합니다. QR 복사 사례에서 정상 기록을 확인해도 메시지 전체가 안전하다는 배지를 주지 않습니다. 체인 조회 실패 시 과거 성공 결과에 현재 확인 시각을 붙이지 않습니다.

공동승인·지갑·체인 단계에는 실제 서버/체인에서 확인한 상태만 표시합니다. 서명 거절과 전송 후 UNKNOWN을 구분하고, UNKNOWN의 기본 행동은 기존 작업 재조회입니다. 가짜 진행률·임의 피싱 확률·지갑 자동 팝업 반복을 사용하지 않습니다.

## 11. 기술 구성·공유 계약·전환

### 11.1 유지할 구조

Next.js/TypeScript 웹, FastAPI/Pydantic·Python 코어, SQLAlchemy/Alembic·PostgreSQL, Solidity/Foundry/OpenZeppelin, 기존 analyzer·indexer·Docker Compose·Makefile·CI를 재사용합니다. Redis/Celery 등은 실제 비동기 작업에 필요한 기존 연결을 사용하며 신규 필수 인프라를 추가하지 않습니다.

공유 모델 원본은 packages/python/originproof_core입니다. JSON Schema·TypeScript·OpenAPI는 원본 생성 경로를 유지합니다. ABI·배포 manifest는 B가 관리하고 C와 호환성을 검토합니다. 검증 코어에 HTTP·DB·UI/provider를 넣지 않습니다.

### 11.2 새로 필요한 계약

2026-10-14 [공유 계약 v5-shared-0.1](shared_contract_v5.md)의 원본 모델·생성 Schema/TypeScript/예정 OpenAPI·인터페이스 ABI·Golden을 준비했습니다. 팀원은 같은 원본을 소비하며 개별 계약을 다시 정의하지 않습니다. 소유자/소비 리뷰·실제 Registry/API/DB 구현은 후속이고 V5-Q03/W1 전체 완료로 처리하지 않습니다.

### 11.3 이행 순서

1. [재사용 인계 문서](handoffs/v5_reuse_handoff.md)의 보존 원본·중복 관계와 현재 phase를 대조하고 기능/검사·API·ABI·데이터 버전 및 사용할 기준 SHA를 선택합니다.
2. 새 지갑/공동승인/문서 모델과 Golden을 별도 버전으로 정의합니다. 구버전 원본·서명·상태는 변경하지 않습니다.
3. DB에는 제안·승인·문서/버전·서명 요청·배포 참조를 필요한 만큼 추가합니다. 기존 Operation/감사·projection 구조를 활용합니다.
4. 로컬에 신규 Registry를 별도 배포하고 manifest·새 Adapter·웹을 연결합니다. 배포자는 단독 우회 권한이나 업그레이드 경로를 가지지 않도록 검사합니다.
5. 신규 발행은 새 경로로 제공하고 기존 카드/Proof 조회·검증·권한·필수 회귀를 유지합니다. 과거 서명을 새 체인의 발행 사실로 자동 이전하지 않습니다.
6. 실패하면 새 발행을 중단하고 기존 읽기를 유지합니다. 이미 확정된 새 온체인 기록·철회는 DB rollback으로 되돌릴 수 없습니다.
7. 구 경로 삭제는 호출자·회귀·자료 보존을 확인한 별도 정리 작업에서만 수행합니다.

평가 설계는 기존 ADR 0003의 원본 사례 **60개(네 수준별 15개), 개발 24개/보류 평가 36개**를 우선 재사용합니다. 선택한 입력만 같은 원본 사례로 변환하고 동일 사례의 모든 변형은 같은 집합에 배치합니다. 세 입력 180개를 확정 수량으로 쓰지 않습니다. 실패 사례는 선정 입력별 최소 4개, 공통 provider/삽입 지시 사례를 포함합니다.

초기 비교 목표는 네 수준 macro-F1 0.80 이상, HIGH recall 0.90 이상, 판독 가능으로 사전 표시한 보호 필드 일치율 0.95 이상입니다. 근거 인용 문자열은 출력 전 대조를 통과해야 하며 별도로 근거 누락·위치 정확도를 평가합니다. 보류·실패율·confusion matrix·표본 수·모델/프롬프트·비용·지연을 공개합니다. PDF의 100개 텍스트 평가안은 대안이며 기존 60개 평가와 무조건 합치거나 유리한 수치만 고르지 않습니다.

입력 결정 후 D가 manifest·분할·라벨을 준비하고 A 또는 C가 사전 검토합니다. 실측 이후 합격선을 조용히 낮추지 않으며 합성 소표본을 실사용 탐지율로 일반화하지 않습니다. 실제 유료 평가 범위·예산은 별도 결정하고 Mock replay와 구분합니다.

## 15. 협업·브랜치·재사용 인계

기존 역할 소유권과 작업 branch → phase/Wn → integration 흐름을 유지합니다. 완료·보존된 phase는 수정/재사용/삭제하지 않고 5.0 변경은 후속 PR로 남깁니다. 단계 번호가 같다는 이유로 새 5.0 변경을 과거 완료 증거에 끼워 넣지 않습니다.

기존 단계 승격/준비 PR #39/#37/#38/#55와 관련 UI/QA/AI PR은 5.0 후속 개발로 대체해 종료했습니다. #52는 문서만 integration에, #50/#47/#49는 각각 phase/W2/W3/W4에 병합했습니다. #56은 `33bc4f4`로 integration에 병합됐으며 실제 서비스 연결·재사용 완료와 구분합니다. 과거 PR을 다시 순서대로 병합하는 절차 대신 [재사용 인계 문서](handoffs/v5_reuse_handoff.md)의 고정 SHA·중복·후속 담당을 기준으로 필요한 변경을 현재 작업에 연결합니다. C가 적용 경계·원본/생성물·ABI·검증 SHA와 후속 PR 대상을 조율합니다. 종료된 브랜치·커밋과 기존 검증 이력은 보존합니다.

인계 문서의 항목은 적용 범위 결정 → 후속 반영 → 검증 완료로 근거를 남깁니다. 완료 시 반영 PR·실제 검증 SHA/명령/결과를 기록하고 활성 목록에서 완료 기록으로 옮깁니다. 완료 전 원본을 삭제하지 않으며 임시 상태를 AGENTS·START_HERE에 복제하지 않습니다. 각 담당자는 독립 구현·검사 완료 시 계약·예시·SHA·실패/미실행을 인계하고, 실제 연결 이후 단계 완료를 판단합니다. 작업마다 필요한 경로 소유자와 작성자 외 리뷰를 받으며 모든 PR에 전원 승인을 요구하지 않습니다. A의 웹 연결·D의 독립 실행·B/C의 서명/ABI 대조를 서로 대신한 것으로 기록하지 않습니다.

개인 기여 기록은 기존 portfolio/Wn-역할과 PR 양식을 사용합니다. 재사용한 팀원 코드·자신의 수정·AI 보조·사람의 결정·실행 근거를 분리합니다. 단계 완료에는 관련 PR·CI·실제 수용 검사·기여/리뷰 근거가 필요합니다. main 통합·외부 제출·배포는 이번 문서 개정으로 실행하지 않습니다.

### 16.1 시연 흐름

1. 가상 기관 확인·내부 승인·지갑 키 보유 확인 후, 승인자 1명으로 활성화되지 않음을 보여드립니다.
2. 두 번째 승인으로 기관을 활성화하고 기관 지갑으로 새 안내를 서명·발행합니다.

6. 철회·DB 원본/상태/기관명 조작을 확인합니다.
7. 키 사고 시 단독 정지와 신규 발행 거부, 공동 키 교체/복구를 보여드립니다.
