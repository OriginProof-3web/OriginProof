# ADR 0002 — v4.0 납부 요청·AI 분석·하이브리드 검증

- 상태: 사용자 합의 방향을 개발 계획에 반영함. 세부 구현 계약·코드·연결·배포·평가 완료를 뜻하지 않습니다.
- 근거: ‘블록체인 저장 범위 구체화’ 대화의 [합의 기록](../mentoring_round1_blockchain_decisions.md)과 개발 계획서 v4.0 반영 요청.
- 기준: [개발 계획서 4.0 보존본](../development_plan_v4.0_snapshot.md)의 4·7~9·15.10·16·17·21.1절.
- 관계: [ADR 0001](0001-finals-contracts.md)의 제품 범위·온보딩·보호 필드 확장·로컬 한정 목표를 부분 대체합니다. 변경하지 않은 v1/v2 서명·세션·binding·키 교체·상태·gateway/consume 정책은 유지합니다.

2026-10-08 착수 기준 보완: 아래의 입력 제한·보존 기간·코드 제한·평가 기준 미정 기록은 [ADR 0003](0003-v4-development-baseline.md)에서 구체화했습니다. 새 납부 버전·필드·API는 같은 문서의 공유 계약 초안으로 작성했으며 소비자 검토·생성/구현은 후속입니다. 모델·공개 네트워크·행사 조건과 UI/UX 배치는 계속 별도로 결정합니다. 아래 내용은 최초 v4.0 방향 합의와 당시 미정 사항의 기록입니다.

## 1. 발행 검증의 범위와 근거

대표 사례는 기관·기업이 발행한 납부 요청입니다. 검증할 사실은 발행 출처·보호된 내용의 일치·현재 유효성이며 납부 의무나 금액의 업무상 정확성은 발행기관 책임입니다. 기관의 참여 가치는 자사 명의 사칭·납부 정보 변조를 구별할 공식 확인 수단입니다. 실제 도입 수요를 확인했다고 주장하지 않습니다.

보호 대상은 기관·요청 ID, 금액·통화, 수취 은행·계좌·예금주, 목적·기한, 발행 시각·유효기간, 특정 수신자 연결 정보입니다. 수정은 철회 후 새 요청 발행으로 처리합니다. 제외한 디자인·안내 문구까지 보호했다고 표현하지 않습니다.

기존 `PAYMENT_REQUEST`와 `OFFICIAL_DOCUMENT`, 두 합성 기관·카드 회귀를 유지합니다. 기존 은행 fixture 이름은 실제 은행 참여를 뜻하지 않습니다. 두 유형의 삭제·통합이나 새 기관명을 이번 개정에서 임의로 확정하지 않습니다.

## 2. 기관 인증과 등록 전 검사

가상 사업자 명부의 기관명·사업자번호·대표자명·개업일자·상태를 대조하고, 명부에 등록된 도메인의 업무용 이메일을 데모 코드로 확인합니다. 코드 만료·재사용 금지·시도 제한을 검사합니다. 국세청 API와 실제 메일 발송은 시연에 사용하지 않습니다.

발행 권한 신청 → 사전 지정 내부 승인자의 별도 계정 승인 → 운영자 최종 승인 → 온체인 활성화 확인 뒤에만 발행을 허용합니다. 자기 신청·타 기관 승인·임의 승인자 지정은 거부합니다. 신청자가 명부를 바꾸거나 이메일만으로 활성화할 수 없습니다.

발행마다 소속·권한·기관/계정/키 상태·입력/기간 → 내용 확정·서명 → 서명/해시/기관·키 연결 검사 → 등록·확정·재조회를 수행합니다. 무권한 API·직접 체인 호출 모두 차단합니다. 기존 trusted gateway가 대행하는 인증 범위는 유지하며 웹 인증을 체인 자체가 검증한다고 설명하지 않습니다.

## 3. 하이브리드 저장과 공개 검증

DB·보호된 파일 저장소에는 기관/계정/권한/승인 이력, 기관 발행 원본·서명, 비공개 수신자 정보, 제출 자료·분석/보고서, 등록/실패 이력을 보관합니다. 개인키는 별도 보호된 키 저장소에서 관리합니다.

체인에는 기관·키 식별자와 공개 signer, 요청 ID, 보호 내용 hash/digest가 결합된 불변 commitment, 기간, 필요한 검증용 수신자 연결값, 철회·키 폐기·기관 중지·사용 상태와 이력을 둡니다. 원문·계좌·개인정보·인증코드·개인키·AI 분석은 직접 올리지 않습니다. 추측 가능한 필드의 해시 노출 위험과 연결값 설계는 새 계약에서 검토합니다.

같은 요청 ID의 대응 규칙으로 DB 원본·서명과 체인을 연결합니다. DB 저장 후 체인 미확정은 등록 대기입니다. 불명확한 거래는 먼저 조회하고 무조건 재전송하지 않습니다. DB 변조는 재계산한 해시로 탐지하되 원본 삭제는 복원할 수 없습니다. 현재 상태는 체인에서 확인하고 조회 실패는 보류합니다. 실제 결제 확인 없는 consume은 납부 완료가 아닙니다.

공개 체인에 증거·이력을 남기고 권한 있는 검증자에게 서명 원본·서명·규칙·네트워크/계약 정보를 제공하여 서비스 API 밖 대조를 가능하게 하는 것이 목표입니다. 공개 네트워크·배포 범위·확정 기준·검증 도구 형태는 미정입니다. 로컬 EVM은 개발·복구용이며 공개 체인 목표 완료로 간주하지 않습니다. 원본 제공 권한, 기관 심사·키·등록 경로에 대한 신뢰는 여전히 필요합니다.

## 4. AI와 사용자 보고서

문자·대화 텍스트, 녹음 파일, 문서/이미지 세 입력을 지원합니다. 텍스트와 문장·시간대·페이지/위치를 보존하고 사칭·불안 조성·송금/계좌 변경 유도·민감정보 요구·링크/앱 설치·확인 방해 정황을 맥락과 함께 분석합니다.

위험 높음 / 주의 필요 / 뚜렷한 의심 정황 없음 / 판단 보류를 사용합니다. 임의의 확률 수치나 안전 보증을 하지 않습니다. 결과·의심 원문/위치·이유·유형·확인 행동과 발행 기록 검증을 함께 표시하되 AI 결과가 verification/lifecycle enum을 결정하지 않습니다. AI 판단으로 기관을 승인하거나 체인 등록하지 않습니다.

기록을 못 찾으면 AI 분석과 발행 확인 불가를 제공합니다. 인식 부족은 확인/보류이고 모델 실패는 성공으로 대체하지 않습니다. ID/QR/직접 필드 비교는 AI 없이 동작합니다. 기본 mock·기존 어댑터를 유지하며 실제 모델 평가·비용·합격선은 후속 결정입니다.

## 5. 보관 원칙

제출 자료·분석 입력은 처리 후 삭제가 기본이며 보고서는 선택 보관, 원본 파일은 별도 선택입니다. 기관 발행 원본·서명은 재검증용으로 분리 보관합니다. 정확한 보존 기간·처리 종료/삭제 시점·실패 잔여물 처리·저장 모델은 미정입니다. v3.0 Artifact의 최대 24시간을 새 입력 전체에 자동 적용하지 않습니다. 기존 Operation·VerificationSession 보존 설정을 바꾸면 전환을 기록합니다.

## 6. 호환성과 완료 조건

기존 `beneficiary_binding`은 기관 ID를 연결하므로 실제 계좌·예금주를 보호한 증거로 사용할 수 없습니다. V4-01에서 새 필드·정규화·버전·예시·Golden·생성 타입·OpenAPI·DB migration·필요한 ABI와 소비자 전환을 정의합니다. 정확한 새 버전 번호/필드명은 이 ADR에서 만들지 않습니다.

기존 카드 v1과 본선 schema 2.0.0은 원래 검증·서명 규칙을 유지하고 보호 범위를 표시합니다. 기존 Proof를 몰래 재서명하거나 새 보호 항목이 있었다고 표시하지 않습니다. 추가 보호가 필요하면 새 계약으로 재발행합니다. 코드 변경 전 관련 소유자가 공유 계약과 migration·되돌림·동시 지원을 검토합니다.

V4-01~08과 F16~F23을 기존 작업·F01~F15에 추가합니다. 파일 제한·모델 평가·보관·공개 네트워크 같은 미정 값은 해당 구현 전에 구체화합니다. mock/실제 모델, 로컬/공개 체인, 독립/연결 검증을 구분하며 이전 phase 완료를 v4.0 완료로 재사용하지 않습니다.

화면 배치·문서 목차·영상 길이·제출 규격은 [산출물 구체화 검토안](../final_deliverables_draft.md)에 준비만 하며 확정 정책으로 취급하지 않습니다.
