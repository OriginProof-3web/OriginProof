# ADR 0003 — v4.0 개발 착수 기준과 공유 계약 초안

> **유지·대체 범위:** 3절 보관·4절 데모 코드 및 공통 분석 제한은 5.0에서 유지합니다. 2절의 모든 입력 지원과 8절의 180입력 필수 구성은 대체됐으며 선정 입력만 적용·평가합니다. 5~7절 모델/API/서명·전환은 구 초안으로, 신규 지갑·문서 계약은 ADR 0004와 계획서 11장에서 다시 연결합니다.

> **2026-10-13 적용 안내:** 이 문서 본문은 당시 결정 기록입니다. 신규 개발은 [ADR 0004](0004-v5-governance-wallet-versioning.md)와 [최신 개발 계획서](../development_plan.md)을 따릅니다. 공동승인·기관 지갑 서명·문서 버전·입력 미정 정책은 새 결정으로 대체되며, 기존 v1/v2 자료의 서명·권한·상태·consume과 명시적으로 유지한 기본값은 보존합니다.

- 작성일: 2026-10-08 · 문서 버전: 0.1 · 적용: 개발 계획서 4.0의 V4-01~08.
- 근거: 사용자님의 “개발 최종 산출물에서 지금 해야 하는 것들을 진행하고 문서 업데이트” 요청.
- 상태: **개발 기본값·정책을 이번 요청 범위에서 선정함. 공유 모델/API/서명 계약은 구현 전 소유자 검토용 초안이며, 팀원 승인·runtime 지원·실제 성능을 확인한 상태가 아닙니다.**
- 책임: C 계약·인증·저장 조율, B 서명/ABI·공개 검증 검토, D 입력·평가·실패 검사, A 계약 소비·사용자 안내.
- 기준: [당시 개발 계획서 4.0](../development_plan_v4.0_snapshot.md), [ADR 0001](0001-finals-contracts.md), [ADR 0002](0002-v4-hybrid-verification.md). 이 문서는 그중 미정이었던 입력·보관·코드 제한과 새 계약의 착수안을 보완합니다. v1/2.0.0의 기존 서명·판정을 변경하지 않습니다.

## 1. 지금 선정한 것과 개발 중 검증할 것

| 영역 | 이번에 정한 착수 기준 | 이후 필요한 작업 |
| --- | --- | --- |
| 입력 | 2절의 형식·상한·처리 제한 | D/C 구현·경계값/실제 처리 검사, A 안내 연결 |
| 보관·소유권 | 3절의 자료별 기간·삭제·계정 정책 | C 삭제/권한 구현, D 실패·재시작 검사 |
| 기관 이메일 코드 | 4절의 만료·재발송·실패 제한 | C/A 구현, D 만료/경쟁/우회 검사 |
| 납부 모델·서명 | 5절의 새 버전·필드·정규화 초안 | C 원본 모델·Golden, B 교차 검증, A/D 소비자 검토 |

수치는 합성 데이터 시제품의 초기 개발 제한이며 법적 보존 의무나 검증된 처리 성능을 뜻하지 않습니다. 상향·완화가 필요하면 근거·영향·새 경계 검사를 기록하고 이 표의 기준 문서를 먼저 갱신합니다. 기준 미달 결과를 보고 합격선을 조용히 낮추지 않습니다.

## 2. 입력 지원과 자원 제한 — Q03

한 분석 요청은 텍스트 또는 파일 하나만 받습니다. 묶음 업로드·압축파일·외부 URL 수집·브라우저 녹음은 추가하지 않습니다. 녹음은 파일 업로드입니다. MiB는 1,048,576바이트이며 크기와 길이/페이지 제한을 모두 만족해야 합니다.

| 종류 | 지원 형식 | 초기 상한 | 검사·거부 |
| --- | --- | --- | --- |
| 텍스트 | UTF-8 텍스트 직접 입력 | Unicode 코드 포인트 10,000개 | 빈 문자열/공백만 입력 거부, 잘라서 성공 처리하지 않음 |
| 이미지 | PNG·JPEG·WebP, 정지 이미지 | 5MiB, 12,000,000픽셀, 1프레임 | 확장자·MIME·signature·실제 디코딩 일치, 손상/다중 프레임 거부 |
| 문서 | PDF | 10MiB, 10페이지 | 암호화·손상·첨부파일 포함 PDF 거부, 스크립트/외부 자원 실행 금지; 렌더링 페이지당 최대 12,000,000픽셀 |
| 녹음 | MP3, WAV(PCM), M4A(AAC) | 20MiB, 300초, 최대 2채널 | 실제 컨테이너/코덱·길이 검사, 손상/미지원 코덱 거부; 파일명만으로 신뢰하지 않음 |

텍스트·이미지 상한은 현재 `services/analyzer/src/originproof_analyzer/inputs.py`의 값과 일치합니다. PDF·녹음은 신규 개발 기준으로 현재 구현 지원을 뜻하지 않습니다. 변환 라이브러리/provider는 D가 기존 의존성을 확인해 선정하며 실제 변환 검사를 거칩니다.

PDF/녹음에서 추출한 텍스트도 총 10,000 코드 포인트를 상한으로 사용합니다. 초과하면 `EXTRACTED_TEXT_TOO_LONG`으로 보류/실패하고 일부만 분석한 결과를 전체 성공으로 반환하지 않습니다. 각 문장·페이지·시간대의 원문 위치를 유지합니다. 문서의 일부를 읽지 못하면 읽은 범위와 누락을 명시하고 전체 비교 성공을 만들지 않습니다.

- 업로드 완료·요청 수락부터 대기열·변환·분석을 포함한 작업 전체 제한은 **180초**입니다. 사용자 조작을 기다리는 UI 시간은 작업 안에 넣지 않습니다.
- 기존 LLM 호출 설정의 기본 **20초/호출, 최대 2회 재시도**를 재사용하되 남은 전체 제한을 초과할 재시도는 시작하지 않습니다. STT/OCR도 남은 시간 이내에 종료·취소하며 미완료 결과는 성공으로 만들지 않습니다.
- 계정당 실행 중 분석은 **1건**, 수락은 **10분당 5건**으로 제한합니다. 동일 요청 ID의 동일 입력 재조회는 새 분석·비용으로 세지 않습니다. IP 제한과 로그인 보호의 기존 규칙을 우회하지 않습니다.
- 작업 제한 도달 시 실제 provider 취소 가능 여부와 관계없이 사용자 결과를 실패/보류로 종료하고, 늦게 도착한 응답은 완료 상태·보관 선택을 덮어쓰지 못하게 합니다.
- 크기 제한은 업로드 스트림에서, 페이지/픽셀/시간/코덱 제한은 디코더에서 검사합니다. 변환은 제한된 프로세스·자원 안에서 수행하고 정상 처리 시간·메모리는 실제 구현 때 측정합니다.
- HTTP 의미는 크기 초과 413, 미지원 미디어 415, 내용/필드 오류 422, 요청 제한 429입니다. 수락 뒤 처리 실패는 작업의 실패 결과로 조회하며 HTTP 조회 성공을 분석 성공으로 해석하지 않습니다.

검사: 경계값 바로 아래/정확히 상한/바로 위, 확장자 위장, 손상·악성 파일, 추출 텍스트 초과, 느린 provider·전체 timeout·늦은 응답·중복 제출을 F12/F15/F16/F19로 연결합니다.

## 3. 분석 소유권과 보관·삭제 — Q05/Q06

**분석 제출·보고서/원본 보관은 준비된 테스트 계정 로그인 뒤 이용**하도록 선정합니다. 기존 8시간 서버 세션을 재사용하고 별도 익명 업로드 계정/소유권 이전 기능은 만들지 않습니다. 공개 ID/QR 조회는 계속 로그인 없이 가능합니다. 보고서 소유자라는 사실은 연결된 기관 Proof의 제한 원본 열람·비교 권한을 부여하지 않습니다.

보고서 보관과 원본 보관은 요청 수락 전에 각각 명시적 boolean으로 받으며 기본값은 둘 다 false입니다. 서로 독립된 선택으로 원본만 보관할 수도 있습니다. 원본은 업로드 파일 또는 직접 입력 텍스트를 뜻합니다. 보고서에는 필요한 인용·위치만 남기고 전체 추출 원문을 자동 복제하지 않습니다. 아래 기간은 계정 세션 만료와 별개이며 다시 로그인한 같은 소유자가 만료 전 접근할 수 있습니다.

| 데이터 | 기본·선택 보관 기간 | 기산·삭제 동작 |
| --- | --- | --- |
| 미선택 제출 원본·전체 추출 텍스트·provider 입력 | 정상/실패 종료 직후 삭제 | 작업 종료 경로에서 삭제, 오류 시 삭제 대기 기록; 처리 시간 180초 제한과 별개로 수락 후 1시간을 잔여물 최대 수명으로 설정 |
| 미선택 결과의 일시 전달본 | 종료 후 최대 10분 | 브라우저 결과 조회용으로 필요한 근거만 보관; `result_expires_at` 표시, 만료 즉시 접근 거부 후 삭제; 저장 이력 기능으로 취급하지 않음 |
| 선택 저장 보고서·필요 인용/위치 | 종료 후 7일 | 고정 `expires_at`, 조회할 때 연장하지 않음; 실패한 작업은 성공 보고서로 저장하지 않음 |
| 별도 선택 원본 | 요청 수락 후 7일 | 검사에 통과한 원본만 보관; 형식/악성 검사 실패 시 선택과 관계없이 삭제; 실패/보류의 진단 보관을 원하면 명시한 원본 선택만 적용 |
| 기관 발행 원본·서명·수신자 대응 | Proof의 `expires_at` 이후 30일 | 철회/consume해도 정해진 만료일까지의 보관을 줄이지 않음; 사용자 분석 삭제와 독립; 기간 종료 후 원본/비공개 대응 삭제 |
| Operation·감사 | 기록 시점 후 30일 | 기존 기준 유지; 원문·전체 계좌·코드·token 제외; 미해결 Operation은 해결 후 30일까지 연장하며 미해결 경고를 남김 |
| VerificationSession | 생성 후 24시간 | 기존 기준 유지; 원문 없이 검사 범위/상태/사유·시각 보관 |

삭제 대기 항목은 서비스 정상 가동 중 **5분 간격**으로 재처리합니다. 만료 자료는 물리 삭제 전에도 읽기·다운로드·분석 재사용을 거부합니다. 프로세스 중단으로 1시간/기간을 넘긴 잔여물은 재시작 시 정리하고, 정리 완료 전 신규 분석을 수락하지 않습니다. 서버가 꺼져 있는 동안 삭제가 실행되었다고 보증하지 않습니다. 임시 입력/전달본은 백업·로그·큐 본문에 복제하지 않고 큐에는 식별자만 넣습니다.

- 사용자는 자기 분석의 결과/저장 원본을 삭제할 수 있습니다. 논리 접근 차단은 즉시, 물리 삭제는 정상 가동 중 다음 정리 주기까지 완료합니다. 실행 중 삭제는 취소 표시를 남겨 늦은 결과의 재저장을 차단합니다.
- 서명된 기관 원본은 사용자 분석 삭제에 따라 지우지 않습니다. 보존 종료 뒤에도 체인 기록은 남지만 원본을 해시로 복원할 수 없습니다. 원본 없는 ID 조회에서는 서명/내용 검사 미실행과 `INCONCLUSIVE`를 표시하고, 보존된 발행 근거/상태만으로 전체 VERIFIED를 만들지 않습니다.
- 만료 후 독립 검증이 필요하면 권한 있는 대상이 기간 내 받은 서명 원본을 사용해야 합니다. 보고서·원본·별도 검증 자료에 각각 보존 한계를 안내합니다.
- 보호된 저장소를 사용하고 모든 객체 접근은 인증 계정/기관/지정 수신자를 확인합니다. 운영자 권한만으로 타인의 원본을 열람하지 않습니다. 새 보관 정책은 기존 운영 데이터를 자동 삭제하는 명령이 아닙니다.
- provider 측 보관과 삭제는 위 서버 보관 기준의 적용 범위가 아닙니다. 실제 모델 선택 시 전송 범위·provider 보관 설정을 확인하고 문서화합니다. 합성/사용 허용 자료만 사용합니다.

검사: 네 가지 보관 선택 조합, 세션 만료/재로그인, 다른 소유자, 삭제 중 처리 완료, 종료·실패·강제 종료·재시작, 기간 경계, 기관 원본과 분석 삭제 분리를 F21로 확인합니다.

## 4. 기관 이메일 코드 — Q07

기존 가상 기관 명부와 데모 메일함을 사용하며 실제 이메일을 보내지 않습니다.

| 설정 | 착수 값·처리 |
| --- | --- |
| 코드 | 암호학적 난수로 생성한 6자리 숫자, 선행 0 보존 |
| 유효시간 | 발급 후 5분, 만료 시각과 같으면 거부 |
| 재발급 | 최소 60초 간격, 계정·신청 묶음당 10분에 최대 3회 |
| 코드 실패 | 코드당 5회까지 비교, 5번째 실패 즉시 폐기; 계정·신청 묶음당 최근 15분에 실패 10회면 추가 비교/발급을 거부 |
| 범위 | 신청 ID·신청자 계정·기관 ID·명부 도메인과 일치하는 이메일에 결합 |
| 소비 | 올바른 코드 확인과 소비를 원자적으로 처리; 새 발급은 이전 코드를 즉시 무효화 |

재발급으로 실패 누적을 초기화하지 않습니다. 시간 제한에는 서버 시각을 사용하고 rate limit에는 재시도 가능 시점을 제공합니다. 신청 기관/이메일 변경은 기존 확인을 무효화하고 명부 대조부터 수행합니다. 코드 확인이 내부/운영자 승인·체인 활성화를 대체하지 않습니다.

검증 저장소에는 코드 평문 대신 서버 비밀키로 계산한 검증값을 둡니다. 데모 메일함의 일시 평문은 해당 신청자만 인증 후 볼 수 있고 만료/소비/재발급 시 삭제합니다. 코드·검증용 비밀키는 공개 API/감사 로그/Git에 남기지 않습니다. 메일함은 시연용 전달 수단이며 실제 이메일 소유 증명의 구현으로 설명하지 않습니다.

검사: 299/300초 경계, 재발급 전 코드·재사용·동시 확인, 시도 제한·재발급 우회·다른 신청자/기관·도메인 불일치를 F17로 확인합니다.

## 5. 납부 보호 모델·정규화 초안 — Q06

공유 계약 초안의 신규 `PAYMENT_REQUEST`는 **schema_version=3.0.0**으로 제안합니다. 필수 필드 추가를 기존 2.0.0으로 해석하지 않습니다. 기존 카드 1.0.0·요청형 2.0.0은 원래 규칙으로 읽고, 변경 없는 `OFFICIAL_DOCUMENT`는 2.0.0을 유지합니다. 개발 계획 4.0과 payload 버전은 별개입니다. C/B 검토 후 원본 모델·Golden을 함께 확정하며, 문서 번호만으로 새 버전을 수신 가능하다고 광고하지 않습니다.

`app_domain=originproof.finals`, 기존 secp256k1/Keccak-256·envelope signing fields·NFC/trim·정렬 JSON·null 포함·UTC 직렬화를 유지합니다. 새 정규화는 해당 버전 입력 모델에서만 수행하며 기존 `canonicalization.py`를 바꿔 구버전 결과를 바꾸지 않습니다.

| 위치·필드 | 필수 값과 정규화 초안 | 생성·비교 |
| --- | --- | --- |
| envelope의 `proof_id`, `issuer_id`, `key_id` | 기존 ID 규칙 유지 | 서버 생성/소속·현재 권한 확인; ID·기관을 발행 입력으로 신뢰하지 않음 |
| payload의 `amount_minor` | 1~9,007,199,254,740,991 정수; float/bool/지수 표기 거부 | 발행 입력과 비교; 소수 금액의 최소 단위 변환은 통화 규칙 적용 |
| `currency` | 대문자 ASCII 3자리, 공백 trim 후 대문자 변환 | 기존 통화 코드 규칙 유지; 지원 통화별 단위는 생성 계약에서 명시 |
| `payee_bank_name` | NFC/trim, 1~120 코드 포인트 | 수취 은행명 전체 비교; OCR 유사명 자동 동일시 금지 |
| `payee_account_number` | ASCII 숫자 6~32자리 | 입력 ASCII 공백·하이픈 제거 후 검사; 선행 0 보존, 숫자형 변환 금지 |
| `payee_account_holder` | NFC/trim, 1~120 코드 포인트 | 예금주 전체 비교, 내부 공백/대소문자 임의 치환 금지 |
| `payment_purpose` | NFC/trim, 1~500 코드 포인트 | 납부 목적 전체 비교; 디자인·주변 안내 문구는 이 필드로 추정하지 않음 |
| `due_at` | timezone 필수, UTC 초 단위; 소수초 거부 | `issued_at < due_at <= expires_at`; 같은 시각의 다른 timezone 표현은 동일 |
| `payer_binding`, `beneficiary_binding`, `target_hash` | 기존 2.0.0의 32바이트 canonical hash 규칙 유지 | 서버에서 생성, recipient binding/기관 연결/대상 참조를 각각 검사; 계좌 보호의 대체물이 아님 |
| `commitment_nonce` | 요청별 32바이트 난수, 소문자 hex 64자리 | 서버 생성·payload hash에 포함; 원본 제한 제공 시 포함, 공개 조회/로그에는 제외 |
| envelope의 `issued_at`, `expires_at`, `subject_binding_hash`, `nonce`, `single_use` | 기존 필수 규칙, 초 단위 UTC, 요청형 single_use=true | 발행 시각·수신자 binding·nonce는 서버 생성, 만료·권한/재사용 검사 유지 |

`commitment_nonce`는 공개 payload hash로 제한 필드의 후보를 추측하는 비용을 높이기 위한 버전별 난수입니다. 권한 있는 검증자는 서명 원본과 함께 이를 받아 재계산합니다. recipient token/salt와는 다른 값이며 수신자 인증 비밀을 공개하지 않습니다. 공개 envelope에는 제한 payload/이 난수를 제공하지 않습니다. 이것만으로 모든 정보 추론이 불가능하다고 보증하지 않습니다.

3.0.0 납부 자료의 내용 비교 대상은 금액·통화·은행명·계좌·예금주·목적·납부 기한·대상 참조와 자료에 표시된 발행기관/ID·발행/만료 시각입니다. 수신자는 인증 계정과 서명된 binding으로 검사합니다. 전체 비교에 필요한 값이 없으면 `PARTIAL_COMPARISON/INCONCLUSIVE`, 실제 불일치가 있으면 `TAMPERED`입니다. 새 필드 mismatch는 기존 `FIELD_MISMATCH`와 필드 경로를 쓰며 제한 원문의 기대값을 공개 오류에 넣지 않습니다.

AI 추출값·사용자 확인값·서버 발행값을 출처별로 구분합니다. 계좌 한 자리, 공백을 제외한 예금주/목적 한 글자, 기한·통화·금액 변경은 모두 검사해야 합니다. 기존 signature scheme 이름을 바꾸거나 AI 수준을 서명 원본에 포함하지 않습니다.

필수 계약 검토 자료: 새 정상/단일 필드 변조 Golden, 선행 0·Unicode NFC·timezone·범위 경계, 기존 v1/2.0.0 Golden 불변, 원본/DB 변조·도메인/chain 불일치, API→Python→생성 타입→B의 digest 비교. F14/F18/F23에 연결합니다.

## 6. API·보고서 공유 계약 초안

아래 경로는 **신규 기능의 제안 URL**이며 현재 실행 가능한 endpoint 목록이 아닙니다. 기존 Wn 구현과 대조한 뒤 C가 중복 경로 없이 OpenAPI로 확정하고 A/B/D가 소비합니다. 기존 v1 카드 endpoint·응답은 보존합니다. 인증은 기존 cookie·CSRF를 재사용합니다.

| 기능/예정 경로 | 최소 요청 | 결과·권한 경계 |
| --- | --- | --- |
| `POST /v1/finals/analyses` | multipart의 text 또는 file 중 하나, request_id, retain_report/retain_original(기본 false) | 로그인 계정, 202·analysis_id·상태·보관 선택/시각; 중복 요청은 기존 작업 |
| `GET /v1/finals/analyses/{id}` | 분석 ID | 소유자만 처리 상태·보고서·만료 시각; 미존재/타인 404, 본인 결과 만료 410 |
| `GET /v1/finals/analyses/{id}/original` | 분석 ID | 원본 보관을 선택한 소유자만 유효기간 내 제공; 임시 입력 다운로드는 제공하지 않음 |
| `DELETE /v1/finals/analyses/{id}` | 분석 ID·변경 요청 보호 | 소유자의 분석 결과/선택 원본 접근 즉시 차단·정리; 기관 발행 원본은 영향 없음 |
| `POST /v1/finals/proofs` | 유형/지원 schema, 유형별 payload 입력, 수신자 선택 ID, 만료, request_id | 승인 기관만 발행; 서버 생성 필드 주입 거부; Proof ID와 등록 Operation·대기/확정 구분 |
| `GET /v1/finals/proofs/{id}` | Proof ID | 기존 공개 필드만; 제한 payload/원문/계좌/binding 제외 |
| `POST /v1/finals/proofs/{id}/verify` | 자료의 비교 candidate, 값의 출처, request_id | 발행자/지정 수신자 권한 먼저 검사; 내용 비교·미실행 사유·현재 상태 |
| `GET /v1/finals/proofs/{id}/verification-material` | Proof ID | 원본 제공 권한이 있는 대상만 서명 원본·규칙·배포 식별 정보 |

기관 신청·이메일 확인·승인·키/Proof 변경·Operation 조회는 기존 W1~W4 계약을 재사용하고, 새 이메일 단계·보호 필드를 같은 계약에 확장합니다. 새 endpoint 별칭을 만들기 전에 기존 소유자 구현을 확인합니다. timeout/UNKNOWN은 새 발행·새 거래 요청으로 자동 전환하지 않습니다.

발행 입력 예시(공유 계약 검토용 합성 자료, 실행 예제가 아님):

```json
{
  "request_id": "req_demo_payment_001",
  "proof_type": "PAYMENT_REQUEST",
  "schema_version": "3.0.0",
  "recipient_id": "demo_recipient_001",
  "expires_at": "2026-10-10T12:00:00Z",
  "payload": {
    "amount_minor": 12000,
    "currency": "KRW",
    "payee_bank_name": "합성 시연 은행",
    "payee_account_number": "000123456789",
    "payee_account_holder": "합성 시연 기관",
    "payment_purpose": "합성 행사 참가비",
    "due_at": "2026-10-10T09:00:00Z",
    "target_ref": "demo-invoice-001"
  }
}
```

`target_ref`는 서버가 `target_hash`로 변환하는 발행 입력 전용 필드이며 서명 payload의 추가 필드가 아닙니다. recipient_id는 준비된 계정에 실제 존재해야 하며 위 문자열이 현재 계정이라고 주장하지 않습니다. 예시의 날짜 검사는 고정 테스트 시계에서 수행합니다. 서버가 기관/키·발행 시각·ID·bindings·nonce를 채우고 서명 원본을 생성합니다. 성공 예시는 새 모델 생성 후 실제 서명/해시·등록 결과와 함께 Golden으로 제공합니다.

권한 거부는 비교 이전에 403/객체 숨김 404, 기존 요청 ID에 다른 계좌·보관 선택을 보내면 409, 새 발행의 빈 목적·기한 순서 오류는 422를 기대합니다. 입력 계좌의 ASCII 공백·하이픈만 다른 경우 정규화 뒤 동일하고, 숫자 한 자리 변경은 내용 비교에서 TAMPERED를 기대합니다. 위 정상/거부 예시를 OpenAPI와 검사에 함께 옮깁니다.

분석 상태는 `QUEUED → PROCESSING → COMPLETED / FAILED / CANCELLED`의 서버 작업 상태를 기본으로 합니다. `COMPLETED`가 안전·발행 유효를 뜻하지 않습니다. 인식 부족·판단 보류는 보고서에 기록하고, 처리 자체가 불가능한 실패는 error로 기록합니다. 사용자 확인/수정은 처리 종료 뒤 별도 내용 비교 요청으로 연결하며 원래 추출 결과를 덮어쓰지 않습니다.

보고서 모델의 최소 계약 초안:

| 항목 | 필수 정보·분리 기준 |
| --- | --- |
| 식별·환경 | analysis_id, report_version, input_kind, created_at, 모델/프롬프트 버전, mock/live 구분; owner는 서버 내부 참조 |
| 추출 | 추출 범위·누락, 후보 필드별 value(없으면 null)·출처·원문 위치; 사용자 확인값은 별도 후보로 관리 |
| AI 결과 | risk_level=`HIGH / CAUTION / NO_CLEAR_SIGN / UNDETERMINED`, 한 줄 결과·이유·유형·확인 행동; 한국어 네 단계와 1:1 대응 |
| 근거 | 원문 인용, 문장 구간 또는 start_ms/end_ms 또는 1부터 시작하는 페이지·이미지 정규화 영역(x/y/width/height, 0~1); 없는 위치를 만들어 넣지 않음 |
| 발행 결과 | proof_id(없으면 null), verification_status·lifecycle_status·scope·checks·reason_codes·verified_at·network; AI가 값을 생성하지 않음 |
| 보관 | retain_report/retain_original, 각 expires_at·result_expires_at·삭제 상태; 선택과 실제 저장 결과 구분 |
| 실패/한계 | 오류 code·입력 필드 경로·재시도 가능 여부·미실행 검사·인식 한계; 비밀 원문/stack trace 제외 |

보고서의 `report_version=1.0.0`을 첫 공유 모델 초안으로 사용하며 Proof schema_version과 별개로 버전 관리합니다. 공개 검증 응답에 보고서·제한 payload를 합치지 않습니다. 작업 전체 결과와 발행 검사 상태를 하나의 성공 boolean으로 줄이지 않습니다.

요청 ID는 기존 `(account_id, action, request_id)`로 식별하고 분석 입력 종류·내용 digest·보관 선택을 포함한 fingerprint가 다르면 409로 거부합니다. fingerprint는 접근 제한된 작업 참조로만 보관하며 공개하지 않습니다. 같은 요청을 다시 보냈다는 이유로 보관 기간을 연장하지 않습니다. 401/403/404/410/413/415/422/429와 처리 오류의 예시를 OpenAPI에 함께 작성합니다.

## 7. 데이터 전환·소비자 인계 순서

1. C는 현재 Wn 구현의 실제 모델/API·DB를 대조하고 5~6절 초안의 차이를 기록합니다. B는 commitment/서명 경계, D는 추출/위치/평가, A는 오류·보관 안내 소비를 검토합니다. 의견을 받지 않았으면 “소유자 검토 대기”로 기록합니다.
2. 원본 모델을 유형·버전으로 분기해 새 3.0.0 읽기/검증과 새 보고서 계약을 추가합니다. JSON Schema·TypeScript·OpenAPI·Golden은 기존 생성 경로를 사용하며 손으로 복제하지 않습니다.
3. DB는 새 필드/보관 시각/소유권·작업 상태를 우선 추가합니다. 기존 서명 원본 bytes·payload hash를 갱신하거나 기존 자료에 새 보호 필드를 가짜로 채우지 않습니다. 신규 계약 배포 전 모든 소비자가 지원 여부를 확인합니다.
4. 새 발행 활성화 전에 정상·거부·경계·구버전 회귀·실제 체인 연결을 검사합니다. B가 기존 digest commitment로 새 payload를 수용할 수 있으면 ABI는 유지하고, 변경 필요 시 ABI/manifest/Adapter/indexer를 함께 버전 관리합니다.
5. 기관 원본의 기존 자료는 보존 만료가 지난 경우에도 문서 업데이트만으로 삭제하지 않습니다. 전환 시 목록·기간 영향을 dry-run으로 확인하고, 승인된 보존/정리 절차에 따라 적용합니다. 이번 작업은 dry-run이나 삭제를 실행하지 않습니다.
6. 실패하면 새 버전의 신규 발행/새 경로를 중단하고 기존 지원 경로를 유지합니다. 이미 발행된 새 Proof는 같은 버전의 읽기/검증 규칙으로 보존하며 구버전으로 재해석하지 않습니다. 체인 기록·폐기·consume을 DB rollback으로 되돌렸다고 표시하지 않습니다.

인계에는 원본 모델/생성물 SHA·필드/예시·오류·호환성 표·migration과 되돌림 한계·단위/통합 검사·미완료를 포함합니다. 문서 초안은 팀 합의나 코드 리뷰를 대신하지 않습니다.

## 8. AI 평가의 선행 기준 — Q04 일부

모델 이름·STT/OCR 구현체와 유료 실행 예산은 실제 비교 후 결정합니다. 지금은 비교할 데이터·방법·초기 통과 기준을 고정합니다. 기존 mock 기본값과 설정 경로를 유지하고 이 문서로 유료 호출을 시작하지 않습니다.

- 기본 합성 사례 **60개**: 네 위험 수준별 15개. 각 사례를 텍스트·녹음·문서/이미지로 만들어 **180개 입력**을 준비합니다. 문서/이미지 경로에는 PDF와 정지 이미지를 모두 포함합니다.
- 개발용 원본 24개(수준별 6개), 보류 평가용 원본 36개(수준별 9개)로 나눕니다. 같은 사례의 세 입력은 반드시 같은 집합에 배정합니다. 변형으로 데이터 수만 늘려 독립 표본 수를 과장하지 않습니다.
- 평가 전에 D가 기대 수준·핵심 필드·근거 위치를 작성하고 C 또는 A가 검토합니다. 모호한 사례는 보류로 정리하며 평가 결과를 보고 정답을 바꾸지 않습니다. 최종 모델 선택은 보류 집합을 반복 튜닝하는 방식으로 수행하지 않습니다.
- 추가 실패 사례 **최소 12개(입력 경로별 4개)**: 빈/누락·잡음/저화질, 삽입 지시, provider/형식 오류·시간 초과 등을 포함합니다. 발행 결과와 AI 결과의 독립 조합은 F20으로 별도 검사합니다.

| 지표 | 정의·초기 목표 | 완료 시 기록 |
| --- | --- | --- |
| 위험 분류 | 보류 집합 네 수준 macro-F1 ≥ 0.80, 위험 높음 recall ≥ 0.90 | 입력 경로별·합산 confusion matrix/분모, UNDETERMINED도 클래스에 포함 |
| 보호 필드 추출 | 읽을 수 있다고 사전에 표시한 필드의 정규화 후 완전 일치율 ≥ 0.95 | 금액/계좌 등 필드별·경로별 결과; null/오추출 모두 오답 |
| 근거 연결 | 제공한 인용이 실제 원문·지정 위치에 대응하는 비율 ≥ 0.95 | 문장·페이지/영역 확인, 음성은 정답 구간과 ±2초 허용; 예상 근거 누락도 별도 집계 |
| 실패·과장 금지 | 준비한 실패 사례 모두에서 추측값·안전 보증·AI의 발행 판정 덮어쓰기 없음 | F16/F19/F20 사례별 통과/실패; 평균 점수로 상쇄하지 않음 |
| 지연·비용 | p50/p95·최대 시간, 입력당 실제 비용 측정; 180초 작업 제한 준수 | 실제 환경·모델·길이·실행 횟수; 정상 입력 timeout도 실패에 포함 |

이 값은 초기 목표이며 측정된 성능이 아닙니다. 보고할 때 소규모 합성 평가의 한계·실패 유형·사람의 정답 검토를 명시합니다. 모델 비교 전에 데이터 manifest/분할·지표 계산 방식을 고정하며 변경하면 새 평가 버전으로 처음부터 기록합니다. 화면에 이 지표를 개별 입력의 피싱 확률로 표시하지 않습니다.

## 9. 공개 체인·독립 검증의 선행 조건 — Q02 일부

공개 네트워크를 지금 임의로 선정하지 않습니다. 후보는 기존 EVM 계약/서명 호환성, 공개 RPC·조회 가능성, 계정/가스 조달, 비용, 서비스 중단/reorg 시 복구, 검증자가 사용할 확정 기준을 비교해야 합니다. 후보가 정해지면 최신 네트워크 문서로 확인하고 실제 배포 범위·예산을 별도로 기록합니다.

B/C는 `네트워크·chain ID / 배포 계약·버전 / 가스·RPC 비용 / 확정 규칙 / 재배포·reorg 대응 / 독립 검증 방법`을 한 목록으로 제공합니다. 로컬의 1 confirmation을 공개 네트워크에 그대로 적용하지 않습니다. 위 항목이 미정인 동안 로컬 구현·자료 준비만 완료 처리할 수 있습니다.

독립 검증의 최소 제공물은 **권한 있는 서명 원본 + 검증 규칙 + ABI/배포 식별 정보 + 기존 도구로 재현 가능한 절차**로 잡습니다. 실행 도구를 별도로 만들지는 실제 재현 난도를 보고 결정합니다. 검증 절차는 서비스 API 없이 hash/서명/체인 발행 근거·현재 상태를 대조하고, 원본 만료·RPC 실패·네트워크 불일치를 성공으로 만들지 않아야 합니다.
