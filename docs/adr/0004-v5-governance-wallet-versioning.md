# ADR 0004 — 5.0 공동승인·기관 지갑 서명·문서 버전 관리

- 작성일: 2026-10-13 · 적용 기준: 개발 계획서 5.0
- 상태: **사용자가 선택한 개발 방향을 반영한 결정 기록 / 세부 공유 계약 검토·구현·연결 검증은 후속 작업**
- 근거: 1·2차 멘토링 이후 계획 개정 요청, 첨부 기획서, 기존 개발을 재사용하는 방향 선택, 입력은 팀 회의 후 확정한다는 답변입니다.
- 기준: [최신 개발 계획서](../development_plan.md), [4.0 보존본](../development_plan_v4.0_snapshot.md).
- 관계: [ADR 0001](0001-finals-contracts.md)·[0002](0002-v4-hybrid-verification.md)·[0003](0003-v4-development-baseline.md)의 아래 변경 범위를 신규 경로에서 대체합니다. 과거 계약과 결정 이유는 보존합니다.
- 담당: B 체인·ABI·권한, C 모델·API·DB·전환, A 지갑·화면, D 분석·독립 실패 검사입니다.
- 2026-10-14 후속: [공유 계약 v5-shared-0.1](../shared_contract_v5.md)과 실제 준비 모델·생성물·독립 서명 검사를 추가했습니다. 소유자/소비 리뷰와 서비스 구현·연결 완료는 아직 기록하지 않습니다.

## 1. 배경과 적용 범위

이전 설계는 서버 기관 서명기와 허가된 gateway, 운영자 최종 승인으로 발행 근거를 연결했습니다. 5.0에서는 공동승인과 기관의 직접 서명으로 권한을 분산하고, 같은 문서의 변경 이력을 버전으로 연결합니다. 기존 인증·Operation·복구·화면·검사 자산을 재사용하며 전체 TypeScript 재작성은 채택하지 않습니다.

검증 대상은 등록 기관의 발행 사실, 검사한 내용의 일치, 현재 상태입니다. 내용의 사실성·납부 의무·실제 결제·행동의 안전을 보증하지 않습니다. 세 승인 지갑을 같은 팀에서 관리하는 시연을 실제 독립 기관 운영으로 표현하지 않습니다.

| 영역 | 신규 5.0 경로 | 보존할 기존 경로 |
| --- | --- | --- |
| 기관 권한 | 등록·키 교체·재활성화 2-of-3, 단독 긴급 정지 | 과거 배포·권한 이력과 기존 자료 읽기 |
| 기관 업무 서명 | 기관 지갑 EIP-712, 컨트랙트 직접 검증 | v1/v2 서명·정규화·Golden·과거 서명 검증 |
| 내용 변경 | 같은 documentId의 다음 버전, 이전 최신 버전 대체 | 기존 Proof ID·철회·새 ID 재발행 계약 |
| 사용 처리 | 공개 안내의 조회·비교에 consume 없음 | 기존 요청형 binding·single_use·consume 회귀 |
| 사용자 입력 | 지원 종류·우선순위·원본 업로드 형식은 회의 후 결정 | 기존 텍스트/이미지 추출 코드와 합성 검사 자산 |
| AI | 규칙·구조화 분석·실제 근거 대조, 발행 판정과 독립 | 기존 provider·오류 처리·Mock |

개발 계획 5.0은 API·서명 schema·문서 내용 버전·배포 버전과 다릅니다. 기존 자료의 ID·서명·hash·상태를 새 계약으로 소급 해석하지 않습니다.

## 2. 기관 확인과 공동승인

가상 명부 → 데모 이메일 코드 → 지정된 별도 내부 승인 → 기관 지갑의 일회성 키 보유 증명 → 고정 제안 → 서로 다른 승인자 2명 승인 → 체인 실행·재조회 순서입니다. 내부 승인은 담당자 권한 확인이며 플랫폼 공동승인과 별개입니다.

| 동작 | 권한·검사 |
| --- | --- |
| 기관 등록 | 배포 시 고정한 서로 다른 승인자 3명 중 2명 |
| 키 교체 | 새 키 보유 증명과 2-of-3 |
| 기관 재활성화 | 2-of-3 |
| 긴급 기관 정지 | 승인자 1명 또는 해당 기관의 활성 키 |
| 발행 | 소유 기관의 현재 활성 키 서명, 기관 ACTIVE |
| 철회 | 해당 문서 소유 기관의 현재 활성 키 서명, 정지 중에도 허용 |

제안은 기관 ID·공개 메타데이터 hash·발행 주소·작업 종류·만료에 묶습니다. 중복 승인·만료·제안 내용 변경·타 기관 키 증명을 거부합니다. 두 번째 승인 트랜잭션에서 실행하고 상태 재조회 후 활성화를 표시합니다. 웹 운영자 혼자 활성화하거나 배포자 권한·업그레이드로 공동승인을 우회하지 못하게 검사합니다. 승인자 교체 운영 기능은 후속 검토입니다.

정지는 신규 발행을 차단하고 기존 안내에 경고를 표시합니다. 단독 재활성화는 허용하지 않습니다. 자유 입력 심사자료와 개인정보는 온체인에 넣지 않습니다.

## 3. 기관 지갑 서명과 내용 검사

기관 지갑이 업무 payload에 서명합니다. 앱·API·DB는 신규 기관 개인키를 수집·생성·보관하지 않습니다. 중계자는 가스용 트랜잭션에 서명할 수 있지만 기관 업무 서명을 대신 만들 수 없습니다. 지갑 주소만으로 웹 권한을 부여하지 않습니다.

1. API가 권한·필드·기간을 검사하고 버전별 원본과 서명 초안을 준비합니다.
2. 기관 브라우저가 원본 bytes의 SHA-256을 다시 계산하고 보호 필드·기간·대상을 보여줍니다.
3. 지갑이 EIP-712 payload에 서명합니다. 주소·네트워크·서명 대상 변경 시 새 검사를 요구합니다.
4. API는 payload·서명을 검사하고 원본·서명·Operation을 같은 DB 트랜잭션에 저장합니다.
5. 중계자 또는 기관이 동일 payload·서명으로 제출하고 컨트랙트가 검증합니다.
6. 성공 receipt·이벤트·문서 상태를 대조한 뒤 확정을 표시합니다.

도메인에는 서비스명·서명 버전·chainId·verifyingContract를, 업무 payload에는 action·issuerId·docKey·documentId·version·원본/보호 내용 hash와 알고리즘·서명 schema·keyId·issuedAt·expiresAt·nonce·deadline을 포함합니다. **정확한 Solidity 타입·필드명·직렬화는 C/B가 하나의 Golden으로 고정할 계약 초안 사항**입니다. 현재 런타임 지원을 선언하지 않습니다.

발행·철회 action을 분리하고 nonce를 기관별로 원자적으로 소비합니다. deadline은 서명 제출 기한, expiresAt은 문서 유효기간입니다. msg.sender가 중계자라는 사실로 기관 서명을 생략하지 않습니다. 서명 거절은 실패/취소로, 제출 결과 미확인은 UNKNOWN으로 처리합니다.

원본 bytes 전체 비교와 보호 필드 비교를 별도 결과로 제공합니다. 기존 Keccak 기반 payload hash를 SHA-256으로 일괄 변경하지 않습니다. QR을 붙인 렌더링 사본과 hash 대상 원본을 구분합니다. ID 조회만 한 경우 받은 내용의 일치를 주장하지 않습니다.

## 4. 문서 소유·버전·키 사고

documentId는 `keccak256(abi.encode(issuerId, docKey))`를 기준으로 계산하며 최종 인코딩은 공유 계약과 교차 Golden으로 고정합니다. 검증된 서명자의 기관으로 ID와 소유권을 검사합니다. 키 교체로 소유 기관을 바꾸지 않습니다.

최초 버전은 1, 다음 버전은 최신 + 1입니다. 새 버전 등록·최신 포인터 변경·ACTIVE인 이전 최신 버전의 SUPERSEDED 전이를 한 트랜잭션에서 처리합니다. 이미 REVOKED인 이전 최신은 철회 상태를 유지하며 대체 이벤트를 내지 않습니다. 이 버전의 재철회는 거부하고 실패 nonce를 소비하지 않되, 과거 SUPERSEDED 버전의 첫 철회는 허용합니다. 원본/hash는 덮어쓰지 않으며 최신 버전 철회로 이전 버전을 자동 활성화하지 않습니다. QR은 documentId와 버전을 식별하고 최신 조회 링크는 실제 조회 버전을 표시합니다.

업무 처리, 문서 버전 상태, 기관/키 경고, 검사 결과를 분리합니다. 문서 상태는 ACTIVE·REVOKED·SUPERSEDED와 기간에 따른 EXPIRED를 사용하며 정확한 응답 enum은 공유 모델에서 고정합니다.

정상 키 교체는 구키의 신규 발행을 차단하되 과거 정상 발행 서명을 위조로 바꾸지 않습니다. 유출 시점이 불명확하면 과거 안내에도 추가 확인 경고를 표시합니다. 정지 → 새 키 공동승인 → 필요한 문서 철회 → 공동 재활성화를 검사합니다. 기존 v1/v2의 유출 키·consume 판정은 그 버전의 규칙을 유지합니다.

## 5. 저장·현재 상태·복구

원본·서명·심사자료·AI 결과·계정/권한은 체인 밖에 둡니다. 체인은 기관/키 이력·메타데이터 hash·승인 규칙/이력, 문서 소유·버전·내용 hash·기간·최신 포인터·철회/대체·nonce를 기록합니다. 현재 상태는 신뢰 설정의 체인에서 직접 확인하며 projection은 조회 편의와 복구용입니다.

DB와 체인을 단일 원자적 커밋으로 취급하지 않습니다. 제출 전 Operation 저장, 멱등 충돌 검사, UNKNOWN 재조회, receipt 뒤 DB 실패 복구를 재사용합니다. 직접 제출 txHash도 네트워크·계약·성공 receipt·기관/문서/버전/hash를 저장 요청과 대조합니다. hash로 삭제된 원본을 복원할 수 있다고 설명하지 않습니다.

새 통합 Registry는 별도 비업그레이드 배포를 목표로 합니다. 과거 주소·ABI·manifest와 읽기 경로를 보존하고 배포 식별을 혼합하지 않습니다. 실패 시 새 발행을 중단하고 기존 읽기를 유지하며 체인 확정 기록을 DB rollback으로 되돌릴 수 없습니다.

## 6. 입력·AI·보관에서 유지하거나 변경한 기준

- 입력 종류·우선순위·사용자 원본 업로드 형식은 V5-Q01에서 결정합니다. ADR 0003의 세 입력 필수·180입력 평가를 자동 적용하지 않습니다.
- 후보 제한은 선택한 형식에만 적용합니다. 공통 분석 작업 제한·보관/삭제·데모 이메일 코드 기본값은 계획서 8.2·9장을 유지합니다.
- 위험 높음·주의 필요·뚜렷한 의심 정황 없음·판단 보류의 의미를 유지합니다. 정확한 enum은 공유 모델에서 결정하며 이전 초안 이름과 혼합하지 않습니다.
- 합성 원본 60개·개발 24/보류 평가 36개 분할을 유지하고 선택된 입력만 평가합니다. 모델·유료 실행·provider 설정은 V5-Q05에서 결정합니다.
- Decisions API는 V5-Q06의 후속 UX 검토 후보입니다. 현재 7주 구현 작업·필수 KPI·완료 조건을 배정하지 않습니다.
- 공개 네트워크·배포 범위·확정 기준은 V5-Q04입니다. 로컬 시연과 공개 목표 달성을 따로 기록합니다.

수용 기준은 계획서의 V5-F01~21, UI 검사는 UX01~14입니다. 구버전 F01~23·Golden은 과거 정의로 보존하고 새 검사 통과로 재사용하지 않습니다. 문서 동기화는 API·Schema·ABI 생성, 배포·기능 검사, 작성자 외 리뷰를 대신하지 않습니다.

공유 모델/API/서명·ABI·migration의 세부 고정은 V5-Q03, 기존 PR 채택·연결은 V5-Q08, 구자료 전환·보존은 V5-Q09로 추적합니다. 이미 선택한 공동승인·기관 서명·버전 관리 방향을 다시 승인 대기로 되돌리지 않습니다.
